## 1. 两套账号体系（必须先分清，否则后面全错）

系统里存在**两个完全独立的账号表**，不共享密码、不共享会话、不发生同步。

| 维度 | 业务账号 | 后台账号 |
| --- | --- | --- |
| 模型 | `apps.users.User`（`AbstractBaseUser` 子类，`users/models.py:24`） | `django.contrib.auth.models.User`（`INSTALLED_APPS` 含 `django.contrib.auth`，`settings.py:234`） |
| 表名 | `users`（`users/models.py:66`） | `auth_user`（Django 默认） |
| 密码字段 | `password_hash`（`CharField(max_length=255)`，`users/models.py:37`） | `password` |
| 哈希算法 | **bcrypt cost=12，本项目自己调**（`users/models.py:80-97`，`rounds=12` 于 `:84`） | Django `PASSWORD_HASHERS` 链，播种为 `pbkdf2_sha256` |
| 认证入口 | `Authorization: Bearer <JWT>` → `JWTAuthentication`（`settings.py:394-396`） | Django session cookie（`sessionid`）→ `/admin/login/` |
| 角色 | `role ∈ {SUPER_ADMIN, COMPETITION_ADMIN, PLAYER}`（`users/models.py:30-38`） | `is_staff` / `is_superuser` |
| 归属比赛 | `competition` 外键（`users/models.py:40-46`） | 无此概念 |
| 权限 | 细粒度权限键数组（`permissions` TEXT 存 JSON，`users/models.py:48`） | Django `Permission` / `Group` |
| 谁在用 | 前端 Vue SPA 的全部 `/api/*` | `/admin` 后台与日志查看器（`backend/logviewer/`）的登录 |

**为什么必须隔离**——`users/models.py:1-5` 的模块 docstring 写明了设计原因：

```
注意：Django 自带 auth.User 与本系统 User 字段差异较大（权限范围字段、role 枚举、
tokenVersion 等），故自定义 AbstractBaseUser 体系，避免与 contrib.auth.User 冲突。
```

**隔离是怎么实现的**：

- 业务 `User` 继承 `AbstractBaseUser`，但 `settings.py` 里**没有** `AUTH_USER_MODEL` 设置，
  因此 Django 的 `request.user`（由 `AuthenticationMiddleware` 提供，`settings.py:286`）永远指向 `auth.User`，业务侧完全不用它。
- 业务侧取用户只有两条路：DRF 的 `JWTAuthentication._get_user()`（`authentication.py:139-150`），
  以及中间件里"仅作日志上下文"的 `decode_jwt_payload`（`middleware.py:180-196`）。两处都 `from apps.users.models import User`。
- `settings.py:158-161` 的注释把两套超管讲清了：业务超管是 `apps.users.User`（前端 JWT 登录用，`role=SUPER_ADMIN`），
  后台超管是 `django.contrib.auth.User`（`/admin` 登录用，`is_staff`/`is_superuser`）。

> ⚠️ **首次 `migrate` 会用同一份 `SEED_ADMIN_*` 凭据在两套体系里各建一个超管**
> （`settings.py:158-173`），所以叫同一个名字（默认 `admin`）却是**两行不同表的记录、两套不同的密码哈希**。
> 重写时若把两套合并，会立刻破坏 `/admin` 与日志查看器的登录，以及 `PASSWORD_HASHERS` 的算法假设。

### 1.1 `PASSWORD_HASHERS` 的硬约束（重写时极易踩）

`settings.py:374-381` 的注释逐字写明了后果：

```
# 与原 bcryptjs cost=12 兼容（业务 users 表为自定义 User，自行用 bcrypt 校验 password_hash，
# 不走本列表，故下方顺序/增删不影响业务登录）。
#
# 注意：必须同时保留 Django 默认算法。/admin 后台使用 django.contrib.auth.User，
# 其密码由 createsuperuser / migrate 播种为 pbkdf2_sha256；若此处只留 bcrypt，
# identify_hasher() 会因找不到 pbkdf2 算法使 check_password 恒返回 False，
# 表现为「后台账号密码正确却永远登录失败」。保留默认算法不影响 bcrypt 已有的哈希。
```

| 项 | 值 | 位置 |
| --- | --- | --- |
| 列表内容 | `BCryptSHA256PasswordHasher`、`BCryptPasswordHasher`、`PBKDF2PasswordHasher`、`PBKDF2SHA1PasswordHasher`、`Argon2PasswordHasher`、`ScryptPasswordHasher` | `settings.py:382-389` |
| bcrypt 参数 | `bcrypt.gensalt(rounds=12)` | `users/models.py:84` |
| 业务侧是否走该列表 | **否**——`User.set_password` / `check_password` 直接调 bcrypt | `users/models.py:80-97` |

## 2. JWT：签发与校验

### 2.1 算法与配置

| 项 | 值 | 来源 |
| --- | --- | --- |
| 算法 | `HS256`（模块级常量 `_ALGORITHM`，非 settings 项） | `authentication.py:20` |
| 密钥 | `settings.JWT_SECRET` ← 环境变量 `JWT_SECRET`，**必填，未配置进程拒绝启动** | `settings.py:26-31` |
| 弱密钥黑名单 | 6 个已知弱值（`your-dev-secret-change-in-production` / `secret` / `jwt-secret` / `change-me` / `password` / `123456`）→ 拒绝启动 | `settings.py:34-46` |
| issuer (`iss`) | `JWT_ISSUER`，默认 `gipfel-competition` | `settings.py:155` |
| audience (`aud`) | `JWT_AUDIENCE`，默认 `gipfel-competition-client` | `settings.py:156` |
| 有效期 | `JWT_EXPIRES_IN`，默认 `24h`；解析器支持 `s/m/h/d`，无法解析时回退 24 小时 | `settings.py:157`、`authentication.py:27-43` |
| 传输 | `Authorization: Bearer <token>`；`keyword = "Bearer"`，比对时大小写不敏感 | `authentication.py:90`、`:130-137` |
| 库 | `PyJWT`（`import jwt`），**不是** SimpleJWT | `authentication.py:14` |

> 🔎 `settings.py:439-449` 有一段 `SIMPLE_JWT` 配置，但它**只是配置默认值**：
> `REST_FRAMEWORK.DEFAULT_AUTHENTICATION_CLASSES` 挂的是自定义的
> `apps.auth.authentication.JWTAuthentication`（`settings.py:394-396`）。
> `authentication.py:88` 的 docstring 说"复用 SimpleJWT 的 ALGORITHM/ISSUER/AUDIENCE 配置"，
> 但代码实际直接读 `settings.JWT_SECRET` / `JWT_ISSUER` / `JWT_AUDIENCE`（`authentication.py:63,73-78`），
> **与 `SIMPLE_JWT` 字典没有代码级耦合**。重写时不要以为改 `SIMPLE_JWT` 就能生效。

### 2.2 claims 全集

签发处只有一个函数：`create_jwt(user)`（`authentication.py:46-67`）。

| claim | 类型 | 值 | 用途 | 代码 |
| --- | --- | --- | --- | --- |
| `sub` | string | `str(user.pk)`（**字符串**，不是 int） | 反查用户 | `authentication.py:53` |
| `username` | string | `user.username` | 操作员日志上下文 | `:54` |
| `role` | string | `user.role` | 日志上下文 / Socket.IO 会话 | `:55` |
| `tv` | int | `user.token_version` | **顶号判定**（与 DB 当前值比对） | `:56` |
| `cid` | int \| null | `user.competition_id` | 比赛归属（日志上下文 / Socket.IO 房间） | `:57` |
| `iss` | string | `settings.JWT_ISSUER` | 签名校验 | `:58` |
| `aud` | string | `settings.JWT_AUDIENCE` | 签名校验 | `:59` |
| `iat` | datetime | `now`（UTC） | 标准声明 | `:60` |
| `exp` | datetime | `now + _expires_in()` | 标准声明 | `:61` |

**校验处**：`decode_jwt_payload(token)`（`authentication.py:70-83`）只做一件事——
`jwt.decode(token, JWT_SECRET, algorithms=["HS256"], issuer=..., audience=...)`；
任何 `PyJWTError`（含 `ExpiredSignatureError`、`InvalidIssuerError`、`InvalidAudienceError`）
或其它异常一律 `return None`（**不抛**）。这一点是契约：`OperatorContextMiddleware` 依赖它"失败不阻断"（`middleware.py:184-198`）。

### 2.3 `JWTAuthentication.authenticate()` 的判定顺序（顺序本身是契约）

`authentication.py:92-124`，逐条按源码顺序：

| # | 条件 | 行为 | `code` 参数 |
| --- | --- | --- | --- |
| 1 | 无 `Authorization` 头 / 不是两段式 `Bearer <x>` | `return None`（交给 `IsAuthenticated` 兜底 → 401） | — |
| 2 | `decode_jwt_payload` 返回 None | `AuthenticationFailed("登录已过期，请重新登录", code="expired")`（`:100-102`） | `expired` |
| 3 | `User.objects.get(pk=sub)` 查不到（`DoesNotExist` 或任何异常） | `AuthenticationFailed("登录已过期，请重新登录", code="invalid_user")`（`:106-108`） | `invalid_user` |
| 4 | `payload["tv"] != user.token_version`（`:111`） | `AuthenticationFailed("账号已在其他设备登录", code="token_version_mismatch")`（`:112-114`） | `token_version_mismatch` |
| 5 | `user.must_change_password` 为真且路径不在放行表内 | `AuthenticationFailed("账号需先修改初始密码", code="must_change_password")`（`:120-122`） | `must_change_password` |
| 6 | 全部通过 | `return (user, token)` | — |

`authenticate_header()` 返回 `"Bearer"`（`:126-127`），使 DRF 在无凭据时回 `WWW-Authenticate: Bearer` 且状态码为 401（而非 403）。

> ⚠️ **第 3、4 步之间没有 `is_active` 校验**（`authentication.py:104-114` 直接跳到 `tv` 比对）。
> 后果：账号被禁用（`is_active=False`）后，**已签发的旧 token 仍可访问全部接口直至自然过期**。
> 禁用只在登录时被拦（`auth/views.py:153-154` 返回 403）。见 §11 缺陷 D-02。

> ⚠️ **`code=` 参数在响应里被丢弃**。`authentication.py` 给每个分支都传了 `code=`，
> 但 `exceptions.py:63-65` 只提取 message：
>
> ```python
>     # DRF 默认异常（权限/认证/校验）
>     message = _drf_message(exc, response)
>     return _wrap(response.status_code, message)
> ```
>
> `_wrap(code, message)`（`:68-71`）调 `error(code, message, None)`，
> 而 `response.py:54` 的 `error()` 产出的体是 `{"code": <int>, "message": <str>, "data": None}` ——
> **响应里没有机器可读的错误码字段**。前端只能按 HTTP 状态与**中文 message 文本**区分语义
> （见 §4.3 与 §6.4）。`exceptions.py` 全文 133 行内**没有** `errorCode` / `get_codes` 之类逻辑。
> 这是重写时必须显式决策的一处契约（§10 R-6）。

## 3. 顶号 / 吊销机制（`token_version`）

### 3.1 语义

`User.token_version`（int，默认 0，`users/models.py:55`）是一个**账号级会话代际计数器**。
JWT 里冻结了签发时的 `tv`；只要 DB 里的 `token_version` 被 +1，**该账号所有已签发的 JWT 立即全部失效**，
下一次请求在 `authenticate()` 第 4 步被拒（`authentication.py:110-114`）。

这是**单设备登录**设计：新登录顶掉旧设备，而不是并存。

### 3.2 所有递增触发点（`origin/master` 全集）

| # | 触发场景 | 代码 | 递增后是否通知旧 WebSocket |
| --- | --- | --- | --- |
| 1 | 每一次成功登录（顶号） | `auth/views.py:156-158` | ✅ `emit_to_users([user.id], "auth:required", {"reason": "token_version_mismatch"})`（`:160-162`） |
| 2 | 用户自助改密 | `auth/views.py:252-261` | ❌ 不通知；改密响应直接换发新 token（见 §3.3） |
| 3 | 管理员重置他人密码 | `users/views.py:151-166` — **不递增** | ❌ 不通知 |
| 4 | 管理员禁用账号 | `users/views.py:113-125` — **不递增** | ❌ 不通知 |
| 5 | 删除账号 | `users/views.py:128-139` — 只 `user.delete()` | 依赖 `authenticate()` 第 3 步（查不到用户）与 Socket.IO 握手 `_resolve_user` 查不到 → 等效失效 |

> ⚠️ **只有登录与自助改密两条路径会吊销 token**（`users/views.py` 全文 202 行内不出现 `token_version`）。
> 第 3、4 条是**真实缺口**：管理员重置某人密码或禁用账号后，
> 该账号**已在线的会话与已签发的 token 继续有效**，直到自然过期（`JWT_EXPIRES_IN`，默认 24 小时）。
> 见 §11 缺陷 D-01。重写时这两条路径**必须**递增 `token_version`。

递增必须走 `user.save(update_fields=[...])` 并显式带上 `token_version`，否则 `auto_now` 的 `updated_at` 不会刷新
（现系统每一处都把 `"updated_at"` 写进 `update_fields`，见 `auth/views.py:254-261`）。

### 3.3 为什么改密时**后端直接签发新 token 返回**（源码注释抄录）

这是本章最重要的一段"被事故逼出来的设计"。抄录 `apps/auth/views.py:263-267`：

```
        # 直接签发新 token 返回，前端用其续接会话——避免让前端再次 /login 触发的
        # SQLite 写后读竞态（曾复现 200 后 20ms 用新密码重登 401、10ms 即返回
        # 「未跑 bcrypt」的场景，本质是 login 路径上 User 实例偶发读到旧/空
        # password_hash）。改密、吊销旧 token、签发新 token 三步在同一请求同一
        # ORM 实例上原子完成，读时已能见到新 hash。
```

前端对应的实现与理由见 `.baseline-master/frontend/src/stores/auth.ts:64-71`：

```
  /** 自助改密：用于首次登录强制改密流程。
   *  后端改密成功后会递增 token_version，吊销包括当前会话在内的所有旧 token（安全设计）。
   *  改密接口本身在同一请求内基于新 token_version 签发新 token 并随响应一起返回，
   *  前端直接拿这个新 token 替换内存 / localStorage 的旧值，心跳与后续请求立即续接，
   *  彻底规避「改密 200 → 再 login」的 SQLite 写后读竞态（曾复现：login 路径 10ms 即
   *  返回 401「未跑 bcrypt」，本质是同连接上 User 实例偶发读到旧 / 空 password_hash）。
   *  同时在改密→续接窗口期：停掉心跳、屏蔽 401 拦截器的踢出逻辑——
   *  旧会话后台请求（心跳/缓存同步）的迟到 401 不得清掉刚换发的新 token。 */
```

**重写要点**：改密是一个**四合一原子操作**——
`set_password` + `must_change_password=False` + `token_version += 1` + **同响应返回新 token**，
四件事在同一个 ORM 实例、同一个请求里完成（`auth/views.py:250-269`）。响应形状：

```json
{ "code": 0, "message": "成功",
  "data": { "ok": true, "token": "<新 JWT>", "user": { "...serialize_user(user)..." } } }
```

前端在 `stores/auth.ts:77-91` 消费 `res.token`：替换内存 token、`setActiveUser(res.user.id)`、
写回账号命名空间、`startHeartbeat()`。**兼容分支**：若响应没有 `token`（旧后端），
回退到"再 login 一次"路径（`auth.ts:88-91`、`:108-117`）。

## 4. 强制改密门禁（`must_change_password`）

### 4.1 到底哪些接口会被拦住（准确清单）

放行表只有一项（`authentication.py:22-23`）：

```python
# 强制改密放行路径（仅改密接口允许在 must_change_password=true 时通过）
_CHANGE_PASSWORD_PATHS = ("/api/auth/change-password",)
```

匹配方式是 **`request.path.endswith(...)` 尾匹配**（`authentication.py:153-156`，注释说明"兼容 include 前缀"）。

| 接口 | `must_change_password=true` 时 | 依据 |
| --- | --- | --- |
| `POST /api/auth/change-password` | ✅ 放行 | 放行表唯一一项 |
| `POST /api/auth/login` | ✅ 放行（`permission_classes = (AllowAny,)`，`auth/views.py:123`） | 无 token，不走 `JWTAuthentication` 第 5 步 |
| `GET /api/health` | ✅ 放行（`AllowAny`，`auth/views.py:70`） | 同上 |
| `GET /api/version` | ✅ 放行（`AllowAny`，`auth/views.py:86`） | 同上 |
| **`GET /api/auth/me`** | ❌ **401**（`must_change_password`） | **不在放行表内** |
| **其它全部 `/api/*` 业务接口** | ❌ 401 | `authentication.py:116-122` |

> ⚠️ **这是最值得注意的一处设计后果**：`/api/auth/me` **没有**被放行。
> 而前端会话心跳正是周期性打 `/auth/me`（`stores/auth.ts:155,168-180`，固定 20 秒），
> 且**响应拦截器把 401 一律当作"会话过期"处理**
> （`api/request.ts:108-149`：清 token、清缓存、跳 `#/login`、派发 `auth:kicked` → `logout()`）。
> 于是**强改密期间的账号，心跳会把刚建立的登录态清掉**。
>
> 前端在强制改密期间**不启动心跳**来规避（`stores/auth.ts:72-74` 的 `changePassword` 先 `stopHeartbeat()`），
> 但这只在"用户停留在改密弹窗"这一条路径上成立——见 §11 缺陷 D-04，以及 §10 的重写建议。

### 4.2 守卫的第二道实现（`MustChangePasswordPermission`：未列入任何权限链）

| 位置 | 机制 | 状态 |
| --- | --- | --- |
| `JWTAuthentication`（`authentication.py:116-122`） | 认证层直接抛 `AuthenticationFailed` | **实际生效的那一道**（DRF 全局默认认证类，`settings.py:394-396`） |
| `MustChangePasswordPermission`（`guards.py:47-59`） | DRF permission 类，`has_permission` 里 `raise PermissionDenied` | **未列入任何权限链，运行时不会执行**：全仓只有 2 处出现（`guards.py:7` 模块 docstring、`guards.py:47` 类定义），既不在 `DEFAULT_PERMISSION_CLASSES`（`settings.py:397-404` 只列两项）也无任何视图引用 |

验证命令：

```powershell
Get-ChildItem .baseline-master -Recurse -Filter *.py |
  Select-String -Pattern 'MustChangePasswordPermission' |
  ForEach-Object { "$($_.Filename):$($_.LineNumber)" }
# → guards.py:7 / guards.py:47（仅此两处）
```

### 4.3 前端如何响应

| 环节 | 行为 | 代码 |
| --- | --- | --- |
| 登录响应 | `user.mustChangePassword` 为真 → 全局弹「修改初始密码」弹窗 | `auth/views.py:55` 序列化；`auth.ts:62` `needsPasswordChange` |
| 改密前 | `changePassword()` 先 `stopHeartbeat()` + `setSessionRefreshing(true)` | `auth.ts:73-74` |
| 401 抑制 | 会话刷新窗口内（`isSessionRefreshing()`，定义于 `api/request.ts:83`）的 401 **静默丢弃**，不清 token、不跳登录页、不派发 `auth:kicked` | `api/request.ts:109-112` |
| 改密续接 | 用响应里的新 token 替换内存 / localStorage，然后 `startHeartbeat()` | `auth.ts:80-87` |
| 顶号兜底 | 改密请求若 401（会话在弹窗期间被别处登录顶掉），用**用户刚输入的旧密码**静默重登一次再重试改密 | `auth.ts:92-107` |
| 改密后 | `mustChangePassword = false` | `auth.ts:121` |

> 📌 **注意 401 分支无法识别"强改密"**：它**只检查状态码**（`api/request.ts:108`），
> 没有任何 `errorCode`/`code` 判断（因为后端不产出机器码，§2.3）。
> 前端完全依赖"强改密期间不启动心跳 + `setSessionRefreshing` 窗口"这两个**时序前提**来避免误踢。
> 重写时若保留"`/auth/me` 不放行"的设计，必须同时保留这两个前提，否则强改密用户会被自己的心跳踢下线。

### 5.2 动作等级蕴含：**2 套**等级表

`permissions.py:12-26` 定义了两套，域通过 `actionRank` 键覆盖默认值：

| 等级表 | 定义位置 | 内容（动作 → rank） | 蕴含链 | 用它的域 |
| --- | --- | --- | --- | --- |
| `DEFAULT_ACTION_RANKS` | `permissions.py:12-18` | `view 10` / `edit 20` / `manage 30` / `execute 40` / `audit 50` | `view < edit < manage < execute < audit` | 18 个域（除 `contract`） |
| `CONTRACT_ACTION_RANKS` | `permissions.py:21-26` | `view 10` / `audit 20` / `execute 30` / `manage 40` | `view < audit < execute < manage` | 仅 `contract`（`actionRank` 于 `permissions.py:151`） |

**合同域为何反过来**：在合同业务里 `manage`（新建/删除合同）是**最低的管理动作**，
`execute`（比赛级执行，不限公司）比它高，`audit`（审核，仅限范围内公司）语义上更靠近"最终裁决"。
源码里三个动作的 label 把这个层次写明了（`permissions.py:154-156`）：
`contract:audit` = "审核（公司范围，仅限范围内公司合同）"、`contract:execute` = "执行（比赛级，不限公司）"、
`contract:manage` = "管理（新建/删除）"。所以 `contract:manage`(40) 蕴含 `contract:execute`(30)
蕴含 `contract:audit`(20) 蕴含 `contract:view`(10)。

**蕴含的判定算法**（`has_permission`，`permissions.py:253-291`；前端镜像 `catalog.ts:65-86`）：

1. `role == "SUPER_ADMIN"` → **立刻 True**（短路，不看权限数组，`permissions.py:264-265`）；
2. `required` 规整为 list；空列表 → True（`:266-268`）；
3. 对每个 `req_key`：拆出 `domain` 与 `req_action`（`_domain_of`/`_action_of`，`:239-250`）；
4. 取该域的等级表；若 `req_action not in ranks` → **`return False`（fail-closed）**，注释见 `:274-277`——
   "required key 的 action 不在目录等级表内（拼错 key）时直接拒绝，防止被该域任意合法动作满足"；
5. 遍历用户权限：**同域**且 `rank(user_action) >= rank(req_action)` 即满足该项（`:279-288`）；
6. **所有** `req_key` 都满足才返回 True（**AND 语义**）。

> ⚠️ 两个不可退化的实现细节：
> - **同域是硬条件**。持有 `data:part:edit`(20) **不能**满足 `data:material:view`，哪怕等级更高。
> - 等级表的 `get(user_action, 0)` 兜底（`:285`）只影响"用户持有的动作名不在表内"这一侧；
>   要求侧是 fail-closed。例：`contract:edit` 不在 `CONTRACT_ACTION_RANKS` 里，
>   所以 `has_permission(任意角色, 任意权限, "contract:edit")` **恒为 False**。

### 5.5 `permissions = null` 的真实语义（与模型注释矛盾）

| 位置 | 说法 / 行为 |
| --- | --- |
| `users/models.py:47`（字段注释） | "细粒度权限 JSON 数组（**null 表示按 role 继承**）" |
| `users/models.py:101-110`（实现） | `if not self.permissions: return []`（`:104-105`）→ **null 返回空列表** |

**矛盾**：字段注释承诺"null = 按角色继承"，实现却是"null = 零权限"。
且全仓**不存在** `role_default_permissions` 之类的函数——
没有任何代码把 `ROLE_TEMPLATES[*]["defaultPermissions"]` 用于"未显式赋权"的账号。

| 存储值 | `permissions_list` | 实际权限 |
| --- | --- | --- |
| `NULL`（未显式赋权） | `[]` | **零权限**（超管除外；超管在 `has_permission:264` 短路） |
| `"[]"`（显式零权限） | `[]` | 零权限 |
| `'["data:map:view"]'` | 该列表 | 按列表 |

**角色模板的 `defaultPermissions` 在运行时是"文档性"的**：它只出现在 `ROLE_TEMPLATES` 里，
既不参与鉴权，也不参与"按角色继承"。新账号若创建时没显式写 `permissions`，会落到"零权限"。

授予接口的写入规则（`users/views.py:177-181`）：

```python
        permissions = request.data.get("permissions")
        if not isinstance(permissions, list):
            raise BusinessError("permissions 必须是数组", code=400, status_code=400)
        _assert_grant(request, user.role, permissions)
        user.permissions = dump_json_scope(permissions) if permissions else None
```

| 请求值 | 落库 | 读回 |
| --- | --- | --- |
| `["data:map:view"]` | JSON 字符串 | `["data:map:view"]` |
| `[]` | `None`（NULL） | `[]` |
| `null` / 缺字段 | **400**（`isinstance` 检查，`:178-179`） | — |

> ⚠️ **`[]` 与 `null` 都落成 NULL**，因此"显式零权限"和"按角色继承"在存储上不可区分。
> 重写时必须选一种明确语义并写迁移；否则会出现"未显式赋权账号零权限、连基础查看都做不了"的批量故障。

### 5.7 权限判定的**真实链路**（⚠️ 高危认知错误区）

先划清两个**都成立**的事实，避免误读：

| 事实 | 状态 | 证据 |
| --- | --- | --- |
| `CompetitionScopePermission` **被定义** | ✅ 成立 | `guards.py:105-127` |
| 它**被列入** `REST_FRAMEWORK.DEFAULT_PERMISSION_CLASSES`（即"已挂载"） | ✅ 成立 | `settings.py:397-404`，类名在 `:403` |
| 它**在运行时参与权限判定** | ❌ **不成立**（对 `origin/master` 上全部 140 个视图类） | 见 §5.7.1 的逐视图取证 |

**所以准确的表述是：该类"已定义、已挂载于全局默认，但不被任何视图采用、运行时不会执行"**
——不是"配置里没写"，也不是"没人引用所以不存在"。
根本原因是 DRF 的替换语义（下节），而 `origin/master` 上**每个**视图类都在自己的继承链里声明了 `permission_classes`。

#### 5.7.1 DRF 的替换语义（不是合并）

DRF `APIView` 的类属性是 `permission_classes = api_settings.DEFAULT_PERMISSION_CLASSES`。
子类**只要赋值就整体替换**，没有"全局默认 + 子类追加"的合并语义。

`settings.py:397-404` 声明的全局默认是两项：

```python
    "DEFAULT_PERMISSION_CLASSES": (
        "rest_framework.permissions.IsAuthenticated",
        # 比赛域全局兜底：非超管的写操作必须有比赛上下文（body 的 competitionId
        # 或自身归属比赛）。显式设置 permission_classes 的视图不受影响；
        # 粗校验无副作用——各视图的 create_competition_id / apply_competition_scope
        # 仍负责精确的归属强制与 queryset 过滤（见 apps/common/guards.py）。
        "apps.common.guards.CompetitionScopePermission",
    ),
```

注释自己就承认了"**显式设置 `permission_classes` 的视图不受影响**"。而 `origin/master` 的实际情况是"**显式设置的视图 = 全部视图**"：

| 事实 | 证据 |
| --- | --- |
| 通用 CRUD 视图用 `_PERM_CLASSES = (IsAuthenticated, CrudPermission)` | `base_crud.py:46`；`permission_classes = _PERM_CLASSES` 于 `base_crud.py:125,137,153,161,194,203`（`CrudListView` / `CrudCreateView` / `CrudDetailView` / `CrudUpdateView` / `CrudDeleteView` / `CrudImpactView`） |
| 各业务 App 各自定义 `_PERM_CLASSES`（如 `(IsAuthenticated, PermissionsPermission)`） | `users/views.py:25`、`competitions/views.py`、`messages/views.py`、`industry_types/views.py`、`stock/views.py`、`contracts/views.py`、`preparation/views.py:147,160,174,201,231` 等 |
| **140 个视图类全部在自己的继承链里解析到 `permission_classes`，回退到全局默认的 = 0 个** | 下表 AST 取证 |
| **`DEFAULT_PERMISSION_CLASSES` 在全仓只被引用 1 次**（就是它自己的定义处） | 见下方命令 ③ |
| **没有 DRF 函数式视图**（`@api_view` 会回退全局默认，是唯一的旁路） | 见下方命令 ④ |

**逐视图取证（AST 分析，可复现）**——对 `.baseline-master/backend` 全部 **306** 个 `.py` 解析类定义，
按"该类的 `permission_classes` 是否在自身或任一祖先类体内被赋值"求解：

```powershell
# 命令 ①：视图类总数与"回退全局默认"的数量（AST 脚本，纯只读）
#   视图类（含间接继承 DRF/Django 视图）        = 140
#   其中自身直接声明 permission_classes         =  86
#   其中经祖先类声明（54 个，承重祖先见下）      =  54
#   ** 回退到 DEFAULT_PERMISSION_CLASSES        =   0 **
#
# 命令 ②：承重祖先与其覆盖的视图数
#   CrudListView(:124) / CrudCreateView(:136) / CrudDetailView(:152) /
#   CrudUpdateView(:160) / CrudDeleteView(:193) / CrudImpactView(:202)  各覆盖 8 个视图
#   CompetitionListView / CompetitionDetailView / FiscalYearListView /
#   FiscalYearUpdateView / UserListView / UserDetailView                各覆盖 1 个视图
#
# 命令 ③：DEFAULT_PERMISSION_CLASSES 全仓引用次数 → 1（仅 settings.py:397 定义处）
Get-ChildItem .baseline-master/backend -Recurse -Filter *.py |
  Select-String -Pattern 'DEFAULT_PERMISSION_CLASSES' |
  ForEach-Object { "$($_.Filename):$($_.LineNumber)" }
#   → settings.py:397

# 命令 ④：是否存在 @api_view 函数式视图（唯一会回退全局默认的旁路）→ 无
Get-ChildItem .baseline-master/backend -Recurse -Filter *.py | Select-String -Pattern '@api_view'
#   → 无匹配

# 命令 ⑤：视图自行声明的规模 → 99
(Get-ChildItem .baseline-master/backend -Recurse -Filter *.py |
  Where-Object { $_.FullName -notmatch '__pycache__' } |
  Select-String -Pattern '^\s+permission_classes\s*=').Count
```

> 📌 **"承重祖先"这个结构很重要**：54 个视图类**自己不写** `permission_classes`，
> 靠继承 `CrudListView` 等 6 个基类拿到 `_PERM_CLASSES`。
> 因此"改 `base_crud._PERM_CLASSES`"这一处改动会**同时影响 48 个视图类**——
> 这既是 §5.7.5 方案 A 的成本优势，也是单点风险。
>
> 📐 **口径说明**：命令 ① 的 140 是"**含间接继承**的全部视图类"。
> 若换成"仅统计可达自 URLconf 的视图"或"仅统计 `APIView` 直接子类"，数字会不同（88 / 90 / 112 等口径都出现过），
> 但**所有口径的结论一致：回退全局默认的视图数为 0**。

#### 5.7.3 比赛域隔离**实际只有两道**

| # | 防线 | 作用 | 代码 | 覆盖范围 |

#### 5.7.4 权限校验的真实调用链

```
HTTP 请求
  │
  ├─ 中间件链（settings.MIDDLEWARE，14 条；process_request 按列表顺序执行，见 §7）
  │    ├─ SecurityHeadersMiddleware       → 响应阶段写安全头
  │    ├─ OperatorContextMiddleware       → 注入操作员日志上下文（不鉴权）
  │    ├─ LoginRateLimitMiddleware        → 只对 POST /api/auth/login 生效
  │    └─ RateLimitMiddleware             → 按角色限流（⚠️ 见 §8.2 的空转问题）
  │
  ├─ Django URL 解析 → DRF APIView.dispatch()
  │
  ├─ APIView.initial()：
  │    ① perform_authentication()  → request.user（触发 JWTAuthentication.authenticate，§2.3）
  │    ② check_permissions()       → 遍历 self.get_permissions()
  │
  ├─ self.get_permissions() → [p() for p in self.permission_classes]
  │    ★ 视图类若声明了 permission_classes，DEFAULT_PERMISSION_CLASSES 被**完全忽略**
  │
  │    实际存在的两种权限类：
  │    ┌─ CrudPermission（base_crud.py:27-43）
  │    │    GET  → 校验 view.view_permission
  │    │    其它 → 校验 view.edit_permission
  │    │    两者都为空 → 直接放行（:37-38）
  │    │    内部调 has_permission(role, user.permissions_list, required)（:41）
  │    │
  │    └─ PermissionsPermission（guards.py:62-85）
  │         取 view.<method小写> 上的 func._required_permissions（由 @require_permissions 打标）
  │         未标注 → 放行（DEBUG=True 时对写/删方法打 warning，guards.py:88-102）
  │         已标注 → has_permission(role, user.permissions_list, list(required))
  │
  └─ 视图方法体
       ├─ 读：apply_competition_scope(get_queryset(...))      ← 比赛域防线 1
       └─ 写：create_competition_id(request.user, data)      ← 比赛域防线 2
```

**同一路径可以叠加多个权限类**：例如某视图若写
`permission_classes = (IsAuthenticated, CompetitionScopePermission, PermissionsPermission)`，
第二项就会生效。**140 个视图类没有任何一处这样写**——
这就是"该权限类运行时不被采用"的确切含义（它的代码是正确的，只是没有调用方）。

#### 5.7.5 重写时怎么办（两种都行，但必须选一种并留证据）

| 方案 | 做法 | 代价 |
| --- | --- | --- |
| **A. 真正接上** | 把 `CompetitionScopePermission` 加进所有权限链：`base_crud._PERM_CLASSES = (IsAuthenticated, CompetitionScopePermission, CrudPermission)`，各 App 的 `_PERM_CLASSES` 同样补上 | 改一处即覆盖 48 个 CRUD 视图；其余类别需逐个补 |
| **B. 删掉它，把"每视图自行过滤"定为契约** | 删除 `settings.py:403` 的挂载与 `guards.py:75` 的错误注释，改成"比赛域隔离必须由每个视图显式调用 `apply_competition_scope` / `create_competition_id`"，并配 lint/测试强制 | 依赖人工纪律；需要"新增视图必须调用过滤"的自动化检查，否则重演同一个坑 |

> ⚠️ 若选方案 A，**必须先修 `CompetitionScopePermission.has_permission` 的一个隐含假设**：
> `guards.py:124` 是 `cid = request.data.get("competitionId") if request.data else None`。
> `request.data` 是 JSON **数组/字符串**时 `list.get` / `str.get` 会抛 `AttributeError` → **500**。
> 该 bug 现在不可达（类从不执行），一旦接上就立刻可达（恶意 body 即可打 500）。
> 修法：`if isinstance(request.data, dict)` 守卫。

| 环节 | 行为 | 代码 |
| --- | --- | --- |

**响应阶段顺序是反的**（Django 中间件是"洋葱"结构）：#14 最先出、#1 最后出。
所以 `DynamicCorsMiddleware`(#2) 的 `process_response` 在 `SecurityHeadersMiddleware`(#3) **之后**执行——
这正是 `cors.py:5` 那句"本中间件在 SecurityHeaders 之后执行，确保响应头一致"的含义。
重写时若把两者顺序调换，CORS 头会被安全头覆盖（或反之），是**静默的行为变化**。

> 🔎 **#11 → #12 的顺序是本次基准修正后新出现的语义点**：`AuthenticationMiddleware` 只提供
> **Django session 用户**，而全部 `/api/*` 业务请求走的是 **DRF 的 JWT 认证**——DRF 的认证发生在
> **视图派发阶段**（`APIView.initial()`），**晚于所有中间件**。因此 #12 的注释虽然写着"需在认证之后"，
> 但它之后的那个"认证"并不是 API 真正用的那个。详见 §8.2 与 §11 D-03。

## 8. 限流：两套独立实现

系统里有**两套互不相干的限流**，参数、存储、粒度都不同，重写时不要合并理解。

| 维度 | 登录限流 | 按角色限流 |
| --- | --- | --- |
| 实现 | `apps.common.middleware.LoginRateLimitMiddleware` | `apps.common.rate_limit.RateLimitMiddleware` |
| 中间件位置 | #5（`settings.py:278`） | #12（`settings.py:288`） |
| 触发范围 | **仅** `POST` 且 `path == "/api/auth/login"`（精确相等） | 所有 `path.startswith("/api/")` |
| 计数粒度 | `(客户端 IP, 用户名)` | **`user.id`** |
| 参数来源 | 代码常量 | `DEFAULT_RATE_LIMITS` + 可经 API 动态改 |
| 存储 | 进程内存 `dict` | 进程内存 `dict` |
| 超限响应 | `{"code":429,"message":"登录尝试过于频繁，请 15 分钟后再试","data":null}` | `{"code":429,"message":"请求过于频繁，请稍后重试","retryAfter":<int>}` |
| 是否带 `Retry-After` 头 | **否** | **否** |

### 8.1 登录限流（`LoginRateLimitMiddleware`）

| 项 | 值 | 来源 |
| --- | --- | --- |
| 拦截范围 | **仅** `POST` 且 `path == "/api/auth/login"`（**精确相等**，非前缀） | `middleware.py:256` |
| 限流键 | `(ip, username)` | `middleware.py:230`、`:246` |
| 失败窗口 `_FAIL_WINDOW` | `5 * 60` 秒 = 300 s | `middleware.py:206` |
| 失败阈值 `_FAIL_THRESHOLD` | `10` | `middleware.py:207` |
| 锁定时长 `_LOCK_DURATION` | `15 * 60` 秒 = 900 s | `middleware.py:208` |
| 存储 | **进程内存** `defaultdict`（模块级 `_locks`） | `middleware.py:203-205` |
| 清理 | 每 10 分钟一次（`_CLEANUP_INTERVAL`，`_cleanup_locks()` 于 `:213-225`） | `middleware.py:209`、`:217` |
| 容量上限 | **无**（键里含攻击者可控的用户名，可无限增长） | 全文件无 `_MAX_LOCK_ENTRIES` 之类常量 |
| 429 响应 | 见上表 | `middleware.py:269-272` |

**用户名提取（只解析 JSON）**——`middleware.py:258-265`：

```python
            username = ""
            try:
                import json

                body = json.loads(request.body or b"{}")
                username = body.get("username", "")
            except Exception:  # noqa: BLE001
                pass
```

而登录视图用的是 **strip 过**的用户名（`auth/views.py:126`）：

```python
        username = (request.data.get("username") or "").strip()
```

> ⚠️ **两侧口径不一致，限流可被绕过**：
> | 绕过手法 | 机制 |
> | --- | --- |
> | 用户名尾随空格 | 中间件键是原始 `"admin "`；而 `record_login_failure` 由视图调用时传的是 `"admin"` → 查锁定用 `("admin ")`、写失败用 `("admin")`，**不是同一个键**，锁定永远命中不了 |
> | 改 Content-Type 为 `application/x-www-form-urlencoded` | `json.loads(request.body)` 解析失败 → `username = ""` → 所有表单提交共用一个键 `(ip, "")`，与视图记账键不同 → 限流失效 |
> | 非字符串 username（数组 / 数字） | 中间件侧存入非字符串键；视图侧 `.strip()` 抛 `AttributeError` → **500** |
>
> 见 §11 缺陷 D-04 与 D-20。

**失败记账点**（`auth/views.py:137-150`）：仅"用户不存在或密码错误"这一支调 `record_login_failure(ip, username)`。
`record_login_success(ip, username)` 会**删除整个条目**（`middleware.py:241-242`），成功即清零。

> ⚠️ **不计入失败的分支**：账号被禁用（`auth/views.py:153-154` 返回 403）**不调** `record_login_failure`。
> 即"已知用户名 + 已禁用账号"的组合可以无限次尝试、不受登录限流约束。见 §11 缺陷 D-06。

### 8.2 按角色限流（`RateLimitMiddleware` + `/api/system/rate-limit`）

| 项 | 值 | 来源 |
| --- | --- | --- |
| 默认配置 `DEFAULT_RATE_LIMITS` | `SUPER_ADMIN`: `enabled=False`, 1000 req/60 s；`COMPETITION_ADMIN`: `enabled=True`, 300 req/60 s；`PLAYER`: `enabled=True`, 100 req/60 s | `rate_limit.py:22-38` |

| 超限响应 | `{"code":429,"message":"请求过于频繁，请稍后重试","retryAfter":<秒>}`，HTTP 429（**带 `retryAfter` 字段，无 `Retry-After` 头**） | `rate_limit.py:149-156` |

| 存储 | 配置 `_config`（`rate_limit.py:43`）与计数 `_rate_limit_store`（`:42`）**都在进程内存**；模块 docstring 即写"配置存储在内存中（重启丢失）" | `rate_limit.py:1-5, 42-44` |
| 线程安全 | 只有 `_record_request`（`:100-103`）与 `clear_rate_limit_store`（`:76-81`）持 `_lock`；读路径 `_get_request_count`/`_cleanup_old_records`（`:84-97`）**不持锁** | `rate_limit.py:44` |

**⚠️ 但它在本项目里实际不生效**——这是本章最容易误判的一处，逐行举证：

| # | 事实 | 证据 |
| --- | --- | --- |
| 1 | 它在中间件链里位于 **`AuthenticationMiddleware` 之后** | `settings.py:286`（#11）→ `:288`（#12） |
| 2 | 而 `AuthenticationMiddleware` 提供的是 **Django session 用户** | Django 语义；本项目的 API 鉴权走 `Authorization: Bearer` JWT |
| 3 | DRF 的 JWT 认证发生在 **`APIView.initial()`**，即**视图派发阶段**，晚于全部中间件 | `settings.py:394-396` 挂的是 DRF 认证类 |
| 4 | 因此对携带 Bearer token 的 `/api/*` 请求，中间件看到的 `request.user` 是 **`AnonymousUser`** | — |
| 5 | 代码如下，直接 `return None`（跳过限流） | `rate_limit.py:118-120`：<br>`if not hasattr(request, "user") or not request.user.is_authenticated:`<br>`    return None` |

**结论**：`RateLimitMiddleware` 的代码、配置与端点都齐全，但**对 JWT 认证的业务请求一律提前返回**，
所以整套按角色限流在运行时是空转的。→ §11 缺陷 D-03。
`【待确认】`运行时确认方法：在 `rate_limit.py:119` 前后打日志，观察 `/api/*` 请求的 `request.user` 类型；
或在测试中设 `PLAYER` 的 `requests=1` 后连发两次请求，看第二次是否 429。

> ⚠️ 重写时若照抄"在中间件里读 `request.user.role`"的写法，会**复现同一个空转**。
> 正确做法是把限流判定放进**认证之后**的阶段（DRF permission / 视图依赖注入 / ASGI 中间件链中位于认证之后的位置）。

### 8.3 限流的已知弱点（汇总，详见 §11）

| 弱点 | 后果 | 依据 |
| --- | --- | --- |
| 两套限流状态都是**进程内存** | 重启即清；多 worker（如 `deploy/start-daphne-workers.sh` 起 4 个）时每进程一份 → 实际阈值 × N；`/api/system/rate-limit` 的配置在不同进程上不一致 | `middleware.py:203`；`rate_limit.py:42-44` |

| 登录限流**无 `Retry-After` 头** | 客户端只能从文案里猜 15 分钟 | `middleware.py:339-342` 同段 |
| 禁用账号的失败**不计入**登录限流 | 可无限尝试 | `auth/views.py:153-154` |

| 无全局 IP 级限流 | 单一 IP 可对**不同用户名**任意爆破（每用户名独立计数） | `middleware.py:304` 同段键结构 |

## 9. 安全头 / CORS / 客户端 IP / CSRF / Cookie

### 9.1 安全头全集（`SecurityHeadersMiddleware.process_response`，`middleware.py:128-145`）

| 头 | 值 | 例外 |
| --- | --- | --- |
| `Content-Security-Policy` | `default-src 'none'; frame-ancestors 'none'; base-uri 'none'; form-action 'none'` | **`/admin*` 完全不设**（含全部 4 个头） |
| `X-Content-Type-Options` | `nosniff` | 同上 |
| `X-Frame-Options` | `DENY` | 同上 |
| `Referrer-Policy` | `no-referrer` | 同上 |
| `Cross-Origin-Resource-Policy` | `cross-origin`（`path.startswith("/uploads")`）否则 `same-origin` | `/admin*` 不设 |

**没有 HSTS**：`SecurityHeadersMiddleware` 不设它；`SecurityMiddleware`（`settings.py:279`）只在
`SECURE_HSTS_SECONDS > 0` 时才设，而 `settings.py` 全 546 行**没有** `SECURE_HSTS_SECONDS`
（也无 `SECURE_SSL_REDIRECT`）。验证命令：

```powershell

# → 只有 :531 SECURE_PROXY_SSL_HEADER / :539,542,543,545,546 SECURE_COOKIES 相关
#   没有 SECURE_HSTS_SECONDS、没有 SECURE_SSL_REDIRECT
```

`/admin` 豁免的理由（`middleware.py:129-131`）：

```
        # 管理后台（/admin）使用 Django 自带会话鉴权与表单提交，必须放行安全头，
        # 否则 form-action 'none' 会拦截登录与所有表单提交、default-src 'none' 会禁掉后台样式与脚本。
        # 仅对 /admin 放行，/api 等业务接口的安全头保持不变。
```

scheme ∈ {`file`, `app`}；`192.168.x.x` / `10.x.x.x` / `172.16–31.x.x`。

> ⚠️ **`settings.py` 的注释与 `cors.py` 的实现相互矛盾**（同一提交内部）：
> `settings.py:184` 写"未配置时仅本地/私网反射**并带凭据**"、`:189` 写"本地/私网反射并带凭据"，

### 9.3 `client_ip()` 信任链（`helpers.py:110-136`）

```
124: def client_ip(request) -> str:
125:     """取客户端 IP：仅当请求来自可信代理（默认回环，即经 nginx 反代）时才信任
126:     其注入的 X-Real-IP（nginx 取自 $remote_addr，不可伪造）。
127: 
128:     绕过 nginx 直连后端（如 --bind 0.0.0.0 内网联调）时，REMOTE_ADDR 不在
129:     可信集合内，直接回退 REMOTE_ADDR —— 防止伪造 X-Real-IP 使登录限速等
130:     按 IP 的防护失效。始终不信任 X-Forwarded-For 首段（攻击者可伪造）。
131:     """
```

| 输入 | 处理 | 代码 |
| --- | --- | --- |
| `request is None` | `"unknown"` | `:132-133` |
| `REMOTE_ADDR` ∈ `_trusted_proxy_addrs()`（定义于 `:110-121`） | 取 `X-Real-IP`（或 `HTTP_X_REAL_IP`），`.strip().split(",")[0].strip()` | `:135-139` |
| 其它 | 直接返回 `REMOTE_ADDR` | `:140` |
| `X-Forwarded-For` | **永不信任** | `:130` 注释 |

`_trusted_proxy_addrs()` 默认 `{"127.0.0.1", "::1"}`，可用环境变量 `TRUSTED_PROXIES`
（逗号分隔**精确 IP**）追加。

**使用点**：登录限流（`middleware.py:257`）、登录审计（`auth/views.py:131`）、日志过滤器（`middleware.py:177`）。

### 9.4 CSRF 与 Cookie

| 设置 | 值 | 来源 | 影响 |
| --- | --- | --- | --- |
| `ALLOWED_HOSTS` | 默认 `["127.0.0.1", "localhost", "::1"]` + `DJANGO_ALLOWED_HOSTS` 追加 + `LOG_VIEWER_PUBLIC_URL` 主机 | `settings.py:75-106` | 未配置时公网 Host 被拒（400） |
| `DJANGO_ALLOW_ALL_HOSTS` | 若为 `true` → `ALLOWED_HOSTS = ["*"]`（允许任意 Host 头） | `settings.py:89-91` | ⚠️ 打开后 Host 投毒防护失效，见 §11 D-22 |
| `CSRF_TRUSTED_ORIGINS` | 4 个回环 origin + `ALLOWED_HOSTS` 里每个非回环主机的 `http://` 与 `https://` + `DJANGO_CSRF_TRUSTED_ORIGINS` 追加 | `settings.py:122-147` | 带 `Origin` 头的 POST 必须命中，否则 403（Origin checking failed） |
| `SESSION_COOKIE_HTTPONLY` / `CSRF_COOKIE_HTTPONLY` | 均为 `True` | `settings.py:534-535` | — |
| `SECURE_PROXY_SSL_HEADER` | `("HTTP_X_FORWARDED_PROTO", "https")` | `settings.py:523-531` | 经 nginx 反代时让 `request.is_secure()` 正确；注释说明"daphne 仅绑回环地址，公网无法直接投递该头，故信任它是安全的" |
| `SESSION_COOKIE_SECURE` / `CSRF_COOKIE_SECURE` | `= (SECURE_COOKIES == "true")`，**未配置时默认 `false`** | `settings.py:537-546` | ⚠️ HTTPS 部署若忘记设 `SECURE_COOKIES=true`，cookie 不带 `Secure`，见 §11 D-09 |
| `SESSION_COOKIE_SAMESITE` / `CSRF_COOKIE_SAMESITE` | **未设置** → Django 默认 `"Lax"` | 无显式设置 | — |
| `SESSION_COOKIE_NAME` / `CSRF_COOKIE_NAME` | **未设置** → Django 默认 `sessionid` / `csrftoken` | 无显式设置 | 见下"两站点隔离" |
| `SESSION_COOKIE_AGE` | **未设置** → Django 默认 2 周 | 无显式设置 | `/admin` 会话 2 周 |
| `BACKEND_GATE_MAX_AGE` | 环境变量，默认 `120` 秒 | `settings.py:54` | 后台防直连令牌 / 标记 TTL |

**两站点 Cookie 隔离的真相**：主后端（`/admin`）与日志查看器（`backend/logviewer/`，默认 :8120）
**不是靠 path 或端口隔离的**——浏览器 Cookie **不区分端口**，同主机时端口隔离无效。
隔离靠的是**Cookie 名不同**：

| 站点 | session cookie | csrf cookie | 来源 |
| --- | --- | --- | --- |
| 主后端 `/admin` | `sessionid`（Django 默认，未覆盖） | `csrftoken`（Django 默认） | `settings.py`（无 `*_COOKIE_NAME` 设置） |
| 日志查看器 | `lv_sessionid` | `lv_csrftoken` | `backend/logviewer/logviewer/settings.py:243-244` |

> ⚠️ **重写陷阱**：若把主后端的 `SESSION_COOKIE_NAME` 改成与日志查看器相同（或反之），
> 同主机下两个 Django 会互相覆盖对方的 session cookie，表现为"登录 A 站点后 B 站点掉登录"。
> 现系统靠"名字不同"避免。
> `【待确认】`主后端为何未显式设置 `SESSION_COOKIE_SAMESITE`：Django 5 的
> `global_settings.SESSION_COOKIE_SAMESITE` 默认为 `"Lax"`，**推断是依赖默认值**。
> 确认方法：`python -c "from django.conf import global_settings as g; print(g.SESSION_COOKIE_SAMESITE)"`。

### 9.5 后台防直连网关（`BackendGateMiddleware` + 令牌签发）

| 维度 | 值 | 来源 |
| --- | --- | --- |
| 签发端点 | `POST /api/auth/backend-token` | `auth/urls.py:21`；视图 `auth/views.py:194-213` |
| 权限 | `IsAuthenticated`（`:205`）+ **手判 `request.user.role != "SUPER_ADMIN"` → 403**（`:208-209`） | 同上 |
| 签名 | `TimestampSigner(key=LOGVIEWER_SECRET_KEY, salt="backend-gate")`，内容 `f"bk:{user.id}"` | `auth/views.py:211-212` |
| 校验 | `apps.common.backend_gate.BackendGateMiddleware`（仅 `/admin/`） | `backend_gate.py:88-127` |
| 有效期 | `settings.BACKEND_GATE_MAX_AGE`（默认 120 s） | `backend_gate.py:61`、`:70` |
| 失败行为 | 302 重定向回前端 SPA | `backend_gate.py:126-127` |

`BackendGateMiddleware.process_request` 的判定顺序（`backend_gate.py:91-127`）：

1. 路径不以 `/admin/` 开头 → 放行（`/api`、`/socket.io`、`/static`、`/uploads` 全部不受影响，`:93-94`）；
2. `path == "/admin/logout/"` → **清除**网关标记，放行（使随后直连必须重新经令牌，`:98-102`）；
3. `request.session.get("_auth_user_id")` 存在（已登录 Django 后台） → 放行，**不受标记 TTL 影响**（`:104-108`）；
4. `?token=` 校验通过 → 写入 `session["bk_gate"] = {"ts": time.time()}` 并 **302 到不带 query 的 `request.path`**（去 token 防泄漏，`:110-115`）；
5. 标记存在且未过期 → 只允许 `/admin/` 与 `/admin/login/`，深层路径则清标记并重定向回前端（`:117-124`）；
6. 其它 → 重定向回前端 SPA（`:126-127`）。

`_gate_set()`（`:76-85`）对标记做 **TTL 校验**（`BACKEND_GATE_TTL`，`:61`），注释理由（`:59-60`）：

```
# 网关标记有效期（秒）：与令牌有效期一致。过期后直连 /admin/ 必须重新经令牌网关，
# 避免「点过一次按钮后会话 cookie 永久有效、随后直连总能进」的绕过（思路一）。
```

日志查看器令牌同构但盐不同：`POST /api/auth/logviewer-token`（`auth/views.py:171-190`），
`salt="logviewer-gate"`，内容 `f"lv:{user.id}"`。

> 📌 这两道网关**不是认证**——它们只是"来源合法性"网关。真正的认证仍是 Django 后台自身的登录表单 /
> 日志查看器自身的登录。源码注释把这点写明（`auth/views.py:178-179, 201-202`）。

## 10. 重构关注点

### ✅ 必须保持的契约（外部可观测）

| # | 契约 | 为什么不能动 |
| --- | --- | --- |
| C-1 | `Authorization: Bearer <JWT>`，HS256，`iss`/`aud` 校验 | 前端 `api/request.ts` 与 `realtime/socket.ts:45` 都按此传 |
| C-2 | claims 名与语义：`sub`(字符串) / `username` / `role` / `tv` / `cid` / `iss` / `aud` / `iat` / `exp` | `tv` 是顶号判定依据；Socket.IO 握手复用同一 `decode_jwt_payload` |
| C-3 | **每一次成功登录都递增 `token_version`**（单设备语义） | 改掉会让"顶号"消失；前端 20 s 心跳（`auth.ts:150-181`）靠它感知被顶 |
| C-4 | **改密响应必须直接带新 `token` + `user`**（不得要求前端二次 `/login`） | 规避 SQLite 写后读竞态；前端已按此实现（`auth.ts:80-87`） |
| C-5 | 强改密放行表当前**只含** `/api/auth/change-password`（尾匹配） | 若重写后要放行 `/auth/me`，必须同步评估 §4.1 的心跳连锁 |
| C-6 | 39 个权限键的**键名逐字**、19 个域的划分、2 套等级表的具体数字 | 键名是持久化数据（`users.permissions` JSON 列）；等级数字变了判定就变 |
| C-7 | `has_permission` 的语义：超管短路 / 同域蕴含 / AND / 拼错动作 fail-closed | 两侧必须逐位一致 |
| C-8 | `is_valid_permissions` 接受 3 个废止键 | 存量数据兼容 |
| C-9 | 授予上限 + 超管专属 3 键不可授予 | 越权防线 |
| C-10 | 安全头四个具体值（CSP 字符串逐字、XFO DENY、XCTO nosniff、Referrer-Policy no-referrer） | 外部扫描器 / 合规基线 |
| C-11 | `/admin*` 前缀**完全不设**安全头 | 否则后台表单提交与样式被拦 |
| C-12 | CORS：回显 origin（不用 `*`）；白名单带凭据、私网反射**不带**凭据 | 见 §9.2 |
| C-13 | `client_ip()`：只信 `X-Real-IP` 且仅当 `REMOTE_ADDR` 可信；**永不**信 `X-Forwarded-For` | 否则登录限流可按 IP 绕过 |
| C-14 | 登录限流参数：5 分钟窗口 / 10 次 / 锁 15 分钟 / 键 = (IP, 用户名) | 与运维预期一致 |
| C-15 | 按角色限流的**配置形状**：`{role: {enabled, requests, window}}` + 429 体带 `retryAfter` | `/api/system/rate-limit` 的对外契约（前端设置页消费） |
| C-16 | `permission_version` 递增 → `permissions:changed` → 前端重拉 `/auth/me` | 赋权即时生效，无需重新登录 |
| C-17 | 两套账号体系隔离 + `PASSWORD_HASHERS` 同时含 bcrypt 与 Django 默认算法 | 见 ⚠️ T-2 |
| C-18 | **比赛域隔离的两道防线必须都在**：读 `apply_competition_scope` + 写 `create_competition_id` | 全局默认里的 `CompetitionScopePermission` 对 0 个视图生效（§5.7） |
| C-19 | 后台防直连：令牌签名盐 `backend-gate`、内容格式 `bk:{id}`、TTL 语义、302 去 token | 与日志查看器共用密钥，改了要双端同改 |
