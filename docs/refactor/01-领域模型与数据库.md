### 1.1 「42 vs 41」——一个会让重写者去找不存在表的陷阱


该正则**不区分 model 与普通类**。逐条列出 42 条匹配后，唯一不是 model 的是：

### 1.4 🚨 归属链：`company_fields` app 没有模型，它的数据在哪两张表上

这是重写时**最容易找错表**的点：

```
backend/apps/company_fields/          ← 有 views/serializers/calc/timer，但 models.py 只有注释
    ├── 字段「定义」→ backend/apps/industry_types/models.py :: IndustryField    → 表 industry_fields
    └── 字段「取值」→ backend/apps/companies/models.py     :: CompanyFieldValue → 表 company_field_values
```

证据：

- `backend/apps/company_fields/models.py`（全文，原始 5 行）：
  > 「公司产业字段值模型定义在 apps.companies（CompanyFieldValue）。本应用 company_fields 复用该模型，无独立模型；读写由 apps.company_fields.views 直接操作 apps.companies.models.CompanyFieldValue。」
- `backend/apps/company_fields/views.py:20` 直接 `from apps.companies.models import Company, CompanyFieldValue`；`:80-88`、`:92-97` 直接读写该模型；`:123-125` 从 `apps.industry_types.models` 取 `IndustryField`。
- `backend/apps/company_fields/timer.py:25-26` 同样直接导入两边的模型。

> **重写建议**：合并为「字段定义表 + 字段值表」两张即可，不必复刻「app 名 ≠ 表所属 app」的历史结构；但**外键指向关系必须保持**（值表按 `(company_id, field_id)` 唯一）。

### 2.3 软删除：**不存在**

全仓库 `apps/` 下 grep `is_deleted` / `deleted_at` / `soft_delete` / `SoftDelete` / `isDeleted` / `deletedAt` —— **0 命中**。

| --- | --- | --- | --- | --- |

| `part_tech_requirements` | `Part` ↔ `TechNode` | `(part, tech_node)` | — | 无 |
| `product_parts` | `Product` ↔ `Part` | `(product, part)` | `ratio` Float | 无 |
| `product_tech_requirements` | `Product` ↔ `TechNode` | `(product, tech_node)` | — | 无 |

### 4.4 级联删除树（以删除 `Competition` 为根）

```
DELETE competitions WHERE id = ?
├── fiscal_years              (CASCADE)
├── users                     (CASCADE)  ← ⚠️ 删比赛会删掉该比赛的全部账号
├── companies                 (CASCADE)
│   ├── company_field_values  (CASCADE)
│   └── stocks.company        (SET_NULL) ← 不删，只置空
├── materials                 (CASCADE) ── part_materials (CASCADE)
├── parts                     (CASCADE) ── part_materials / part_tech_requirements / product_parts (CASCADE)
├── products                  (CASCADE) ── product_parts / product_tech_requirements (CASCADE)
│                                          / consumer_demands.product (SET_NULL)
├── tech_nodes                (CASCADE) ── part_tech_requirements / product_tech_requirements
│                                          / tech_prerequisites (CASCADE)
├── map_node_types            (CASCADE) ── map_nodes (CASCADE) ── map_edges (CASCADE)
├── path_types                (CASCADE) ── map_edges / vehicle_path_types (CASCADE)
├── infrastructures           (CASCADE)
├── fuels                     (CASCADE) ← ⚠️ 但 vehicles.fuel 是 PROTECT：
│                                          若存在引用该燃料的载具，删除会被数据库拒绝
├── vehicles                  (CASCADE) ── vehicle_path_types (CASCADE)
├── warehouses                (CASCADE)
├── production_lines          (CASCADE)
├── contracts                 (CASCADE) ── contract_field_effects (CASCADE)
├── regions                   (CASCADE) ── companies.region (SET_NULL)
├── consumer_demands          (CASCADE)
├── messages                  (CASCADE) ── message_recipients (CASCADE)
├── stocks                    (CASCADE) ── stock_holdings / stock_orders / stock_candles (CASCADE)
├── stock_funds_accounts      (CASCADE) ── stock_holdings / stock_orders (CASCADE)
└── (不删) ContractType / IndustryType / IndustryField / Announcement / WidgetPackage / AuditLog
```

**⚠️ 两个级联陷阱**：

1. `fuels` 与 `vehicles` 都是 `competition` 的 CASCADE 子表，而 `vehicles.fuel` 是 `PROTECT`。正常情况下 Django 的删除收集器会算好顺序；但**如果某个载具的 `fuel` 指向了另一场比赛的燃料**（数据库层完全允许，因为 `vehicles.fuel` 与 `vehicles.competition` 之间没有一致性约束），删比赛 A 会被 `PROTECT` 挡住并抛 `ProtectedError`。这是**跨比赛数据不一致**会暴露成删除失败的真实路径。
2. `messages.competition` 可空 ⇒ **超管跨比赛发布的消息（`competition_id IS NULL`）不会被任何比赛删除带走**；而它的 `sender` 是 CASCADE ⇒ 删一个超管账号会连带删掉他发过的**所有比赛**的消息。

### 8.2 🚨🚨 头号风险：`DecimalField(60,4)` 在 SQLite 上**无法精确保存 >15 位有效数字**

**master 上没有 `ExactDecimalField`，也没有任何写入侧精度守卫** —— 因此**精度损失是静默的**。

#### 事实链（每一环都可复现）

1. **列型声明**：Django 5.0.14 在 SQLite 后端把 `DecimalField` 映射为列类型 `decimal`（`django/db/backends/sqlite3/base.py:68`）。
   实测 `DecimalField(max_digits=60, decimal_places=4).db_type(connection)` → `"decimal"`（§9.4.2 表）。
2. **SQLite 亲和性**：`decimal` 含 `DEC` 子串 ⇒ **NUMERIC 亲和性** ⇒ 超出 15 位有效数字的十进制值被强制转成 **REAL（IEEE double）**存储。
3. **读回二次损失**：Django 的 SQLite 转换器用 `decimal.Context(prec=15).create_decimal_from_float` 还原。源码注释原文（`django/db/backends/sqlite3/operations.py:331-334`）：

   ```
   def get_decimalfield_converter(self, expression):
       # SQLite stores only 15 significant digits. Digits coming from
       # float inaccuracy must be removed.
       create_decimal = decimal.Context(prec=15).create_decimal_from_float
   ```

4. **master 自带验证脚本**：`tests/sqlite_decimal_roundtrip.py` —— 写入 `Decimal("12345678901234567890123.4567")`（28 位有效数字）到 `Fuel.price_per_liter`，`refresh_from_db()` 后比对，**不相等则退出码 2**。该脚本用 `transaction.atomic()` + `SystemExit` 触发回滚，不残留数据。

⇒ **结论**：`max_digits=60` 的高精度**只在非 SQLite 后端成立**。而 master 的 `DATABASES` **是双分支的**（`backend/backend/settings.py:315-371`）：设了 `DB_ENGINE` 走 PostgreSQL 分支（`:342-359`），否则回退 SQLite（`:362-371`，`OPTIONS.timeout = 60`）。

因此这条精度上限**是否在现网成立，取决于部署时有没有设 `DB_ENGINE`**：

| 部署形态 | 判定依据 | 精度后果 |
| --- | --- | --- |
| 未设 `DB_ENGINE` ⇒ SQLite | `settings.py:360-371` | 🔴 **静默丢精度**（10^13 级起出现分位误差，10^23 级不可用） |
| 设了 `DB_ENGINE` ⇒ PostgreSQL | `settings.py:319-359` | ✅ 声明精度成立（`NUMERIC(60,4)` 精确） |

> ⚠️ 但 `requirements.txt` 里**没有 `psycopg2`**（只有 Django/DRF/simplejwt/cors-headers/python-socketio/daphne/bcrypt/python-dotenv/Pillow 共 9 行）—— 即 PG 分支**在依赖层面缺驱动**。这是 [07-部署运维与环境变量.md](07-部署运维与环境变量.md) 的话题，本章只记录它对精度结论的影响：**「现在跑的是哪个库」必须实测 `.env` 的 `DB_ENGINE`**（§11 Q-12）。

#### 重写决策矩阵

| 目标库类型 | Decimal 精度 | 需要做什么 |
| --- | --- | --- |
| **SQLite**（未设 `DB_ENGINE` 时的回退分支） | ❌ NUMERIC 亲和性 → REAL，>15 位有效数字静默丢 | 二选一：<br>(a) 列型改 **TEXT 亲和性**（存十进制文本），应用层自行精确往返；<br>(b) 保留 NUMERIC 但**加写入侧位数校验**，把静默丢值变成明确报错 |
| **带精确 `NUMERIC`/`DECIMAL` 类型的关系库**（master 已有 PostgreSQL 分支） | ✅ 精确到声明精度 | 声明 `NUMERIC(60,4)` 即可，不需要 15 位守卫 |
| **应用层精确十进制类型**（如 Java `BigDecimal` / C++ 定点） | ✅ 精确 | 注意 `decimal_places=4`：**价格场景实际只用 2 位**，4 位是给撮合误差留的余量（`stock/models.py:15-17` 注释） |

> ⚠️ **千万不要**因为「Django 声明了 `max_digits=60`」就以为 SQLite 能存 60 位。这是本章最重要的一句话。

### 8.5 出站口径（重写时必须复刻的 HTTP 契约）

`backend/apps/common/renderers.py:21-40` 的 `_convert_big_numbers()` 在 `backend/apps/common/response.py` 的统一 `JSONRenderer` 渲染前递归扫描：

| 输入 | 输出 | 理由 |
| --- | --- | --- |
| `int`，`abs > 2^53` | **字符串** | JS `Number` 是 IEEE double，精确整数上限 2^53 ≈ 9.007×10^15；10^23 量级 ULP≈10^7（`renderers.py:1-9` docstring） |
| `int`，`abs <= 2^53` | JSON number | id、version 不受影响 |
| `Decimal`，整数值 | 先转 `int`，再按上一条判断 → **可能是 number 或 string** | |
| `Decimal`，非整数值 | **字符串**（`format(obj, "f")`） | 如 `Decimal("12.3450")` → `"12.3450"` |
| `Decimal`，非有限（inf/nan） | `None` | |
| `float` | **原样返回**（`:34-35`） | ⚠️ master **没有** inf/nan 兜底；若 `FloatField` 里存在 `inf`/`nan`，DRF 的 `JSONRenderer`（`allow_nan=False`）会抛 `ValueError`，**一行脏数据即可让该模块所有读接口 500**。重写时应补写入侧与出站侧双向拦截 |

> 🚨 **契约警告**：**小数金额出站是字符串，不是 number**。前端契约是 «string | number» 混合。历史调用方按 number 处理会崩。重写时必须保持这一出站口径，否则前端金额格式化全线失效。
> 同一口径也被 `backend/apps/common/json_util.py:36-46` 的 `dumps_json_safe` 复用（把含 `Decimal` 的引擎产物落库为 JSON 字符串）。

### 9.3 `select_for_update` 在 SQLite 上**是否真的加锁** —— 已查证

**结论：SQLite 上 `select_for_update` 是彻底的空操作（no-op），不加任何行锁。**

#### 证据 1：源码自己承认（`backend/apps/stock/engine.py:1921-1929`）

```python
# 并发推进（#16）：在事务内对目标 Stock 行加行级锁（select_for_update），
# 与进程内 threading.Lock 形成「进程内 + DB」双重防护，避免多 worker 部署下双推进。
# SQLite 不支持行锁（select_for_update 为 no-op），此时仅依赖进程内锁。
with transaction.atomic():
    qs = Stock.objects.filter(competition_id=competition_id)
    if stock_ids:
        qs = qs.filter(pk__in=stock_ids)
    if connection.vendor != "sqlite":        # ← 显式判断，SQLite 上连 SQL 都不生成
        qs = qs.select_for_update()
    stocks = list(qs.order_by("code"))
```

#### 证据 2：另外两处**没有**做 vendor 判断（重写时的真陷阱）

| 位置 | 代码 | SQLite 上的行为 |
| --- | --- | --- |
| `backend/apps/stock/views.py:907-908` | `locked_account = StockFundsAccount.objects.select_for_update().get(pk=account.id)` | `FOR UPDATE` 被 Django 的 SQLite 后端**静默丢弃**，**实际没有加锁** |
| `backend/apps/stock/views.py:983-985` | `order = StockOrder.objects.select_for_update().get(pk=pk)` | 同上 |

⇒ **下单接口的注释写着「防止并发下单导致超买超卖」（`:907`）、撤单接口写着「防止撤单与撮合引擎并发竞态」（`:983`），但在 SQLite 上这层防护不存在。** 只有 `stock/engine.py:1929` 的推进轮次做了 vendor 判断并退回进程内 `threading.Lock`。

| 部署 | `select_for_update` | 重写建议 |
| --- | --- | --- |
| SQLite（未设 `DB_ENGINE` 时的回退分支） | **no-op**。并发安全完全依赖 SQLite 的**库级写锁**（同一时刻只有一个写事务）+ 进程内锁 | 把并发防护做成**应用层锁 + 事务内重新计数校验**，或改 `BEGIN IMMEDIATE` 乐观重试 |
| PostgreSQL（设了 `DB_ENGINE` 时；master 已有该分支 `settings.py:319-359`） | ✅ 真加行锁（`FOR UPDATE`，需在事务内，且长事务会阻塞） | 两处调用点无需改代码即可生效；但要避免长事务 |

> ⚠️ **这条风险与 §8.2 一样取决于 `DB_ENGINE`**：SQLite 部署下下单/撤单的并发防护**完全不存在**；PG 部署下同一份代码才真的加锁。`【待确认】` 生产实际用的是哪个（§11 Q-12）。
