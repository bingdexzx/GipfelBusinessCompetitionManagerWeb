### 1.2 开发态：`scripts/dev.py` 监管进程

| 事实 | 证据 |
| --- | --- |
| `start-dev.bat` **只做前置检查**，然后把控制权交给 `dev.py`（在独立窗口 "Gipfel Dev" 里跑） | `scripts/start-dev.bat:42-44` |
| 它解释了为什么不用 `start /B`：`start` 把子进程放进新进程组，控制台 `CTRL+C` **不投递**给它们 → 服务继续跑、端口继续占，cmd 停在「Terminate batch job (Y/N)?」 | `scripts/start-dev.bat:9-16` |
| `dev.py` 自己当监管者：子进程以 `CREATE_NEW_PROCESS_GROUP` 启动，退出时**定向**向每个进程组发 `CTRL_BREAK_EVENT`，超时再用 `taskkill /T /F` 兜底 | `scripts/dev.py:3-9`、`:40-41`、`:57` |
| 端口约定：Django **写死** `127.0.0.1:8000`（不读 `.env` 的 `PORT`）、Vite `127.0.0.1:5173`、日志查看器读 `backend/.env` 的 `LOG_VIEWER_PORT`（默认 8120） | `scripts/dev.py:14-17`、`:51-54` |
| 子进程工作目录分别是 `backend` / `frontend` / `backend/logviewer`，保证 `LOG_DIR="./logs"` 落在 `backend/logs` | `scripts/dev.py:19-20` |
| 进程号写入 `%TEMP%\gipfel-dev.pids` | `scripts/dev.py:21`、`:56` |
| `stop-dev.bat` 有**两条**停止路径：① 按 PID 文件逐个 `taskkill /PID /T /F`；② 兜底——按端口 `8000/5173/8120` 用 `netstat` 找监听者并 `taskkill` | `scripts/stop-dev.bat:16-29` |
| 首次初始化由 `bootstrap-dev.bat` 负责（venv + pip + npm + migrate + 建默认超管） | `scripts/bootstrap-dev.bat:1-30` |

> ⚠️ `stop-dev.bat` 的第 ② 条路径是**无差别强杀**：任何占用 8000/5173/8120 的进程（可能是 Docker、另一个 Vite、用户自己的服务）都会被 `taskkill /T /F`。而 PID 文件路径**没有身份校验**（PID 被系统回收后会误杀无关进程）。见 §11 DEF-07-06 与 [08-技术债与风险.md](08-技术债与风险.md)。

- 「全集」= **代码中真正读取的键**：`settings.py`(29) ∪ `logviewer/settings.py`(19) ∪ `apps/**`(3) = **36 个唯一键名**。

### 3.3 `CONN_MAX_AGE` 的真实语义（源码里唯一的「血泪注释」）

`settings.py:320-336` 与 `.env.example:99-113` 用几乎相同的文字写清了同一件事：

> 它**不是定时器**。Django 只在「请求开始 / 请求结束」这两个时刻，检查**当前线程自己那条**连接是否超龄（`close_at = 建连时刻 + CONN_MAX_AGE`）：
> - `0` → 请求结束即关闭，连接数 ≈ 同时在处理的请求数；
> - `N>0` → 只有该线程**下次再接到请求**时才会关闭重建；线程若不再被使用，那条连接会一直挂着（**实测出现过 51 条 idle、最长闲置 73 秒仍未释放**）；
> - `None` → 永不自动关闭。
>
> PostgreSQL 默认 `max_connections=100`，其中 `superuser_reserved_connections=3` 只留给超级用户，**应用实际只能用 97 条**。打满后报：
> `FATAL: remaining connection slots are reserved for non-replication superuser connections`
> 需要用持久连接省下建连开销时，**正确做法是上 PgBouncer（transaction 模式）**，而不是把这里调大 —— 调大只是把「连接打满」推迟到更高的并发。

配套的 `CONN_HEALTH_CHECKS: True`（`settings.py:351-354`）解决另一半问题：数据库重启或连接被 `pg_terminate_backend` 清理后，复用死连接会抛 `server closed the connection unexpectedly` 而不是安静重连。

### 5.3 ⚠️⚠️ 重点：4-worker 模式与 master 的「单进程内存态」直接冲突

`deploy/start-daphne-workers.sh`（89 行）用 `WORKERS=4` / `BASE_PORT=8000` 在 **8000–8003** 各起一个 `daphne … backend.asgi:application`（`:18-19`、`:60-75`），启动前先 `pkill -f "daphne.*backend.asgi"`（`:46`）。

而 master 的以下状态**全部是进程内内存**，没有任何跨进程共享：

| 状态 | 位置 | 4 个 worker 下的后果 |
| --- | --- | --- |
| **事件序号 `seq` + 环形缓冲** | `apps/realtime/emit.py`：`_seq_value`、`_event_ring: deque`、`_ring_seqs: deque`（配 `_seq_lock` / `_ring_lock`） | 每个 worker 有**独立的 seq 与独立的环**；`replay_since()` 只能补发**本进程**产生的事件 → **重连补发漏事件** |
| **广播投递用的 event loop 引用** | `apps/realtime/emit.py`：`_loop` + `register_loop()`（首个 socket 连接时注册） | 只有持有 socket 的进程注册过 loop；REST 请求若落在别的 worker 上 → 广播**静默丢弃**（源码注释点名了历史缺陷 `#P3`） |
| **Socket.IO 房间** | `apps/realtime/gateway.py`：`sio.enter_room(sid, f"user-{id}")` / `f"comp-{cid}"` | 房间是**每进程一张表**：同一比赛的用户分散在 4 个 worker 上，广播只能覆盖其中一部分 → **部分客户端不刷新** |
| **登录失败限流计数** | `apps/common/middleware.py`：`_locks: dict[(ip, username) → {fails, first_at, locked_until}]` | 有效阈值被放大到「worker 数 × 阈值」；锁定状态不共享 → **爆破防护被稀释** |
| **按角色限流计数** | `apps/common/rate_limit.py`：`_rate_limit_store: dict[user_id, list[(ts, count)]]` + `_lock` | 同上：`PLAYER` 的 100 次/60 秒变成实际 400 次/60 秒 |
| **并发互斥锁** | `apps/stock/engine.py`（`_advance_locks`）、`apps/company_fields/timer.py`（`_fiscal_locks`） | 互斥**完全失效** → 可能双推进 |

**再叠加一个不对称**：nginx 的 `upstream gipfel_django` **只指向 `127.0.0.1:8000`**（`deploy/nginx-gipfel.conf:11`），即只有 worker 1 会被 nginx 使用；worker 2–4 虽然绑了 127.0.0.1:8001–8003，**既不被 nginx 覆盖、也不被任何负载均衡覆盖**，但如果有人（或旧脚本）直连它们，就会落进「另一个事件环」。

> **结论**：`origin/master` 在设计上是一个**单进程应用**。`start-daphne-workers.sh` 这条路径不是「扩容」，而是**同时打破六件事**。若新系统要多进程，这六类状态必须逐一外置（DB / Redis / 队列），或者把「单进程」写成部署期的强制前置条件。**这条是 08 章的架构级重点，也是 09 章进程模型的输入。**

### 7.4 cookie 隔离（两个站点同在 `localhost`）

| 站点 | CSRF cookie | Session cookie | HttpOnly | SameSite | 证据 |
| --- | --- | --- | --- | --- | --- |
| 主后端 | `csrftoken`（默认名） | `sessionid`（默认名） | 两者都 **True** | 默认 | `settings.py:534-535` |

## 8. 限流与可观测性

### 8.1 master 的限流机制（14 条中间件里的第 3 与第 12 条）

| 层 | 实现 | 关键参数 | 证据 |
| --- | --- | --- | --- |
| **登录失败锁** | `apps/common/middleware.py` 的 `LoginRateLimitMiddleware`：仅拦 `POST /api/auth/login`，超限返回 429 | `_locks: dict[(ip, username)]`；`_FAIL_WINDOW = 5*60`、`_LOCK_DURATION = 15*60`；失败 10 次锁 15 分钟 | `middleware.py` |
| **按角色限流** | `apps/common/rate_limit.py` 的 `RateLimitMiddleware`：仅 `/api/`、已认证、且该角色 `enabled` 时生效；超限返回 `{"code":429,"message":"请求过于频繁，请稍后重试","retryAfter":N}` | `DEFAULT_RATE_LIMITS`：`SUPER_ADMIN` disabled / 1000 次每 60s；`COMPETITION_ADMIN` enabled / **300 次每 60s**；`PLAYER` enabled / **100 次每 60s**；`_EXEMPT_PATHS = {"/api/auth/login","/api/auth/refresh","/health","/healthz"}` | `rate_limit.py:22-52`、`:110-161` |
| 配置端点（仅超管） | `GET`/`PUT` `/api/system/rate-limit`、`POST` `/api/system/rate-limit/reset` | `RateLimitConfigView` / `RateLimitResetView`：`permission_classes = (IsAuthenticated,)` + 函数内再校验 `role == "SUPER_ADMIN"`；PUT 的 `role` 只接受 `SUPER_ADMIN`/`COMPETITION_ADMIN`/`PLAYER` | `backend/urls.py:25-26`；`rate_limit_views.py:20-95` |
| nginx 层 | **无** | — | §6.5 N1 |

⚠️ **两个限流表都在进程内存里**（`_locks`、`_rate_limit_store` + `_lock`），因此**与 §5.3 的多 worker 问题同源**：多 worker 下有效阈值被放大到「worker 数 × 阈值」，且「重置」只清当前进程的记录。

### 9.2 升级时的注意点

| 注意点 | 原因 | 证据 |
| --- | --- | --- |
| **`systemctl enable --now` 不会重启已在运行的 unit** | `enable --now` 对 active 的 unit 是空操作 → 新代码落盘但进程仍是旧代码 | `scripts/deploy-linux.sh:583,594` |
| **`git pull` 失败会降级继续** | 只打 `warn`，随后照样 migrate + 构建 + 重启 → 可能「新库结构 + 旧代码」 | `scripts/update-from-github.sh:199-202` |
| **升级脚本会自动切 PG** | 检测到 SQLite 就 `dumpdata`→`loaddata`；凭据校验失败还会**自动轮换密码并写回 `.env`** | `scripts/update-from-github.sh:322-412` |
| **升级会从各 unit 的 `ReadWritePaths` 移除 `db.sqlite3`** | 迁 PG 后该文件不存在 → 否则 `status=226/NAMESPACE` 无限重启（**真实事故：重启计数 229**） | `scripts/update-from-github.sh:458-464`；`deploy/logviewer.service:53-55` |
| **两个正式 unit 共用 `RuntimeDirectory` / `LogsDirectory`** | `systemctl restart gipfel` 会连带清理/重建 `/run/gipfel` 与 `/var/log/gipfel`，影响另一个服务 | `deploy/gipfel.service:27-30`；`deploy/logviewer.service:29-32` |
| **`deploy-linux.sh` 只有 `ERR` trap，没有 `EXIT` trap** | 失败时能定位行，但不会自动把服务拉回运行态，也不打印回滚指引 | `scripts/deploy-linux.sh:28-42`（仅 `trap … ERR`） |
| **备份无保留策略** | 每次部署/升级新建一份备份目录，脚本内无清理逻辑 | 备份段；§11 DEF-07-04 |

### 9.3 回滚

`origin/master` **没有脚本级回滚**。可用路径：

1. 备份目录里的库 / `uploads` / `.env` 副本 —— 手工恢复（**注意**：备份是文件级拷贝，恢复前必须先停两个服务，并处理可能的 `-wal`/`-shm`）；
2. `git` 回退 + 重跑 `update-from-github.sh`（若部署目录是 git 仓库）；
3. PostgreSQL 场景：`migrate_to_postgresql.sh` 在迁移前会 `dumpdata` 到 `BACKUP_DIR`（`migrate_to_postgresql.sh:69`），并带逐 app 回退逻辑（`:392-401`）。

⚠️ 脚本不会替运维执行「停服 → 覆盖 → chown → 起服」这套顺序（§11 DEF-07-03）。

## 10. 重构关注点

### ✅ 必须保持的契约

| # | 契约 | 为什么不能动 | 证据 |
| --- | --- | --- | --- |
| C1 | **`JWT_SECRET` 缺失或命中弱密钥黑名单时拒绝启动** | 「配置错就上不了线」的安全底线；降级为「用默认值悄悄启动」等于把默认密钥送上生产 | `settings.py:26-46` |
| C2 | **`.env`（`EnvironmentFile`）优先级高于 unit 的 `Environment=`** | 这是运维唯一「升级不会覆盖」的覆盖入口；顺序反过来会导致「改了 `.env` 不生效」 | `deploy/gipfel.service:14-15` |

| T4 | **`--delete` + 未锚定的排除模式** | rsync 段的 `--exclude db.sqlite3` 等裸名模式 | 排除模式要**锚定**（前导 `/`）；带边车文件的用通配符 |
| T5 | **`systemctl enable --now` 当「重启」用** | `scripts/deploy-linux.sh:583,594` | 「部署生效」必须有断言（版本号/行为探针），不能只看 `is-active` |
| T6 | **`\|\| true` 吞掉关键失败** | `scripts/migrate-server.sh:239-241,250`（chown 早于 useradd 且都被吞） | 关键步骤不许 `\|\| true`；PATH 不要假设完整（`/usr/sbin` 常缺） |
| T7 | **`ReadWritePaths` 指向可能不存在的路径** | 两个正式 unit 已修好并带警告，但**迁移脚本必须在每次升级时同步清理** | 白名单只列保证存在的路径；把「同步清理」写进部署工具，而不是指望人记得 |
| T8 | **`Restart=always` + 配置错误 = 无限重启且不报警** | `gipfel.service:32-33`；**真实事故：日志查看器重启计数 229** | 补 `StartLimitBurst` + `OnFailure=` 告警单元 |
| T9 | **两个服务共用 `RuntimeDirectory`** | `gipfel.service:27` 与 `logviewer.service:29` 都是 `gipfel` | 每服务独立目录 |
| T10 | **把「进程内锁」当并发保护** | `apps/stock/engine.py` 的 `_advance_locks`；`apps/company_fields/timer.py` 的 `_fiscal_locks` | 并发保护要么落到 DB 层，要么明确写「只支持单进程」并禁止多进程部署 |
| T11 | **以为 `select_for_update` 在工作中** | `apps/stock/engine.py` 显式 `if connection.vendor != "sqlite"` 跳过 | 迁 PG 后行锁会真的生效 → 先列全部调用点再做并发回归 |
| T12 | **静默的限流绕过** | 登录锁按 `(ip, username)` 记录，而 middleware 检查用的 username 未做 `strip`、视图记账用的是 `strip` 后的值（见 [08-技术债与风险.md](08-技术债与风险.md) 的复核条目） | 限流键必须**规范化后再用**，并有一条「等价变体命中同一个桶」的测试 |
| T13 | **「上传物 = 可执行代码」+「放在无鉴权静态目录」** | `/uploads/` 无鉴权（`nginx:80-103`、`urls.py:58-60`）；控件包的 `componentUrl` 指向 `/uploads/widget-packages/<id>/component.js`，前端用 `<script>` 注入主文档 | 可执行资源与静态资源分离；需要鉴权的走带鉴权的下载端点 |
| T14 | **配置文件里「未收录的键」** | `.env.example` 26 个 vs 代码读取 36 个（§2.7） | 用脚本断言「代码读取的键集合 ⊆ 示例键集合」 |
| T15 | **改端口/路径时漏改硬编码处** | `PORT` 有三处来源（`.env`、unit 的 `-p 8000`、`dev.py:51`）；`UPLOAD_DIR` 改了但 nginx 的 `alias` 是写死的（§2.4） | 端口与路径要有**单一真源**，或在部署工具里做一致性校验 |
| T16 | **仓库里存在互相矛盾的模板/脚本** | `nginx-gipfel.conf` vs `nginx-gipfel-optimized.conf`；`gipfel-daphne.service` 被 5 处引用又被 `update.sh` 删除；三套更新入口 | 收敛为**唯一定义**；删除或显式标注废弃物，不要留「两种都像是对的」 |
| T17 | **在仓库里硬编码凭据** | `deploy/migrate-to-postgresql.sh:20` 有一个看起来像真实口令的 `DB_PASSWORD=…`；根 `migrate_to_postgresql.sh:16` 是 `CHANGE_ME_TO_STRONG_PASSWORD` | 凭据只能来自 `.env`/交互输入/密钥管理；禁止入库 |
| T18 | **跨平台脚本的行尾/编码** | `scripts/*.sh` 需要 LF；仓库根有 `.gitattributes` | 在**目标平台**上验证（容忍 CRLF 的兼容层通过 ≠ Linux 可用） |
