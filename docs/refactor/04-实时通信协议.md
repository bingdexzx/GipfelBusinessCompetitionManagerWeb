## 1. 传输与端点

### 1.1 ASGI 分发：与 HTTP **同源同端口**

`.baseline-master/backend/backend/asgi.py` 全文 40 行，核心是 `ASGIApp.__call__`（`:32-37`）：

```python
    async def __call__(self, scope, receive, send):
        path = scope.get("path", "")
        if path.startswith("/socket.io"):
            await self.socketio(scope, receive, send)
        else:
            await self.django(scope, receive, send)
```

| 维度 | 值 | 来源 |
| --- | --- | --- |
| 分发规则 | `scope["path"].startswith("/socket.io")` → python-socketio；其余 → Django ASGI | `asgi.py:34-37` |
| 端口 | **与 REST 完全相同**（同一个 ASGI 进程、同一个端口） | `asgi.py:25` 的 docstring："保持 REST 与 WebSocket **复用同一端口、同源**，与原 NestJS 行为一致。" |
| socket.io path 前缀 | 默认 `/socket.io/`（客户端未覆盖 `path`，服务端 `socketio.ASGIApp(sio)` 用默认值） | `gateway.py:287`；`.baseline-master/frontend/src/realtime/socket.ts:44-53` 未传 `path` |
| 协议版本 | Socket.IO v4 协议（Engine.IO v4）；由 `python-socketio` / `socket.io-client` 版本决定 | 【待确认】精确版本号需 `pip show python-socketio` 与前端 `package.json` 复核；契约层面只依赖 v4 语义 |
| 初始化顺序 | `django.setup()` **先**执行，再 `from apps.realtime.gateway import sio` | `asgi.py:11-14` |
| ASGI 服务器 | `daphne`（置于 `INSTALLED_APPS`，`settings.py:232` 注释："置于 `django.contrib.staticfiles` 之前以接管 runserver"） | `settings.py:232` |
| 应用注册 | `apps.realtime`（`settings.py:266`） | 同上 |
| 完整路由清单 | `backend/urls.py` 全 66 行只有 `admin/`、`api/*`（26 个 `include(...)`）、`/uploads`、`/static`；**没有任何进程间通信入口**。全文 **31 个 `path()` + 2 个 `re_path()` = 33 条路由行** | `urls.py:14-66` |

> ⚠️ **重写陷阱**：`asgi.py` 里 `django.setup()` 必须在 import `gateway` **之前**完成（`asgi.py:11-12`）。
> 因为 `gateway.py` 顶层会调 `_socketio_cors_origins()` → `from django.conf import settings`。
> 顺序颠倒会在启动期抛 `ImproperlyConfigured`。

### 1.2 服务端 `AsyncServer` 参数（`gateway.py:54-59`）

```python
sio = socketio.AsyncServer(
    async_mode="asgi",
    cors_allowed_origins=_socketio_cors_origins(),
    ping_interval=25,
    ping_timeout=20,

```

| 参数 | 值 | 说明 |
| --- | --- | --- |
| `async_mode` | `"asgi"` | 必须与 daphne 匹配 |
| `cors_allowed_origins` | `_socketio_cors_origins()` 的返回值 | 见下 |
| `ping_interval` | **25**（秒） | Engine.IO 心跳间隔 |
| `ping_timeout` | **20**（秒） | 心跳超时 |
| `client_manager` | **未传** | 使用 python-socketio 默认的**进程内**管理（无 Redis / 无跨进程房间） |

`_socketio_cors_origins()`（`gateway.py:27-51`）的逻辑——**关键点：它不做动态反射**：

| `settings.CORS_ORIGIN` | 返回 |
| --- | --- |
| 空（未配置） | `"*"`；且 `DEBUG=False` 时打 warning（CSWSH 风险，`gateway.py:42-46`） |
| 含 `"*"` | `"*"` |
| 显式白名单 | 白名单列表（逐项 `strip`，丢弃空项） |

源码注释（`gateway.py:34-35`）解释了为什么不能像 HTTP 层那样反射：

```
    注意：socket.io 的 cors_allowed_origins 是静态列表，不支持 HTTP 层那样的动态反射校验，
    故直接复用 CORS_ORIGIN 的静态白名单，避免在 WebSocket 层开后门。
```

> ⚠️ **这是与 HTTP CORS 策略的一处刻意不一致**：HTTP 层未配 `CORS_ORIGIN` 时只反射"本地/私网来源"
> （见 [03-认证权限与安全.md](03-认证权限与安全.md) §9.2），而 Socket.IO 层退化为 `"*"`。
> 也就是说**未配置 `CORS_ORIGIN` 的公网部署，WebSocket 层对任意站点开放**（CSWSH）。生产必须配 `CORS_ORIGIN`。
> 见 §11 缺陷 D-09。

## 2. 握手鉴权

### 2.1 token 从哪里取（两种，优先级明确）

`gateway.py:96-105`：

1. **`auth` 字段**（Socket.IO 握手包）：`auth` 是 dict 时取 `auth["token"]`。前端用的就是这个（`socket.ts:45` `auth: { token }`）。
2. **query string 兼容**：若 (1) 没拿到，则解析 `environ["QUERY_STRING"]`，找 `token=` 开头的段，
   取 `pair[len("token="):]`（`gateway.py:100-105`）。

> ⚠️ query 分支**不做 URL 解码**（直接切片）。若 token 含 `%2E` 之类转义或 `&`，会拿到错误值。
> 现前端不用这条路，属低风险既有缺陷（§11 D-07）。

### 2.2 校验链与失败行为

| # | 条件 | 行为 | 客户端观测 |
| --- | --- | --- | --- |
| 1 | `token` 为空 | `return False` | 通用 `Connection rejected`（前端只能看到 `connect_error`） |
| 2 | `decode_jwt_payload(token)` 返回 `None`（签名 / `exp` / `iss` / `aud` 任一不符） | `return False` | 同上 |
| 3 | `_resolve_user(payload)` 返回 `None`（见 §2.3） | 先向 `user-{sub}` 房间 `emit("auth:required", {"reason": "token_version_mismatch"})`，再 `raise ConnectionRefusedError({"message": "auth_required", "reason": "token_version_mismatch"})` | `connect_error` 的 `err.message === "auth_required"` |
| 4 | 全部通过 | 建会话 + 入房间，`return True` | `connect` |

**为什么第 3 步必须抛 `ConnectionRefusedError` 而不是 `return False`**——抄录 `gateway.py:132-135`：

```
        # 抛出 ConnectionRefusedError 而非 return False：
        # - return False 仅发送通用"Connection rejected"，客户端无法区分认证失败和其他原因
        # - ConnectionRefusedError 携带明确的错误标识，客户端 connect_error 处理器可据此
        #   检测到「被顶号」并立即触发 auth:kicked → logout，而非无限重连
```

前端对应实现 `socket.ts:58-70`：

```ts
  socket.on("connect_error", (err: Error & { data?: { reason?: string } }) => {
    const msg = err?.message || "";
    // 服务端 ConnectionRefusedError({"message":"auth_required","reason":"token_version_mismatch"})
    // 的 message 字段为 "auth_required"
    if (msg === "auth_required") {
      logger.warn("[Realtime] 被顶号/认证失败，触发登出");
      socket?.disconnect();                       // 立即停止重连
      window.dispatchEvent(new CustomEvent("auth:kicked"));
      return;
    }
```

> 📌 **两条不可退化的契约**：
> 1. `ConnectionRefusedError` 的首参必须是 `{"message": "auth_required", ...}`——前端**精确比对
>    `err.message === "auth_required"`**（`socket.ts:62`）。若只写 `{"reason": "..."}`，
>    前端拿到的 `message` 会是别的值，于是退化为"无限重连 + 401 噪声"，用户永不被登出。
> 2. 认证失败时**必须**先向 `user-{sub}` 房间广播 `auth:required`（`gateway.py:124-128`）。
>    因为 socket.io 的 `connect` 拒绝只作用于**本次新连接**，`user-{sub}` 房间里**已建立**的旧连接不会因此断开——
>    广播 `auth:required` 是通知它们"你被顶了"的手段。

### 2.3 `_resolve_user`：握手层的校验（`gateway.py:63-79`）

```python
    sub = payload.get("sub") if payload else None
    if not sub:
        return None
    try:
        user = User.objects.get(pk=sub)
    except User.DoesNotExist:
        return None
    except Exception:  # noqa: BLE001
        return None
    if payload.get("tv") != user.token_version:
        return None
    return user
```

| 校验 | 依据 |
| --- | --- |
| `sub` 非空且能查到 `User` | `gateway.py:68-76` |
| `payload["tv"] == user.token_version`（顶号） | `gateway.py:77-78` |
| `user.is_active` | **不校验**（`_resolve_user` 无此分支） |
| `must_change_password` | **不校验** |

> ⚡ **与 HTTP 侧的一致性边界**：
> - HTTP 侧 `JWTAuthentication` 也**不校验** `is_active`（见 [03-认证权限与安全.md](03-认证权限与安全.md) §2.3），
>   所以两侧在"禁用账号"上是一致的——**都不拦**。禁用账号只要持有未过期 token，
>   HTTP 与 WebSocket 都能继续用（§11 D-01）。
> - 强改密期间 Socket.IO **仍可连接并收广播**。这是必要的（改密弹窗需要实时事件），
>   但意味着"强改密门禁"只覆盖 HTTP 面。

| 3 | `enter_room(sid, f"user-{user.id}")`（**无条件**） | `:152` |
| 4 | 若 `competition_id` 非空 → `enter_room(sid, f"comp-{cid}")` | `:153-155` |
| 5 | `return True` | `:158` |

**没有握手即下发状态**：master 的 `connect` 只做上面 5 步，
**不向新连接补发任何状态快照**（对比：若日后需要补发，只能靠 `sync:replay`，见 §6）。

第 1 步的意义（`emit.py:3-11` 的模块 docstring）：

```
【关键集成点】python-socketio AsyncServer(async_mode="asgi") 的 emit 必须在 ASGI
事件循环内执行（await sio.emit）；Django HTTP 视图/信号运行在同步线程中，直接
调用 sio.emit 会因「当前线程无正在运行的 event loop」而静默失败或抛异常。
```

> ⚠️ `register_loop` **只在 `connect` 事件里被调用**（`gateway.py:87-94`）。
> 换言之：**在第一个客户端连上来之前，服务端的一切 `emit` 都会被静默丢弃**
> （`_run_coro_on_loop` 在 `_loop is None` 时返回 `False`，`emit.py:197-199`）。
> 单进程部署下可接受（没人连接就没有投递对象），但这是"顺序依赖"——见 §7 与 §11 D-05。

## 4. 房间模型

### 4.1 命名规则（只有两种）

| 房间名 | 构造 | 语义 |
| --- | --- | --- |
| `comp-{competitionId}` | `f"comp-{cid}"` | 某场比赛的广播组 |
| `user-{userId}` | `f"user-{uid}"` | 某账号的私有推送组 |

**没有别的房间类型**。`_parse_room_key` 允许传入任意 `room` 字符串，但 `_can_join` 只认这两种前缀，
所以自定义房间名一定订阅失败（`gateway.py:189-204`）。

`sid` 本身也是一个房间（socket.io 特性），被用于一个"仅发给本人"的场景：
`sync:replay:result`（`gateway.py:281`）。

### 4.2 加入/退出时机

| 时机 | 房间 | 代码 |
| --- | --- | --- |
| 连接建立（`connect` 成功） | `user-{own_id}` **无条件** | `gateway.py:152` |
| 连接建立且 `user.competition_id` 非空 | `comp-{own_cid}` **自动** | `gateway.py:153-155` |
| 客户端 `emit("subscribe", ...)` 且 `_can_join` 通过 | 请求的房间 | `gateway.py:213-215` |
| 客户端 `emit("unsubscribe", ...)` | 请求的房间（**无权限校验**） | `gateway.py:225` |
| 连接断开 | socket.io 自动移除该 sid 的所有房间 | 无需代码 |

> ⚡ **自动入 `comp-{own_cid}` 的后果**：
> - `PLAYER` / `COMPETITION_ADMIN`（有 `competition_id`）：**连接即已在该比赛房间**，
>   前端的 `subscribeCompetition(comp.id)`（`socket.ts:97-100`）是**冗余的**（但无害，`enter_room` 幂等）。
> - `SUPER_ADMIN`（`competition_id` 为 `null`）：**不会**自动进任何 `comp-*` 房间，
>   必须靠 `subscribeCompetition()` 显式订阅。所以前端那句 `subscribe` 对超管是**必需的**。
> - **重写时若去掉 `connect` 里的自动 `enter_room`**，非超管会收不到任何比赛广播
>   （他们的 `subscribe` 只在 `selectCompetition` / `loadFromStorage` / 重连时发，一旦错过就没有补）。

### 4.3 `_can_join`：可见性边界（`gateway.py:189-204`）

| 房间 | 判定 | 允许 |
| --- | --- | --- |
| `user-{uid}` | `uid == session["user_id"]` | 只能进自己的 |
| `comp-{cid}` | `session["role"] == "SUPER_ADMIN"` → True；否则 `cid == session["competition_id"]` | 超管任意；其余仅自己的比赛 |
| 其它任何名字 | `return False` | 拒绝 |

**`unsubscribe` 不做校验**（`gateway.py:220-227` 没有调 `_can_join`）——这不是漏洞：
退订只会让客户端**少收**事件，不能借此获得任何数据。

### 4.4 广播可见性总表（谁能收到什么）

| 事件 | 投递房间 | 谁能收到 |
| --- | --- | --- |
| `resource:changed`（`emit_resource_changed`） | `comp-{cid}`；`competitionId` 为空或是 `GLOBAL_RESOURCES` → `None`（全局） | 该比赛的所有**已连接**用户（含同比赛的其他人）+（若已订阅）超管 |
| `resource:changed`（定向版） | `user-{uid}` × N | 仅收件人 |
| `permissions:changed` | `user-{uid}` | 仅被赋权者 |
| `auth:required` | `user-{uid}` | 仅该账号 |
| `sync:replay:result` | `sid` | 仅请求者 |
| `message:new` | `user-{uid}` × N | 仅收件人 |
| `fiscal-year:changed` | `comp-{cid}` | 该比赛全体 |
| `competition:changed` | `comp-{cid}` | 该比赛全体 |
| `widget-package:changed` | `None`（全局） | 全体在线用户 |

> ⚠️ **`GLOBAL_RESOURCES = {"industry-types", "industry-fields"}`**（`emit.py:163`）：
> 这两个 resource 的 `resource:changed` **永远发到全局房间**（`room=None`），
> 即使 `competitionId` 非空也被忽略（`emit.py:288-291`）。
> 语义依据：产业类型/产业字段是跨比赛共享的字典数据。
> **重写时若把它们当普通资源处理**，非超管客户端会收不到字典变更。

**可见性过滤只在两处生效**：`_can_join`（订阅时）与 `on_sync_replay`（补发时，§6.3）。
实时广播本身**不做二次过滤**——房间成员关系就是可见性边界。

### 5.1 值为 `None` 的含义（三件事，别只看字面"不广播"）

`signals.py:198-200`：

```python
            # None 表示该模型只列在映射里但显式标记为「不广播」（如 PartMaterial/子表）
            if MODEL_TO_RESOURCE.get(name) is None:
                continue
```

| 含义 | 细节 |
| --- | --- |
| 1. **不连信号 → 不广播** | `connect_all_signals` 跳过它们，`post_save` 不会产生 `resource:changed` |
| 2. **不落审计** | `signals.py:103-105` 与 `:145-147` 都是先 `resolve_model_info(sender)`，`resource` 为 `None` 就 `return` → 也不写 `AuditLog` |
| 3. **但名字必须在表里** | `resolve_model_info` 用 `MODEL_TO_RESOURCE.get(name)`（`emit.py:166-171`）；**不在表里的 model 与值为 `None` 的 model 行为相同**（都不广播不审计）。所以 `None` 条目实际上是"文档性的显式登记"——它的价值是让人看出"这个子表被**有意**排除"，而不是被遗漏 |

> ⚠️ 第 3 点带来一个真实风险：**新增 model 时忘了加进表 = 静默无广播无审计**，
> 与"显式标 None"在运行时**不可区分**。重写时应把这个表变成**强制的、可校验的登记**
> （例如未登记的 model 在启动时告警），而不是查表失败就静默跳过。见 §10 R-5。

## 6. seq 序号与环形缓冲重放

### 6.1 序号生成（**两把锁，不是一把**）

| 项 | 值 | 代码 |
| --- | --- | --- |
| 计数器 | 模块级 `_seq_value: int = 0` | `emit.py:33` |
| 锁 | `_seq_lock = threading.Lock()` | `emit.py:32` |
| 取号函数 | `_next_seq()`：`with _seq_lock: _seq_value += 1; return _seq_value` | `emit.py:66-70` |
| 当前值 | `_current_seq()`（`server_seq()` 的实现，`emit.py:110-111`） | `emit.py:73-75` |
| 环形缓冲的锁 | **另一把** `_ring_lock = threading.Lock()` | `emit.py:37` |
| 写入环 | `_push_ring(event, data, room)`：`with _ring_lock:` append 两个 deque | `emit.py:78-88` |

> ⚠️ **"取号"与"入环"分处两把锁 → 环内 seq 可能非单调**。
> 线程 A 拿到 41、线程 B 拿到 42；若 B 先进入 `_ring_lock` 执行 append，
> `_event_ring` 的 seq 序列会变成 `[..., 42, 41]`，**不再单调递增**。
> 而 `replay_since` 依赖单调性做二分（`_bisect_right_seqs`，`emit.py:91-100`：
> `if _ring_seqs[mid] <= target: lo = mid + 1`）——序列非单调时二分定位会偏移，
> 导致客户端重连补发**重复或漏发**。见 §11 缺陷 D-03。
>
> 重写时必须把"取号 + 写入 `data["seq"]` + 入环"放进**同一个临界区**。

### 6.2 环形缓冲

| 项 | 值 | 来源 |
| --- | --- | --- |
| 长度上限 | `_RING_MAX_LEN = 5000` | `emit.py:36` |
| local 存储 | `collections.deque(maxlen=_RING_MAX_LEN)` × 2：`_event_ring`（条目）与 `_ring_seqs`（并行 seq 数组） | `emit.py:38-40` |
| 条目结构 | `{event, data, room, seq, ts_ms}`，`seq` / `ts_ms` 从 `data` 里取 | `emit.py:79-85` |
| 溢出行为 | `deque(maxlen=...)` **自动淘汰最旧**（append 即挤出） | `emit.py:38-40`、`:86-88` |
| 读取 | `replay_since(last_seq)`：持 `_ring_lock`，二分定位后 `islice(_event_ring, idx, None)` | `emit.py:103-107` |

**溢出行为：丢最旧事件，不触发任何全量刷新信号。** 被淘汰的事件**永久不可补发**，
客户端只能靠对账（`reconcileAllIncremental()`）兜底。见 §9.3。

### 6.3 `sync:replay` 的完整处理流程

服务端 `gateway.py:231-283`：

```python
    last_seq = 0
    if isinstance(data, dict):
        try:
            last_seq = int(data.get("lastSeq") or 0)
        except (TypeError, ValueError):
            last_seq = 0

    from .emit import replay_since, server_seq

    raw_events = replay_since(last_seq) if last_seq > 0 else []
```

| 步骤 | 行为 |
| --- | --- |
| 1 | 解析 `lastSeq`（缺失/非数字 → 0） |
| 2 | **`lastSeq > 0` 才重放**；`lastSeq == 0` 时 `raw_events = []`（**不重放任何东西**） |
| 3 | `replay_since(last_seq)` → 返回 `seq > last_seq` 的条目（环上二分） |
| 4 | **按可见性过滤**（见下表） |
| 5 | `await sio.emit("sync:replay:result", {"ok": True, "events": filtered, "serverSeq": server_seq()}, room=sid)` |
| 6 | `return {"ok": True}`（ack，前端不使用） |

第 4 步的过滤规则（`gateway.py:255-274`，逐条）：

| 条目的 `room` | 是否补发 |
| --- | --- |
| `None`（全局） | ✅ 总是补发 |
| `user-{uid}` | 仅当 `uid == session["user_id"]` |
| `comp-{cid}` | 仅当 `session["role"] == "SUPER_ADMIN"` 或 `cid == session["competition_id"]` |
| **其它任何前缀** | ❌ 跳过（源码注释："其他房间类型暂不重放"） |

> ⚠️ **第 6 步的 ack 与第 5 步的 emit 必须同时在**（原因见 §3.1）。
> ⚠️ `sync:replay:result` **不进环形缓冲**（它直接 `await sio.emit`，不经 `_push_ring`），
> 因此不会被自己触发的事件污染环。

### 6.4 客户端侧：序号跟踪与补发触发

| 环节 | 行为 | 代码 |
| --- | --- | --- |
| 记录 `_lastSeq` | 只在**严格更大**时推进：`if (payload.seq && payload.seq > _lastSeq) _lastSeq = payload.seq` | `resource-changed.ts:69-73` |
| 同步到 socket 模块 | `updateLastReceivedSeq(payload.seq)`（同样只在更大时更新） | `socket.ts:127-131` |
| 补发触发点 | **`onRealtime("connect", ...)`**（**含首次连接与重连**） | `resource-changed.ts:163-171` |
| 补发请求条件 | `if (_lastSeq > 0)` 且 `sock.connected` | 同上 |
| 补发结果处理 | `sync:replay:result` 处理器遍历 `events`，**只处理 `event === "resource:changed"` 的条目** | `resource-changed.ts:136-158` |
| 服务端序号回退检测 | `if (payload.serverSeq < _lastSeq) _lastSeq = 0` | `resource-changed.ts:132-134` |
| 对账 | 无论是否补发，`connect` 处理器最后都调 `reconcileAllIncremental()` | `resource-changed.ts:173` |

> ⚡ **三个容易漏掉的契约**：
> 1. `sync:replay:result` 的 `events` 里**只有 `resource:changed` 会被消费**（`resource-changed.ts:137`）。
>    `permissions:changed` 虽然**入了环**（§3.2），但**不会被补发消费**——
>    它只在实时到达时被处理（`resource-changed.ts:111-122`）。重连期间错过的权限变更**不会补到**。
> 2. `_lastSeq` 是**模块级单例**（`resource-changed.ts:15`），**不区分账号**。
>    换账号登录后（`logout()` → `disconnectRealtime()`）它不会重置，
>    新账号的首个 `connect` 会用上一个账号的 `_lastSeq` 请求补发——
>    服务端按新会话的可见性过滤（§6.3 第 4 步）会挡住越权内容，所以**不是越权漏洞**，
>    但会造成一次多余的补发请求与可能的重复事件处理。→ §11 D-04。
> 3. `lastSeq == 0` 时**完全不重放**（`gateway.py:250`）。首次连接或 `_lastSeq` 被重置后，
>    环里的历史事件不会被补发——这是**有意的**（首次连接不该收到历史事件），
>    但对账必须兜住：`reconcileAllIncremental()` 不在条件分支内（§9.3）。

### 6.5 重连补发的完整时序

```

  │

## 7. 单进程投递模型

### 7.1 为什么需要"跨线程投递"

`emit.py:3-11`（模块 docstring）把问题与方案写死了：

```
【关键集成点】python-socketio AsyncServer(async_mode="asgi") 的 emit 必须在 ASGI
事件循环内执行（await sio.emit）；Django HTTP 视图/信号运行在同步线程中，直接
调用 sio.emit 会因「当前线程无正在运行的 event loop」而静默失败或抛异常。

修复方案（基于 experience 563698）：
1. gateway 保存其 ASGI server 的 running loop（在 connect 事件中记录）
2. 同步侧通过 `asyncio.run_coroutine_threadsafe(coro, loop)` 把协程投递到那个 loop
3. 结果用 Future 等待，但有 1s 超时；超时不阻断 HTTP 主流程
4. loop 未就绪时（如脚本/migrate/测试）降级为静默跳过
```

### 7.2 三个环节

| 环节 | 函数 | 行号 | 行为 |
| --- | --- | --- | --- |
| 注册 loop | `register_loop(loop)` | `emit.py:47-54` | 由 `gateway.connect` 调用；持 `_loop_lock`，仅在 `_loop is None or _loop.is_closed()` 时覆盖。注释："ASGI worker 重启 / reload 后旧 loop 可能已关闭，必须刷新，否则 `_run_coro_on_loop` 会因 `loop.is_running()` 为 False 静默丢弃所有实时广播" |
| 取 loop | `_get_loop_safe()` | `emit.py:57-60` | 持同一把锁读取 |
| 投递 | `_run_coro_on_loop(coro)` | `emit.py:190-209` | `loop is None or not loop.is_running()` → 返回 `False`（静默降级）；否则 `asyncio.run_coroutine_threadsafe(coro, loop)` 后 **`future.result(timeout=0.01)`**（只给调度器 10 ms 挂载，不等待 emit 完成） |

> ⚠️ **模块 docstring 说"有 1s 超时"，代码是 `0.01` 秒**（`emit.py:203` vs `emit.py:10`）。
> 以代码为准：**10 ms**。这不影响正确性（异常被吞、emit 在后台继续），但说明文档与实现已漂移。见 §11 D-06。

### 7.3 唯一的投递出口：`_emit_sio`

`emit.py:212-238`：

```python
def _emit_sio(event: str, payload: dict, room: str | None = None) -> None:
    """把事件投递到 sio；loop 未就绪或失败静默。"""
    try:
        from .gateway import sio
    except Exception:  # noqa: BLE001
        return

    async def _do_emit():
        try:
            if room:
                await sio.emit(event, payload, room=room)
            else:
                await sio.emit(event, payload)
        except Exception:  # noqa: BLE001
            logger.debug("emit_sio await 失败 event=%s", event, exc_info=True)

    # 如果当前就在 ASGI 循环内（Socket.IO 处理器本身），直接 await
    try:
        cur_loop = asyncio.get_running_loop()
        loop_ref = _get_loop_safe()
        if cur_loop is not None and (loop_ref is cur_loop):
            cur_loop.create_task(_do_emit())
            return
    except RuntimeError:
        pass  # 无运行中 loop → 走 run_coroutine_threadsafe

    _run_coro_on_loop(_do_emit())
```

| 分支 | 条件 | 行为 |
| --- | --- | --- |
| A | 当前线程已在**已注册的那个** ASGI loop 内（如 Socket.IO 处理器） | `create_task` 直接调度，不跨线程 |
| B | 当前线程无运行中的 loop（Django 同步视图 / 信号） | `_run_coro_on_loop` → `run_coroutine_threadsafe` |
| C | 有 loop 但不是注册的那个 | 走 B（`run_coroutine_threadsafe` 到注册 loop） |
| D | 未注册 loop（脚本 / migrate / 首次连接前） | `_run_coro_on_loop` 返回 `False`，**静默丢弃** |

### 7.4 全部广播 API 与其"入环/带 seq"语义

`emit.py:276-379`，五个函数，语义各不相同，重写时必须逐一对齐：

| 函数 | 行号 | 取号 | 入环 | 房间 | 延迟到提交后 | 用在哪 |
| --- | --- | --- | --- | --- | --- | --- |
| `emit_resource_changed(resource, record_id, competition_id, action, *, ids=None)` | `:276-311` | ✅ `_next_seq()`（`:305`） | ✅ `_push_ring`（`:308`） | `comp-{cid}` / `None` | ✅ `_after_commit`（`:311`） | 信号（`signals.py:131,171`）与各视图 |
| `emit_resource_changed_to_users(resource, record_id, user_ids, action, competition_id=None, ids=None)` | `:314-345` | ✅ `_next_seq()`（`:339`） | ❌ **不入环** | `user-{uid}` × N | ✅（`:345`） | 消息（`messages/views.py:395,446`） |
| `emit_to_users(user_ids, event, data)` | `:348-350` | ❌ | ❌ | `user-{uid}` × N | ❌ **立即**（无 `_after_commit`） | `auth:required`（`auth/views.py:162`）、`message:new`（`messages/views.py:381`） |
| `emit_to_competition(competition_id, event, data)` | `:353-362` | ❌ | ❌ | `comp-{cid}` | ✅（`:362`） | `fiscal-year:changed`、`competition:changed` |
| `emit_permissions_changed(user_id, permission_version)` | `:368-379` | ✅ `_next_seq()`（`:369`） | ✅ `_push_ring`（`:378`） | `user-{uid}` | ❌ **立即** | `users/views.py:189` |

> ⚠️ **`emit_to_users` 不带 `_after_commit`**，而它的两个调用点都在写事务语义内：
> - `auth/views.py:157-162`：先 `user.save(update_fields=["token_version", ...])` 再 `emit_to_users`，
>   中间**没有** `transaction.atomic`，所以 master 上"提交后立即通知"成立；
> - `messages/views.py:381`：在创建 Message / MessageRecipient 之后立即发。
> 若重写把这些调用包进 `atomic()`，`auth:required` 与 `message:new` **会在提交前发出**，
> 客户端回拉可能读到旧数据。重写时应统一走 `_after_commit`。

### 7.5 单进程约束（**不是可选项**）

| 事实 | 后果 |
| --- | --- |
| `_loop` 是**进程级**全局变量（`emit.py:44`） | 只有"注册过 loop 的那个进程"能投递事件。多进程时，A 进程注册的 loop 与 B 进程的 socket 无关 |
| `_seq_value` / `_event_ring` 都是**进程级**（`emit.py:33,38,40`） | 多 worker 时 seq 与环形缓冲被切成 N 份，`replay_since` 语义错乱 |
| socket.io 的 `client_manager` **未配置**（`gateway.py:54-59`） | 房间成员关系在**进程内**；`comp-{id}` 的广播只覆盖本进程的 socket |
| 无任何"由 HTTP 进程转发事件给 WebSocket 进程"的端点（`urls.py` 全 66 行的路由清单里没有这类入口） | HTTP 进程与 WebSocket 进程无法互通事件 |

**结论（写成硬性部署约束）**：

> ⚠️ **`daphne`（ASGI 进程）必须单进程单实例，且 `/api/*` 业务请求必须由同一个进程承载。**
> 一旦把 REST 拆到独立 WSGI 进程、或给 daphne 加 `--workers N`，实时广播会**部分或全部静默丢失**，
> 且没有任何错误提示（`_run_coro_on_loop` 在 loop 不匹配时只是 drop）。

**仓库里同时存在两个互相冲突的部署模板**——这正是本节结论的**最强证据**（一个正确、一个会破坏实时模型）：

| 模板 | 内容 | 与单进程模型的关系 |
| --- | --- | --- |
| `.baseline-master/deploy/gipfel.service:18-24` | `ExecStart=…/daphne \ -u /run/gipfel/gipfel.sock \ -b 127.0.0.1 \ -p 8000 \ --access-log … \ --proxy-headers \ backend.asgi:application` ——**没有 `--workers`** | ✅ **一致**：单进程，HTTP 与 Socket.IO 同进程同端口，§7.2 的 `register_loop` + `run_coroutine_threadsafe` 得以成立 |
| 同上 `:19-21`、`:27-28` | 同时监听 **Unix socket** `/run/gipfel/gipfel.sock` 与 **`127.0.0.1:8000`**；`RuntimeDirectory=gipfel` + `RuntimeDirectoryMode=0755` 保证 socket 目录存在 | ✅ 一致 |
| `.baseline-master/deploy/gipfel-daphne.service` | `Type=forking`（`:7`）、`Requires=mysql.service`（`:4`）、`ExecStart=/opt/gipfel/deploy/start-daphne-workers.sh`（`:15`），注释"启动 4 个 worker 进程"（`:14`） | ❌ **冲突**：多进程会把 §7.5 表格里的四项全部切成 4 份 |

**若按 `gipfel-daphne.service` + `start-daphne-workers.sh` 部署，会具体坏成什么样**（逐项可验证）：

| 后果 | 机制 |
| --- | --- |
| **seq 与环形缓冲被切成 4 份** | `_seq_value` / `_event_ring` / `_ring_seqs` 都是模块级进程内变量（`emit.py:33,38,40`）。4 个进程各自从 1 开始计数、各自维护 5000 条环 |
| **同比赛的用户可能连在不同 worker 上 → 收不到广播** | socket.io 房间成员关系在进程内（`gateway.py:54-59` 未配 `client_manager`）。worker 8002 上 `emit_resource_changed("contracts", ...)` 只投给 8002 的 socket；连在 8001 的同比赛用户**什么都收不到**，且**无任何日志** |
| **`sync:replay` 可能补到"另一个世界"的环** | 客户端的 `lastSeq` 来自 worker A，重连落到 worker B → worker B 的环里 seq 语义完全不同 → `replay_since` 结果无意义（`gateway.py:250` 起） |
| **`register_loop` 各注册各的** | `_loop` 是单进程全局（`emit.py:44`）；同步 Django 视图只在"自己那个进程"里投递，跨不到别的 worker |
| **心跳参数出现两套数字** | `gateway.py:57-58` 是 `ping_interval=25` / `ping_timeout=20`；`start-daphne-workers.sh:69-70` 是 `--ping-interval 30 --ping-timeout 10`。`【待确认】`两者作用于不同层（python-socketio 的 Engine.IO 心跳 vs daphne 自身 WS keepalive），其交互需实测；此处仅记录"数字不一致"这一事实 |

> 📌 因此本节结论对**重写者**的意义是：**不要照抄仓库里的 systemd 模板**——先数清楚有几个 daphne 进程。
> 部署侧应以 `gipfel.service`（单进程）为准，并在 [07-部署运维与环境变量.md](07-部署运维与环境变量.md) 里明确废弃 `gipfel-daphne.service` 与 `start-daphne-workers.sh`。

**同一类问题的第二个实例：`stock` 的推进锁**（说明"进程内状态"在本项目里是**系统性**的，不是孤例）：

| 证据 | 内容 |
| --- | --- |
| `.baseline-master/backend/apps/stock/engine.py:1842-1843` | `_advance_locks: dict[int, threading.Lock] = {}` + `_advance_locks_guard = threading.Lock()` ——**进程内**锁表 |
| 同文件 `:1849-1852` 的 docstring（逐字） | "当前为进程内 `threading.Lock`，对「单进程 ASGI（daphne 单实例）」部署已能防止同一比赛轮次被并发推进。若未来扩展为多进程/多 worker…需改用跨进程互斥（如 Redis 分布式锁 / Postgres 咨询锁），**本锁本身不跨进程**。" |
| 与本节的关系 | **完全同源**：`seq` 计数器、环形缓冲、ASGI loop、socket 房间成员、限流计数、推进锁——**六处状态全部在进程内存里**，"单进程"不是优化选项而是**正确性前提** |
| 一处容易误判的细节 | `_release_advance_lock`（`:1862-1874`）对同一把锁**连续调用两次 `lock.release()`**（都包在 `try/except RuntimeError` 里）。这**不会**释放他人持有的锁：两次 release 都在同一个 `with _advance_locks_guard` 块内（`:1864`），而取锁路径（`:1854-1859`）也持同一把 guard，因此不存在"释放后别人取到、再被第二次 release 放掉"的交错窗口；第二次 release 抛 `RuntimeError` 被吞掉（`:1871-1874`），**无害**。真正的风险只有上面那句**不跨进程** |

> 因此本节的结论要**扩展到全系统**：只要存在任何一个进程内状态被当作权威，
> 横向扩展（多 daphne worker / 多 WSGI 进程 / 多机）就必须**同时**解决
> seq+环、loop 投递、房间成员、限流计数、业务锁这五类跨进程问题——
> 否则会得到"部分用户收不到广播 + 限流阈值漂移 + 同一比赛被并发推进"的组合故障，且**都不会报错**。
> → 归 [07-部署运维与环境变量.md](07-部署运维与环境变量.md) 与 [08-技术债与风险.md](08-技术债与风险.md)

### 8.2 为什么**禁止**直接 `socket.on(...)`

这不是风格偏好，有四个具体原因：

| # | 原因 | 证据 |
| --- | --- | --- |
| 1 | **socket 是可变单例**，`connectRealtime()` 会在 baseUrl 变化或版本封锁时 `disconnect()` 并重建。直接 `on` 的 handler 绑在**旧实例**上，重建后静默失效 | `socket.ts:33-40`；`stores/competition.ts:255-257` 用 `server:changed` 事件统一重建 |
| 2 | **注册时机决定事件会不会丢**。顶号（`auth:required`）可能在 socket 一建立就到达，而 `bindResourceChanged()` 要等用户**选了比赛**才调用——中间存在竞态窗口 | `socket.ts:71-74`（"bindResourceChanged 在 competition store 选择比赛后才调用，存在竞态窗口：socket 已连接 → 服务端立即广播 auth:required → 但 handler 尚未注册 → 事件丢失"） |
| 3 | **横切逻辑必须集中**：别名归一（`toCollectionKey`）、memo 失效（`bumpResourceEvent`）、400 ms 去抖（`scheduleResourceReload`）、`_lastSeq` 记账——分散到各组件会重复实现且不一致 | `resource-changed.ts:29-49,80-100` |
| 4 | `onRealtime` 在 socket 为 `null` 时会**惰性建连**，直接 `socket.on` 会因 `socket === null` 静默不生效 | `socket.ts:112-115` |

**分层契约（重写时必须保住这个分层）**：

```
socket.io 原生事件
   │
   ├─ 早期注册（socket 创建时）：connect_error / auth:required / reconnect
   │     └─ 只派发 window 事件，不碰业务 store                      [socket.ts:58-85]
   │
   └─ 后期注册（选比赛后 bindRealtime()）：resource:changed / permissions:changed /
        sync:replay:result / connect / fiscal-year:changed / competition:changed
          └─ 归一 + 去抖 + 派发 window CustomEvent
                └─ useResourceChanged()（组件层）→ 重拉列表
                   或 stores/auth.ts / stores/message.ts 等消费方
```

| 中间层 | window 事件名 | 消费者 |
| --- | --- | --- |
| 顶号 | `auth:kicked` | `stores/auth.ts:201-202`（logout）、`stores/message.ts:97-98`（重置幂等锁）、`views/.../competition.ts:24-30`（raw fetch 的 401） |
| 资源变更 | `resource-changed` | `useResourceChanged()` |
| 权限变更 | `permissions-changed` | `stores/auth.ts:217-227` |
| 服务器地址变更 | `server:changed` | `stores/competition.ts:255-257`、`stores/message.ts:95-96` |

> ⚠️ **`onReconnect(handler)` 只有一个槽位**（`socket.ts:10` `let reconnectHandler: (() => void) | null = null`）。
> 多次调用会**静默覆盖**前者。当前只有 `stores/competition.ts:250` 调用它，所以没问题；
> 重写时若让多个模块各注册一次，只有一个能收到重连通知。→ §11 D-05。

### 8.3 断线重连与心跳（两个不同的机制，别混）

| 机制 | 通道 | 参数 | 职责 |
| --- | --- | --- | --- |
| **Socket.IO 心跳**（Engine.IO ping/pong） | WebSocket | `ping_interval=25`，`ping_timeout=20`（`gateway.py:57-58`） | 保持/探测 socket 连接活性。**前端不参与**，由 `socket.io-client` 库内部处理 |
| **会话心跳**（顶号探测） | **HTTP** `GET /api/auth/me` | 固定 **20 秒**（`stores/auth.ts:155`） | 探测"是否被别的设备顶号"（后端 `token_version` 校验 → 401） |

会话心跳为什么必须存在（`stores/auth.ts:150-154`）：

```
  // 绝大多数 GET 走本地缓存、不发网络，旧设备停在界面浏览时不会触发任何被守卫的请求，
  // 也就不会被后端 tokenVersion 校验踢掉。心跳周期性向 /auth/me 真实打网络，
  // 一旦被新设备登录顶号（tokenVersion 不一致 → 后端 401），响应拦截器会清空登录态并跳转登录页。
  // 20s 间隔：作为 socket 实时通道之外的兜底，保证即使 WebSocket 断连也能在 20s 内感知顶号。
```

| 心跳细节 | 值 | 来源 |
| --- | --- | --- |
| 间隔 | `HEARTBEAT_INTERVAL_MS = 20 * 1000`（固定，**无隐藏态自适应**） | `auth.ts:155`、`:180` |
| 请求 | `api.get("/auth/me", { cache: false, silent: true })` | `auth.ts:176` |
| 失败处理 | 401 交给全局响应拦截器（清登录态 + 跳登录页 + 派发 `auth:kicked`）；其余错误静默忽略 | `auth.ts:177-179`；`api/request.ts:108-149` |
| 停止时机 | `logout()`（`auth.ts:184`）、`changePassword()` 开头（`auth.ts:73`） | — |

> ⚠️ 会话心跳打的是 `/api/auth/me`，而该路径**不在强改密放行表内**
> （见 [03-认证权限与安全.md](03-认证权限与安全.md) §4.1）。
> 现系统靠"`changePassword()` 先 `stopHeartbeat()`"规避，属时序脆弱设计。

## 9. 一致性语义

### 9.1 "先落库后广播"是被强制保证的（除两处例外）

`emit._after_commit(fn)`（`emit.py:244-270`）把广播延迟到**数据库事务提交之后**。
源码注释（`emit.py:247-256`）抄录：

```
    为什么必须延迟：post_save 信号在 `save()` 那一刻就触发，显式 emit 也常写在
    `transaction.atomic()` 内部（合同落账 / 复原、股票推进轮次、财年定时器、
    产业字段级联重算）。若此时立即广播，客户端会马上回拉数据，但它走的是另一个
    数据库连接、读不到尚未提交的写入 —— 于是拿到旧值，而事件已经消耗掉、不会再来，
    表现就是「刷新不及时」（数据要等下一次事件或手动刷新才对）。

    行为说明：
    - 不在事务中时，on_commit 会同步立即执行，与原先行为完全一致；
    - 事务回滚时回调被丢弃，顺带消除了「回滚了却已广播」的假事件；
    - seq 在回调内才分配，保证重放环形缓冲的 seq 顺序与实际提交顺序一致。
```

| 语义 | 后果（若退化） |
| --- | --- |
| 广播在提交后 | 否则客户端回拉到**旧值**，且事件不会再来 → "刷新不及时" |
| 回滚时回调被丢弃 | 否则产生"回滚了却已广播"的**假事件**，客户端反复拉不到数据 |
| **`seq` 在回调内才分配** | 否则环内 seq 顺序与提交顺序不一致 → `replay_since` 补发乱序 |
| 无事务时 `on_commit` 同步立即执行（行为不变） | 否则非事务路径的实时性变差 |

**两处不走 `_after_commit` 的例外**（§7.4 表）：`emit_to_users`（`auth:required` / `message:new`）与
`emit_permissions_changed`。它们目前**恰好**都在无外层事务的路径上被调用，所以行为等价；
但这是**隐式依赖**，重写时必须显式化。→ §11 D-08。

### 9.2 广播与 HTTP 响应的时序关系

| 问题 | 答案 | 依据 |
| --- | --- | --- |
| 先落库后广播？ | **是**（§9.1，除两处例外） | `emit.py:244-270` |
| 广播是否可能先于**发起方**的 HTTP 响应到达？ | **可能**。`on_commit` 回调在事务提交那一刻执行，而 HTTP 响应是在视图返回后由框架写出的。两者之间没有顺序保证，且签名/序列化/网络传输各自有延迟 | 架构性结论；【待确认】精确时序需实测（在 `_deliver` 与视图 return 处各打时间戳） |
| 广播是否可能先于**其他客户端**的响应到达？ | 无关——其他客户端没有对应的 HTTP 响应 | — |
| 发起方会不会因为"自己发的广播"而重复刷新？ | **会**，而且这是设计接受的行为。发起方自己的 `resource:changed` 也走同一路径；400 ms 去抖 + memo 失效把它合并成一次重拉 | `resource-changed.ts:34-49` |
| 有没有跨通道的顺序保证？ | **没有**。HTTP 与 WebSocket 是两条独立通道，只保证"事件之间按 `seq` 有序"，不保证"事件与 HTTP 响应之间有序" | — |

> ⚡ **重写时的正确心智模型**：广播是 **at-least-once、按 seq 有序、与 HTTP 无跨通道顺序**的
> "数据变更提示"，**不是**数据本身。客户端收到事件后的动作永远是"回源重拉"
> （`resource-changed.ts` 全篇），而不是"把事件载荷当成新数据直接写进列表"。
> 唯一的例外是 `fiscal-year:changed`（`stores/competition.ts:150-166`）——它把 `fiscalYear` 对象**直接**写进
> `currentFiscalYear`，因为财年状态是单个标量、无并发写风险。重写时若要推广"事件载荷直接落库"，
> 必须逐个评估。

### 9.3 丢失事件的后果与补偿

| 场景 | 事件会丢吗 | 补偿 |
| --- | --- | --- |
| 客户端短暂断线（< 重连时间） | 环里有 → `sync:replay` 补回 | §6.5 时序 |
| 客户端长时间离线，事件**超出环容量 5000** | **会丢**（最旧的被 `deque(maxlen)` 挤出） | `reconcileAllIncremental()` 全量对账（`resource-changed.ts:173`） |
| 服务端重启（`seq` 归零） | **会丢** | 前端 `serverSeq < _lastSeq` → `_lastSeq = 0`，后续按新序号累计；丢失的变更靠对账兜底（`resource-changed.ts:132-134`） |
| `_run_coro_on_loop` 时 loop 未注册 / 不匹配 | **会丢**（静默 drop，`emit.py:197-199`） | 无（多进程部署会造成大面积丢失，§7.5） |
| 事件到达时客户端**没订阅该房间** | 收不到 | 重连后 `handleReconnect()` 重订阅；对账 |
| `permissions:changed` 在断线期间发出 | **会丢**（前端只消费 `resource:changed` 的补发条目） | 无显式补偿；靠用户下一次操作/刷新页面时重新拉 `/auth/me` |
| `resource:changed` 的 `id` 为 `null`（bulk） | 不适用 | 组件按 `bulk` 无条件整表重拉（`useResourceChanged.ts:60-63`） |

> ⚠️ **`reconcileAllIncremental()` 是唯一的最终一致性兜底**，它在**每次 `connect`**（含首次）都会执行
> （`resource-changed.ts:173`，**不在** `if (_lastSeq > 0)` 分支内）。
> 重写时若把它挪进条件分支，首次连接就没了对账；若整个删掉，
> "环溢出 / 服务端重启 / loop 未就绪丢事件"这三类丢失将永久不一致。

### 9.4 批量操作：`suppress_signals()` 避免事件风暴

`common/signals.py:39-60`：

```python
class suppress_signals:
    """上下文管理器：临时关闭所有写操作信号（审计 + 广播）。

    用法：
        with suppress_signals():
            for obj in many: obj.save()  # 不触发 per-row 信号
        emit_resource_changed(..., "bulk")  # 随后统一 bulk 广播

    典型场景：stock advance_round 对 StockOrder/Holding/Candle 大量 save，
    若不抑制会每 save 都发出 resource:changed（单条），前端会收到上百条事件。
    """
```

实现：`threading.local()` 的 `_signals_enabled_local.value`，`__enter__` 保存前值并置 False，
`__exit__` 还原（可嵌套，`signals.py:31-36,53-59`）。
实际调用点示例：`stock/engine.py:1316-1317`、`:1816-1817`、`:1977-1979`
用 `emit_resource_changed("stock-orders"/"stocks", None, competition_id, "bulk")`
（`suppress_signals` 的导入在 `:1903`、使用在 `:1951`）。

`bulk` 事件的载荷特征：`id = None`，`ids = []`
（`emit_resource_changed` 在 `record_id=None` 且未传 `ids` 时 `ids` 为空列表，`emit.py:284-286`）。

> ⚠️ 前端对 `bulk` 的处理是**无条件刷新整个集合**（`useResourceChanged.ts:60-63`）。
> 所以 `bulk` 事件的代价是一次全表重拉。重写时若把大批量的 per-row 写改成一个个 `bulk` 事件，
> 会退化成事件风暴 + 全表重拉风暴。**正确用法是"抑制 per-row + 一条 bulk"。**

## 10. 重构关注点

### ✅ 必须保持的契约（外部可观测）

| # | 契约 | 为什么不能动 |
| --- | --- | --- |
| C-1 | **8 个服务端 → 客户端事件名逐字**（§3.2 列表） | 前端按字符串 `on("...")` 订阅，改名即静默失效——**不报错、不 401，只是永不刷新** |
| C-2 | **3 个客户端 → 服务端事件名逐字**（`subscribe` / `unsubscribe` / `sync:replay`） | 服务端按字符串 `@sio.on("...")` 注册，改名后调用无响应（且 ack 永远不返回） |
| C-3 | **每个事件的载荷字段名与类型**（§3.2 表 + 样例） | 前端直取字段（`payload.seq`、`payload.userId`、`payload.events`…），改名即 undefined |
| C-4 | `resource:changed.action` 的四取值 `created`/`updated`/`deleted`/`bulk` | `deleted` 触发精确移除、`bulk` 无条件刷新，是行为分支 |
| C-5 | 房间命名 `comp-{id}` / `user-{id}`（连字符 + 数字，无空格） | 前后端都用字符串拼接，且服务端 `_can_join` 用前缀解析 |
| C-6 | `connect` 时自动 `enter_room(user-{id})`，有 `competition_id` 时自动 `enter_room(comp-{cid})` | 去掉后非超管收不到任何比赛广播（§4.2） |
| C-7 | 握手凭据在 `auth.token`；兼容 query `token=` | 前端用 `auth.token` |
| C-8 | 握手失败必须 `raise ConnectionRefusedError({"message": "auth_required", ...})` | 前端精确比对 `err.message === "auth_required"`（§2.2） |
| C-9 | 握手失败必须先向 `user-{sub}` 广播 `auth:required` | 否则被顶的旧连接不会下线（§2.2） |
| C-10 | `sync:replay` 的结果必须走 **`sync:replay:result` 事件**（不能只给 ack） | 前端不带回调，ack 被丢弃（§3.1） |
| C-11 | `sync:replay:result` 的载荷是 `{ok, events: [{event, data}], serverSeq}` | 前端读 `payload.events` 与 `payload.serverSeq` |
| C-12 | 服务端序号回退时 `serverSeq < lastSeq` 要能被前端观测到（即必须回传**权威当前序号**） | 前端据此判断"服务端重启过"并重置基线 |
| C-13 | `seq` 单调递增，且 `sync:replay` 返回**严格大于** `lastSeq` 的事件 | 环形缓冲二分定位的前提 |
| C-14 | 环形缓冲默认 5000，溢出淘汰**最旧** | 容量与淘汰方向变了，重连补发的行为就变了 |
| C-15 | 入环/不入环的事件划分逐事件一致（§3.2「入环」列） | 多入环 → 重连重复消费；少入环 → 重连漏事件 |
| C-16 | 广播延迟到 `transaction.on_commit`（`resource:changed` / `permissions:changed` / 两个 `emit_to_*`） | 否则客户端回拉旧值 + 产生回滚后的假事件（§9.1） |
| C-17 | `seq` 在提交后才分配 | 否则补发顺序与落库顺序不一致 |
| C-18 | `MODEL_TO_RESOURCE` 的 39 条映射（含 10 条 `None`）与广播名逐字 | 广播名是前端 `toCollectionKey` 与组件订阅名的输入；改错 → 事件到了不刷新 |
| C-19 | `GLOBAL_RESOURCES = {industry-types, industry-fields}` | 改成按 competitionId 隔离会让非超管收不到字典变更 |
| C-20 | `/socket.io` 与 HTTP **同源同端口** | 前端 `io(getApiBaseUrl())` 不加端口 |
| C-21 | 保留事件名与语义：`connect` / `disconnect` / `connect_error` / `reconnect` | 客户端库行为 |
| C-22 | 客户端 `useResourceChanged` 监听 window `CustomEvent("resource-changed")`，不是 socket | 组件层契约 |
| C-23 | 事件名的**风格逐字**：`resource:changed` / `permissions:changed` / `auth:required` / `sync:replay:result` 用冒号；`fiscal-year:changed` / `competition:changed` / `widget-package:changed` 用连字符 + 冒号；`message:new` 用冒号 | 前端逐字匹配 |
| C-24 | 会话心跳固定 20 s 打 `/api/auth/me`（顶号兜底） | 实时通道之外的唯一顶号感知手段 |
