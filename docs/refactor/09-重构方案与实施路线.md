## 1. 重构目标与非目标

### 1.1 先分清三类问题

`【事实】` 现系统的问题可以分成**性质完全不同**的三类：

| 类别 | 具体问题 | 需要换语言吗？ | 需要换框架吗？ |
| --- | --- | --- | --- |
| **A. 存储/并发级** | SQLite 单写者模型；`select_for_update` 在该引擎上不生效；并发保护依赖库级写锁 + 进程内锁 | ❌ | ❌ |
| **B. 单进程约束级** | 广播投递、`seq` 环、登录限流计数全部在**一个进程的内存**里；一旦多进程即失真 | ❌ | ❌ |
| **C. 结构级** | `preparation`（4,563 行）+ `stock/engine.py` 2,003 行 + `contracts/engine.py` 2,723 行的巨型模块；28 个 app 粒度极不均；前端存在超大组件 | 部分 | ✅ |

> `【建议】` **A 与 B 是"先做掉再谈重写"的**：它们与语言无关，且是重写的**前置**——
> 没有稳定的存储与明确的进程模型，差分测试没有可信基线。
> `【事实】` 它们在 master 上都是真实存在的（[00](00-系统全景与运行时.md) §4.2/§8、[08](08-技术债与风险.md)）。

### 1.2 目标（按优先级）

| # | 目标 | 验收方式 |
| --- | --- | --- |
| G1 | **行为等价**：外部可观测行为与现系统一致 | §7 契约套件 + 差分测试 |
| G2 | **存储与并发语义明确**：不再依赖"库级写锁侥幸串行" | §5 迁移 + §7 压测 |
| G3 | **进程模型与状态归属一致**：要么维持单进程并写明约束，要么外置状态 | §7 并发用例 |
| G4 | **模块边界清晰**：无 2,000 行级单文件 | §4 模块切分 |
| G5 | **建立回归网**：重写后能自动证明"没写坏" | §7 契约套件进 CI |

### 1.3 非目标（**明确不做**）

| # | 不做 | 理由 |
| --- | --- | --- |
| N1 | **不追求"顺手把业务规则改对"** | `【事实】` 股票侧数值包含随机量（详见 [05](05-核心引擎与算法.md) 的可复现性分档），核心链路缺少真实运行基线（[08](08-技术债与风险.md)）。**在没有可信基线的领域改规则 = 无法验证** |
| N2 | **不在重写中引入多租户/SaaS 化** | 现有隔离单元是"比赛"；先把单场比赛隔离做扎实 |
| N3 | **不重写 `/admin` 与日志查看器** | `【建议】` 它们是"同一份 DB + 一次性令牌"的侧车（[07](07-部署运维与环境变量.md)）；重建 Django Admin 是无底洞 |
| N4 | **不借机改前端可见的产品行为** | 前端存在若干**隐性契约**（见 [06](06-前端架构.md)，如效果执行顺序）；改产品行为应单独立项 |
| N5 | **不在没有契约套件的情况下开始写业务代码** | `【事实】` 当前没有自动契约测试（[08](08-技术债与风险.md) 覆盖率盲区）。没有它，"重写验收"无从谈起 |

## 2. 契约冻结清单

> `【事实】` 全部依据见各章。等级：**F1 逐字冻结**（改了会**静默**出错）/ **F2 语义冻结**（可换实现，须前后端同改）/ **F3 行为冻结**（内部可自由重设计，外部结果不变）。

| # | 契约 | 等级 | 冻结到什么程度 | 依据 |
| --- | --- | --- | --- | --- |
| **Z1** | HTTP 响应信封 `{code,message,data}` | **F1** | 逐字；成功时 `code` 的取值规则不变 | [02](02-API契约全集.md) |
| **Z2** | **2xx 必须带 `code: 0`**；错误语义靠 **HTTP 状态码 + `message` 文案**（master **无** `errorCode` 字段） | **F1** | 逐字。前端首判定是 `code !== 0`；且 401 的四类原因只能靠文案区分 | [02](02-API契约全集.md) |
| **Z3** | 全部路径字面量、尾随斜杠方向、创建成功的状态码 | **F1** | 逐字 | [02](02-API契约全集.md) |
| **Z4** | 分页参数名与元字段名 | **F1** | 逐字（写错参数名会**静默**回落到默认值 → 少数据） | [02](02-API契约全集.md) |
| **Z5** | 静态子路径必须排在 `<int:pk>` 之前的**路由顺序** | **F1** | 顺序即契约 | [02](02-API契约全集.md) |
| **Z6** | 增量同步字段名与语义 | **F1** | 逐字 | [02](02-API契约全集.md)、`apps/common/sync.py` |
| **Z7** | `/api/version` 无鉴权 + `data.version` 值等于 `VERSION.json` | **F1** | 逐字（前端据此做版本校验） | [02](02-API契约全集.md)、[06](06-前端架构.md) |
| **Z8** | **39 个权限键的键名逐字 + 19 个域的划分** | **F1** | 逐字。**键名持久化在用户表的 JSON 列里**，改名等于存量授权全失效 | [03](03-认证权限与安全.md) |
| **Z9** | 动作等级表的具体数字与蕴含规则 | **F1** | 逐字 | [03](03-认证权限与安全.md) |
| **Z10** | JWT claims 名与语义（含 `token_version`） | **F1** | 逐字；Socket.IO 握手复用同一解析 | [03](03-认证权限与安全.md)、[04](04-实时通信协议.md) |
| **Z11** | 强制改密的放行路径集合 | **F1** | 集合本身是契约（少一个会锁死管理员） | [03](03-认证权限与安全.md) |
| **Z12** | Socket.IO 服务端→客户端**事件名与载荷字段名** | **F1** | 逐字。前端按字符串订阅，**改名即静默失效**（不报错、只是永不刷新） | [04](04-实时通信协议.md) |
| **Z13** | Socket.IO 客户端→服务端事件名 | **F1** | 逐字（服务端按字符串注册） | [04](04-实时通信协议.md) |
| **Z14** | 房间命名 `comp-{id}` / `user-{id}` | **F1** | 逐字（前后端都用字符串拼接） | [04](04-实时通信协议.md) |
| **Z15** | `MODEL_TO_RESOURCE` 映射的**广播名** | **F1** | 逐字。广播名是前端匹配键的输入 | [04](04-实时通信协议.md) |
| **Z16** | `resource:changed.action` 的取值集合 | **F1** | 逐字（不同取值触发不同刷新分支） | [04](04-实时通信协议.md) |
| **Z17** | 模型 `save()` 自动产生审计 + 广播的**写路径集中化语义** | **F2** | 语义冻结。实现可换（如提交后事件表），但**必须仍然集中**，不能散回视图 | [00](00-系统全景与运行时.md) §5.2/§6 |
| **Z18** | 合同的**条件与效果类型全集及其 JSON 形状** | **F1** | 逐字。存量合同类型必须仍可执行 | [05](05-核心引擎与算法.md) |
| **Z19** | 合同引擎的**执行结果**（含 CAS 防重复、事务边界） | **F3** | 行为冻结，可逐位对拍 | [05](05-核心引擎与算法.md) |
| **Z20** | 股票**撮合结果与定价公式** | **F3** | 行为冻结，可逐位对拍 | [05](05-核心引擎与算法.md) |
| **Z21** | 股票侧的**随机量**（做市商报价、漂移、噪声等） | **F3** | **只能统计对拍**（分布 + 边界 + 不变量）——取决于 [05](05-核心引擎与算法.md) 的可复现性结论 | [05](05-核心引擎与算法.md) |
| **Z22** | 计算图字段的**结构与求值结果** | **F1/F3** | 结构逐字（前端产出的 JSON 要能执行）；结果行为冻结 | [05](05-核心引擎与算法.md)、[06](06-前端架构.md) |
| **Z23** | **41 个 model 的表名/列名**与全部 choices 字面量 | **F1** | 逐字。**枚举值是持久化数据** | [01](01-领域模型与数据库.md) |
| **Z24** | 数值精度与**出站表示**（大数/非整 Decimal 的 JSON 表示） | **F1** | 逐字。改则前端精度丢失 | [01](01-领域模型与数据库.md)、[02](02-API契约全集.md) |
| **Z25** | 前端**哈希路由**与账号隔离存储键格式 | **F2** | 可换，但会破坏书签/深链与"换账号串档"防线 | [06](06-前端架构.md) |
| **Z26** | 前端**隐性契约**（效果执行顺序等，见 [06](06-前端架构.md)） | **F1** | 逐字。这类契约在 UI 上"看起来只是排版"，实际是业务语义 | [06](06-前端架构.md) |

`【事实】` 线上契约**不止 HTTP + Socket.IO**：

| 契约面 | 为什么必须冻结 | 依据 |

| HTTP 形态 | 前端契约 | [02](02-API契约全集.md) |

## 3. 候选目标架构

> `【估算】口径`：**本节不给工期数字**。原因：`【事实】` 无人实现过本系统；[08](08-技术债与风险.md) 指出
> 核心链路缺少真实运行基线、前端缺少自动化测试。在这种前提下给出精确工期是**假精度**。
> 本节只给**方案对比 + 相对工作量排序**。

### 方案 A · 原地演进（Django 保留）

| 维度 | 内容 |
| --- | --- |
| 做什么 | ① 明确并可切换存储（SQLite → PostgreSQL）；② 把 `select_for_update` 依赖处与并发保护改对；③ 明确进程模型（维持单进程**并写明约束**，或外置 `seq`/限流状态）；④ 拆巨型模块；⑤ 前端逐步替换超大组件 |
| 适用场景 | 团队熟练 Django；目标是"把系统做稳"而非换栈；有真实办赛压力、不能停服大改 |
| 模块映射 | 不变（28 个 app 保留） |
| 相对工作量 | **最低** |
| 风险 | 低 |
| **致命缺陷** | ① 不改善 2,723 / 2,003 / 2,701 行三个巨型文件的可维护性（除非 G4 单独立项）；② 若团队本就要去 Django，此方案不解决；③ 每步都可交付，容易"改到一半停下" |
| 依据 | [08](08-技术债与风险.md) 重构必查清单 |

### 方案 B · 后端换语言重写，前端保留

| 维度 | 内容 |
| --- | --- |
| 做什么 | 冻结 §2 全部契约，按**资源前缀**把 `/api/*` 逐个切到新后端；`/socket.io/` 整体切换；`/admin` 与日志查看器保留侧车 |
| 适用场景 | 团队栈不是 Python；或需要 JVM/原生带来的收益；能接受较长过渡期双栈运维 |
| 相对工作量 | **高**。`【事实】` 需重实现：合同引擎（2,723 行 + 条件/效果全集）、股票引擎（2,003 行 + 撮合 + 定价 + K 线）、**建包链路（`preparation` 4,563 行，含 `archive.py` 2,701 行）**、计算图、41 个模型的数据层、39 条广播映射、39 个权限键判定 |
| 风险 | 中高（语义漂移） |
| **致命缺陷** | ① 股票侧随机量**不可逐位对拍** → 只能证明"分布等价"，无法证明"结果等价"；② 需要与 Django 侧共存期间的**审计与广播时序**一致（`transaction.on_commit` 语义）；③ 双栈期间两份权限判定必须严格一致 |
| 依据 | [05](05-核心引擎与算法.md)、[08](08-技术债与风险.md) |

### 方案 C · 全栈重写

| 维度 | 内容 |
| --- | --- |
| 做什么 | 前后端同时重写 |
| 适用场景 | 产品形态本身要变；或前端技术栈已被组织放弃 |
| 相对工作量 | **最高**。`【事实】` 前端 26,449 行 `.vue`，且存在**隐性契约**（[06](06-前端架构.md)） |
| 风险 | **很高** |
| **致命缺陷** | ① 前端**缺少自动化回归**（[08](08-技术债与风险.md)）→ 重写后无法自动证明行为等价；② 合同可视化编辑器与地图画布是**不可替代的交互资产**；③ 一次性切换意味着断崖式风险，与"办赛现场不能出事"直接冲突 |
| 依据 | [06](06-前端架构.md)、[08](08-技术债与风险.md) |

### 对比矩阵

| 维度 | A 原地演进 | B 后端换语言 | C 全栈重写 |
| --- | --- | --- | --- |
| 解决 A 类（存储/并发） | ✅ 直接 | ✅ 需先做同样的事 | ✅ 需先做同样的事 |
| 解决 B 类（单进程约束） | ✅ | ✅ | ✅ |
| 解决 C 类（结构） | ⚠️ 部分 | ✅ 后端部分 | ✅ |
| 换技术栈 | ❌ | ✅ | ✅ |
| 存量数据兼容风险 | 低 | 中 | 中高 |
| **能复用现有回归资产** | ✅ 大部分 | ⚠️ 有限 | ❌ 前端基本没有 |
| 停机需求 | 无 | 无（绞杀者） | 有（或双写） |
| 相对工作量 | 低 | 高 | 最高 |

### `【建议】` 推荐路线

**先做 A 的 ①②③，再决定是否上 B/C。** 理由全部来自前面章节的事实：

1. `【事实】` A/B 类问题**与语言无关**，且是重写的前置（[00](00-系统全景与运行时.md) §10、[08](08-技术债与风险.md)）
2. `【事实】` 重写的**验收基线（黑盒契约套件）目前不存在** → 无论选哪条路，**第一步都是建它**
3. `【事实】` 前端缺少自动化回归，**方案 C 的验收成本最高、风险最集中**
4. `【建议】` 若最终选 C，前端应**推迟到后端契约稳定之后**

## 4. 模块切分建议

### 4.1 现系统模块划分的问题

| # | 问题 | 证据 |
| --- | --- | --- |
| M1 | **粒度极不均**：22 个 app 不足 700 行，而 `preparation` 4,563 行、`stock` 3,776 行、`contracts` 3,755 行 | [00](00-系统全景与运行时.md) §9 |
| M2 | **`common` 是杂物间**：CRUD 基类、响应、异常、分页、权限、中间件、审计、信号、CORS、比赛域、增量同步、字段引用清理全在一个 app（2,176 行 / 20 文件） | [00](00-系统全景与运行时.md) §2.1 |
| M3 | **app 名与内容不符**：`company_fields` 没有自有 model（数据落在 `industry_fields` 与 `company_field_values`） | [01](01-领域模型与数据库.md) |
| M4 | **无显式"平台层"**：审计、广播、权限、比赛域这些横切关注点与业务同级 | [00](00-系统全景与运行时.md) §7 |
| M5 | **三个巨型单文件**：`contracts/engine.py` 2,723 行、`preparation/archive.py` 2,701 行、`stock/engine.py` 2,003 行 | [05](05-核心引擎与算法.md) |

### 4.2 `【建议】` 目标模块边界

```
平台层（横切，不依赖业务）
├── platform/contract      统一响应信封、错误码、分页            ← 现 common/{response,renderers,exceptions,pagination}
├── platform/identity      认证、JWT、会话、令牌版本              ← 现 auth + users
├── platform/authz         权限目录、动作等级、比赛域强制          ← 现 common/{permissions,guards,scope}
├── platform/events        写路径集中化：审计 + 广播 + 提交后投递   ← 现 common/signals + realtime/emit
├── platform/realtime      Socket.IO 网关、房间、seq/重放          ← 现 realtime
├── platform/persistence   表元数据、精度类型、迁移真源            ← 现各 models + common/helpers
├── platform/observability 日志、审计存储、后台网关                ← 现 common/{audit,logfilter,backend_gate} + audit
└── platform/sync          增量同步                               ← 现 common/sync

领域层
├── domain/production     物料→零件→产品→产线/仓库/基础设施/车辆/燃料
├── domain/geography      地图、区域、科技树
├── domain/company        公司、动态字段、产业类型与计算图、消费需求
├── domain/contract       合同模型 + 合同引擎（**拆细**：数值层/解析器/算子/执行器）
├── domain/market         股票：撮合、做市商、K 线、轮次
```

## 5. 数据迁移策略

### 5.1 从 SQLite 出发的前提

`【事实】` master 的**代码里已经有 PostgreSQL 分支**：`settings.py` 读取 `DB_ENGINE` / `DB_HOST` / `DB_PORT` / `DB_NAME` /
`DB_USER` / `DB_PASSWORD` / `DB_CONN_MAX_AGE`，`.env.example` 里也有对应条目；**实际默认跑的是 SQLite**。

`【事实】` ⚠️ **但依赖清单里没有 `psycopg2`**（`requirements.txt` 只有 9 行）→ 真把 `DB_ENGINE` 指到 PostgreSQL，
Django 会在**加载 settings 阶段**就 `ImproperlyConfigured` 起不来。
仓库里另有 `migrate_to_postgresql.sh`、`deploy/migrate-to-postgresql.sh`、`deploy/postgresql-migration-guide.md` 等迁移材料。

`【建议】` 因此切 PG 的工作量比"从零支持"小，但**第一步必须先补驱动依赖**，再走 §5.2。
**注意**：这不是重构，是**配置 + 运维**工作，但它会改变并发语义（见 §5.3）。

### 5.2 步骤

| 步骤 | 要点 |
| --- | --- |
| 1 | **先补 `psycopg2` 依赖**（当前缺失，不补则连 settings 都加载不了） |
| 2 | 以「**模型定义 + 可由零重建**」为迁移真源；物理库与迁移记录都是派生物 |
| 3 | **迁移前对账**：逐表行数 + 内容校验（哈希）；先跑 `foreign_key_check` 之类的一致性检查 |
| 4 | 建 PG 库，字符集/排序规则与时区语义对齐 |
| 5 | 数据搬运后**逐表对账**（行数 + 逐表哈希） |
| 6 | ⚠️ **并发语义会变**：SQLite 下"库级写锁 + `select_for_update` 不生效"与 PG 下"真行锁 + 等待/死锁"是**两种不同的世界**，必须做写并发回归 |
| 7 | ⚠️ **数值语义可能变**：SQLite 的 `decimal` 是 NUMERIC 亲和，但 Django 的 `DecimalField` 取值路径与 PG 的 `numeric` 行为不同，需专门对拍（见 [01](01-领域模型与数据库.md) 的精度分析） |
| 8 | 部署侧：连接数上限、`CONN_MAX_AGE` 语义（**它不是定时器**，详见 [07](07-部署运维与环境变量.md)）、健康检查探活 |

### 5.3 两个**可能发生**的行为变化（必须提前承认或补偿）

| # | 变化 | 说明 | 补偿 |
| --- | --- | --- | --- |
| **P1** | **行锁语义变化** | `【事实】` SQLite 下 `select_for_update` 不是真行锁，并发靠库级写锁 + 进程内锁（[05](05-核心引擎与算法.md)）。换 PG 后它**真的加锁** → 可能出现行锁等待/死锁，也可能把原本会丢失更新的路径保护住 | 先列出所有依赖行锁的代码点，逐点写出「现行为 / 新行为」对照，再做并发回归 |
| **P2** | **数值精度语义变化** | 见 [01](01-领域模型与数据库.md) 的精度分析（`max_digits/decimal_places` 分布与 SQLite 亲和性） | 定"精度契约"（存储/传输/展示三层），**不允许静默截断** |

### 5.4 双跑差分与回滚点

| 项 | 做法 |
| --- | --- |
| 双跑 | 新旧两套后端接同一份「冻结输入集」，比对输出。**可逐位对拍的量逐位对拍；含随机量的只能统计对拍**（分档见 [05](05-核心引擎与算法.md)） |
| 回滚点 | 每个阶段结束做一次**数据库文件级备份**（`【事实】` master 无内置快照系统，所以备份必须在运维层做——见 [07](07-部署运维与环境变量.md)） |

## 6. 分阶段实施路线

### 6.1 绞杀者（渐进）vs 一次性重写

| 维度 | 绞杀者渐进 | 一次性重写 |
| --- | --- | --- |
| 风险分布 | 分散到每一切片（可回滚） | 集中在切换日 |

| 适用 | **本项目**：办赛有固定档期、现场不能出事 | 产品形态要变、可接受停服 |

`【建议】` **选绞杀者**。

## 7. 验收标准：如何证明新系统与旧系统等价

### 7.1 四级验收

| 级别 | 内容 | 通过标准 |
| --- | --- | --- |
| **L1 契约** | 黑盒契约套件（§2 的 F1 条目） | 对新旧两端**同时全绿**；逐字比对 HTTP 形状、错误码、事件名与载荷、权限矩阵 |
| **L2 差分** | 冻结输入集双跑 | **可逐位对拍的量逐位相等**；含随机量的量：分布与边界等价 + 不变量成立（[05](05-核心引擎与算法.md)） |
| **L3 数据** | 迁移对账 | 行数 + 逐表校验一致 |
| **L4 性能** | 压测 | 达到 M4 固化的基线；**多客户端并发写入**下无锁超时、无限流误伤（并发规模与出口 IP 形态需在 M0 由业务方给出，master 无记载） |

### 7.2 必须包含的具体断言

| # | 断言 | 为什么 |
| --- | --- | --- |
| A1 | 未标注权限的**写视图必拒**（若采纳 S6 的 allow-list） | 现模型是 opt-in |
| A2 | **跨比赛 ID 必拒**（非超管） | 比赛域是硬隔离 |
| A3 | 关键计数断言（39 权限键 / 41 model / 事件数…） | 防止文档与代码数字漂移 |
| A4 | **广播时序**：客户端不得回拉到旧值 | `on_commit` 语义 |
| A5 | **seq 单调 + 重连补发不重不漏** | 进程内环是易碎点 |
| A6 | 生产入口可导入（`import wsgi/asgi`、`systemd-analyze verify`、`nginx -t`） | "全绿但上不了线"的经典位置 |
| A7 | 数值出站表示（大数/非整 Decimal） | 静默精度丢失 |
| A8 | 随机量的**不变量与边界** | 无法逐位对拍的部分只能这样验 |

### 7.3 `【估算】` 诚实说明

`【事实】` L2 差分**不可能覆盖全部行为**：股票侧含随机量、核心链路缺真实运行基线。
因此 **M4（基线固化）不是可选项而是前置条件**。

## 10. 一页纸执行摘要

```
第一步（无论最终选哪条路，都必须先做）
  M0 拍板 §9 的决策（尤其 D1 目标、D4 进程模型、D5 存储）
  M1 建「黑盒契约套件」        ← 现在不存在，是唯一的验收基线
  M2 明确状态归属（单进程约束 or 状态外置）
第二步
  M3 存储切换（若选 PG）
  M4 固化差分基线              ← 让核心链路首次在真实规模上跑通并冻结结果
第三步（此时才真正"开始重写"）
  M5–M7 按资源前缀绞杀式切换，或按方案 A 拆模块
  M8 补齐回归网（并行）
  M9 结构整改（并行）
第四步
  M10 全量验收 + 压测 + 旧后端下线
```

**三条不可妥协的红线**：

1. **没有 M1 契约套件，不开工写业务代码** —— 否则无法证明等价
2. **权限键与枚举字面量不得改名** —— 它们是持久化数据
3. **进程模型必须先定，再谈性能** —— 多进程会让广播、seq、限流同时静默失真

**三条最容易犯的错**：

1. 只按 API 文档实施 → 漏掉权限键/枚举/DSL/脚本入口等契约面（§2.1）
2. 把"信号驱动写路径"改成视图里手动调用 → 必然漏播
3. 认为换存储只是改配置 → 行锁与精度语义都会变（P1/P2）
