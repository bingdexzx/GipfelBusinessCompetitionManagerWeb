## 1. 这是什么系统

**一句话**：一套**多人在线商业模拟比赛（商赛）的办赛与参赛平台**。主办方建比赛、配产业链、发合同、跑股票市场；选手在同一场比赛里注册公司、建产线、买卖物料与股票、签约履约；所有客户端通过 WebSocket 实时看到同一场比赛内的变化。

**关键业务概念**（定义见 [01](01-领域模型与数据库.md)）：

| 概念 | 含义 |
| --- | --- |
| 比赛（Competition） | 顶层隔离单元，所有业务数据都归属某一场比赛 |
| 财年（FiscalYear） | 比赛内的时间轴 |
| 公司（Company） | 选手的参赛实体，持有资金、产线、库存、股票 |
| 产业链 | 物料（Material）→ 零件（Part）→ 产品（Product），含科技树前置要求 |
| 地图 / 区域 | 公司选址与基础设施的空间载体 |
| 合同（Contract） | 主办方下发的带条件与效果的规则对象，由引擎结算 |
| 股票（Stock） | 比赛内的模拟证券市场，含集合竞价撮合、AI 做市商、K 线 |
| 产业类型 / 计算图字段 | 由主办方定义的动态字段与依赖求值图 |

**运行特征**（下面每条都能在 master 里找到出处；**具体并发规模在 master 中没有任何记载**）：

- **单机、单进程**：整套后端跑在**一个 daphne 进程**里，HTTP 与 WebSocket 同端口（`backend/asgi.py`、`deploy/gipfel.service`）
- **本地 SQLite 文件**：`settings.py` 写死 `django.db.backends.sqlite3`，没有服务端数据库进程（见 §4.2）
- **多客户端同时在线**：这是设计前提——证据是 Socket.IO 的房间广播、按 (IP, 用户名) 计数的登录限流、以及股票下单/撤单处试图用 `select_for_update` 做行级并发保护
- **实时性是核心体验**：广播带 `seq` 与重放机制，说明"断线后要能补齐"被当成需求
- ⚠️ 各处的**并发规模、部署网络形态（是否共用出口 IP）等运行参数，master 中没有记录**【待确认】；
  因此后文所有与"容量/限流阈值"相关的判断，都只能依据代码里的常量，不能依据业务规模假设

**`deploy/` 有 15 个文件**：3 个 systemd 单元（`gipfel.service`、`logviewer.service`、**`gipfel-daphne.service`**）+
`nginx-gipfel.conf`、`nginx-gipfel-optimized.conf`、`migrate-to-postgresql.sh`、`monitor.sh`、`start-daphne-workers.sh`、
`quick-optimize.sh`、`README.md`、`MIGRATION-README.md`、`postgresql-migration-guide.md`、`mysql-migration-guide.md`、
`README-POSTGRESQL-MIGRATION.md`、`README-OPTIMIZATION.md`。
**`scripts/` 有 23 个**：含 `dev.py`（开发监管进程）、`stop-dev.bat`、`change-db-password.sh`、压测脚本等。

> ⚠️ **三条容易看错的关键事实**（重写取舍都要从这里出发）：
> ① **没有 HTTP/WebSocket 进程拆分**——不存在 gunicorn/WSGI 单元；`/api/*` 与 `/socket.io/*` 都由**同一个 daphne 进程**处理（`deploy/gipfel.service`）。
> ② **PostgreSQL 分支存在但跑不起来**：`settings.py` 读 `DB_ENGINE`/`DB_HOST`/`DB_PORT`/`DB_NAME`/`DB_USER`/`DB_PASSWORD`/`DB_CONN_MAX_AGE`，
>    可切到 PG；**但 `requirements.txt` 里没有 `psycopg2`** → 真去切会在加载 settings 时 `ImproperlyConfigured`。**当前实际运行的是 SQLite。**
> ③ **`deploy/` 里存在多个互相冲突的历史模板**：`gipfel-daphne.service` + `start-daphne-workers.sh` 会起**多个 daphne worker**，
>    与 ②之外更要紧的是——**master 的广播/seq/限流状态全是单进程内存态**（见 §8），多 worker 会**同时静默破坏**它们。
>    另有 `mysql-migration-guide.md` 等与本项目无关或已过时的文档。详见 [07](07-部署运维与环境变量.md) / [08](08-技术债与风险.md)。

## 5. 一次 HTTP 请求的完整生命周期

### 5.1 中间件链（**14 条**，顺序即语义）

来源：`backend/backend/settings.py` 的 `MIDDLEWARE` 列表。

| # | 中间件 | 职责 | 为什么在这个位置 |
| --- | --- | --- | --- |
| 1 | `corsheaders.middleware.CorsMiddleware` | CORS 基础处理 | 最外层，早于任何可能短路响应的中间件 |
| 2 | `apps.common.cors.DynamicCorsMiddleware` | 自研动态 CORS 反射 | 紧跟其后接管判断——静态白名单无法动态反射 |
| 3 | `apps.common.middleware.SecurityHeadersMiddleware` | 安全响应头 | 越早越好，保证异常响应也带头 |
| 4 | `apps.common.middleware.OperatorContextMiddleware` | 建立"当前操作者"上下文（operator / client IP / device），供日志与审计读取 | 早于认证：审计要记录**失败**请求的 IP |
| 5 | `apps.common.middleware.LoginRateLimitMiddleware` | **只拦** `POST /api/auth/login` | 必须能在认证前拒绝 |
| 6 | `django.middleware.security.SecurityMiddleware` | Django 安全中间件 | Django 标准栈起点 |
| 7 | `django.contrib.sessions.middleware.SessionMiddleware` | Session（供 `/admin` 与日志查看器网关） | 早于 `BackendGateMiddleware` |
| 8 | `apps.common.backend_gate.BackendGateMiddleware` | **仅 `/admin/*`**：缺失/无效一次性令牌则 302 回前端 SPA | 必须在 Session 之后（要写 `request.session`） |
| 9 | `django.middleware.common.CommonMiddleware` | URL 规范化 | Django 标准 |
| 10 | `django.middleware.csrf.CsrfViewMiddleware` | CSRF | Django 标准 |
| 11 | `django.contrib.auth.middleware.AuthenticationMiddleware` | Django 认证（`/admin` 用；业务 API 走 DRF） | Django 标准 |
| 12 | `apps.common.rate_limit.RateLimitMiddleware` | **名义上**按角色限制 API 请求频率（配置由 `rate_limit_views.py` 提供） | 放在认证之后是为了读用户角色——**但它在中间件阶段读到的 `request.user` 恒为匿名**（DRF 的 JWT 认证发生在视图派发期，晚于所有中间件）→ **实际不生效**。见 [02](02-API契约全集.md) / [03](03-认证权限与安全.md) |
| 13 | `django.contrib.messages.middleware.MessageMiddleware` | Django messages | Django 标准 |
| 14 | `django.middleware.clickjacking.XFrameOptionsMiddleware` | 点击劫持 | Django 标准 |

> 注：master 上**没有**快照门禁中间件。
> 频率控制实际有**两套**：第 5 条 `LoginRateLimitMiddleware`（**生效**，只作用于登录路径）与第 12 条
> `RateLimitMiddleware`（**文件存在、已挂载，但因读不到用户身份而空转**）。
> 这个"配置齐全但不生效"的模式在 master 上**重复出现**（另见 §12 的不确定性清单），是重写时要特别警惕的一类缺陷。

### 5.2 进入视图之后的固定骨架

```
Browser
  │  axios（Authorization: Bearer <JWT>）
  ▼
nginx（限流 / 静态 / 反代；透传 X-Real-IP、X-Forwarded-Proto）
  ▼
daphne 127.0.0.1:8000
  ▼
[中间件链 #1..#13]                                   ← 见上表
  ▼
URLConf  backend/urls.py → apps/<app>/urls.py        ← 统一 /api 前缀
  ▼
DRF 视图
  ├─ 认证：apps.auth.authentication.JWTAuthentication
  ├─ 全局默认权限：settings.REST_FRAMEWORK.DEFAULT_PERMISSION_CLASSES
  ├─ 视图内权限：@require_permissions("domain:resource:action")
  └─ 比赛域：读过滤 + 写归属（见 [02](02-API契约全集.md) §比赛域隔离）
  ▼
[写操作] 模型 save()/delete()
  ├─ post_save / post_delete 信号（apps/common/signals.py）
  │    ├─ 审计落库 log_write(...) → AuditLog 表
  │    └─ emit_resource_changed(...) → 进程内投递（见 §6）
  └─ 注意：信号在 save() 那一刻触发，**不是事务提交后**；
           emit 内部用 transaction.on_commit 收口延迟投递
  ▼
DRF 渲染器 apps.common.renderers → 统一信封 {code, message, data}
  │  异常路径：apps.common.exceptions.exception_handler → 同信封
  ▼
HTTP 响应
```

**这里有一个重写时必须保留的因果关系**：审计与广播**不是**视图里显式调用的，
而是由**模型信号**统一驱动。只要模型在 `MODEL_TO_RESOURCE` 里注册了，任何地方
（视图、管理命令、admin、其他 app 内部）的 `save()` 都会自动产生审计 + 广播。
这把"忘记广播"的风险降到了零，代价是：**广播粒度绑定在模型类上，无法按业务语义定制**，
且批量操作必须显式抑制信号后手动发 `bulk` 广播。

（信号总开关与批量操作的正确姿势见 `backend/apps/common/signals.py`。）

## 6. 一次实时广播的完整生命周期

**master 是单进程模型**——没有跨进程环节，这是与"多进程部署"形态最大的差别。

```
① 业务代码改动模型
   obj.save() / obj.delete()
        │
        ▼
② apps/common/signals.py 捕获
   · 仅处理 pk 为 int 的实例
   · 查 MODEL_TO_RESOURCE：未注册 → 直接 return；映射值为 None → 只列名，不广播
        │
        ├──────────────────────────────┐
        ▼                              ▼
③ 审计落库                        ④ 实时广播
   log_write(model=resource,          emit_resource_changed(resource, record_id,
             action="<res>:<act>",              competition_id, action)
             record_id, changes,            · action ∈ created/updated/deleted/bulk
             competition_id)                · 延迟到事务提交后（on_commit）
        │                                   · 分配 seq + 写入重放环形缓冲
        ▼                                        │
   AuditLog 表                                   ▼
                                    ⑤ 进程内投递
                                       emit.py 持有 ASGI 事件循环引用（gateway 在
                                       connect 时调用 register_loop 注册），同步信号
                                       通过 run_coroutine_threadsafe 把协程投递到该 loop；
                                       loop 未就绪时（脚本/migrate/测试）静默降级跳过。
                                       ⚠️ 没有跨进程总线、没有内部转发端点。
                                        │
                                        ▼
                             ⑥ Socket.IO 房间广播（python-socketio AsyncServer）
                                · comp-{competitionId}   同场比赛的所有客户端
                                · user-{userId}          定向单用户
                                事件：完整事件表见 [04](04-实时通信协议.md)
                                     （master 实测：服务端→客户端 8 个、客户端→服务端 3 个）
                                        │
                                        ▼
                             ⑦ 浏览器 socket.io-client
                                frontend/src/realtime/ → composable 统一订阅
                                        │
                                        ▼
                             ⑧ 视图响应式刷新
```

**补发机制**：服务端维护递增 `seq` 与重放环形缓冲；客户端重连时通过 `sync:replay` 带上
`lastSeq`，服务端补发缺口。容量与载荷细节见 [04](04-实时通信协议.md)。

## 8. 状态归属：重写时最容易错的地方

| 状态 | 存放位置 | 生命周期 | 丢失后果 |
| --- | --- | --- | --- |
| 全部业务数据 | **SQLite 文件**（`backend/db.sqlite3`，无服务端进程） | 持久 | — |
| 上传文件 | `backend/uploads/`（`UPLOAD_DIR`） | 持久 | 图片/附件丢失 |
| 审计日志 | `AuditLog` 表 | 持久 | 赛后无法追溯 |
| 运行日志 | `LOG_DIR`（默认 `backend/logs/`），按天轮转 | 持久 | — |
| **登录失败计数与锁定** | **进程内存** | **重启即清空** | 重启后锁定失效 |
| **seq 序号与重放环形缓冲** | **进程内存** | 进程内 | **daphne 重启后 seq 与环清空 → 客户端补发失效** |
| **ASGI 事件循环引用** | `realtime/emit.py` 的模块级变量 | 进程内 | 未注册时投递静默跳过 |
| JWT | 浏览器 | 由 `JWT_EXPIRES_IN` 决定（默认 24h） | `token_version` 可即时吊销 |
| 登录态 / 业务缓存 | 浏览器 `localStorage` | 会话 | 各 store 自行管理 |

> **重写结论**：与"多进程/多实例"形态相比，master 的进程内存状态是**自洽的**——
> 因为只有一个进程、只有一份 seq 环、只有一份限流计数。
> **一旦将来拆成多进程（例如加 gunicorn 或多个 daphne worker），这张表里所有"进程内存"的行都会立刻失真**
> （广播丢事件、seq 不单调、限流计数被放大 worker 数倍）。这在 [08](08-技术债与风险.md) 里作为架构约束记录。

## 10. 本章的重构视角结论

**决定重写成败的 5 件事**：

1. **单进程是 master 的隐含前提，不是实现细节。**
   广播投递、seq 环、限流计数全部活在**一个 daphne 进程的内存里**。
   新系统若打算多进程/多实例，这三样**必须外置**，否则会静默丢事件、seq 非单调、限流失效。
   → 本表 §8、[04](04-实时通信协议.md)、[08](08-技术债与风险.md)

2. **写路径集中化（信号驱动）是最优雅也最不可替代的设计。**
   审计与广播由模型信号统一产生，"忘记广播"在结构上不可能发生。
   改成"视图里手动调用"必然漏。
   → §5.2 / §6 / [04](04-实时通信协议.md)

3. **存储是本地 SQLite 文件，且 `select_for_update` 在此引擎上不生效。**
   并发正确性目前依赖 SQLite 的库级写锁 + 进程内锁。
   换存储会**同时改变并发语义**，这是迁移的头号风险。
   → [01](01-领域模型与数据库.md)、[05](05-核心引擎与算法.md)、[08](08-技术债与风险.md)

4. **业务复杂度高度集中在合同与股票两个引擎。**
   `contracts/engine.py`（2,723 行）、`stock/engine.py`（2,003 行）与 `preparation/archive.py`（2,701 行）是系统真正的资产，
   重写的第一原则是**结果等价**，不是代码优雅。
   → [05](05-核心引擎与算法.md)

5. **契约面比"HTTP 接口"宽。**
   除 REST 与 Socket.IO 外，还包括：统一信封（含 2xx 必带 `code: 0`）、错误语义（状态码 + 文案）、权限键字面量（**持久化在用户表里**）、
   事件名与载荷、合同 DSL 的 JSON 形状、归档/导入格式（若存在）、枚举字面量、数值精度与出站表示。
   → [README](README.md) §不可变契约总表

## 11. 重构关注点

### ✅ 必须保持的契约

| 契约 | 内容 | 依据 |
| --- | --- | --- |
| HTTP 路径前缀 | 全部业务接口在 `/api` 下，路径字面量与路由文件一致 | `backend/urls.py` |
| 响应信封 | `{code, message, data}` 三字段形状与语义 | §7 |
| Socket.IO 分流 | `/socket.io` 前缀由 ASGI 层分流给 socket.io 应用，其余给 Django | `backend/asgi.py:34` |
| 同源同端口 | REST 与 WebSocket **复用同一端口** | `backend/asgi.py` 注释 |
| 静态路径无条件托管 | `/uploads/`（`MEDIA_ROOT`）与 `/static/`（`STATIC_ROOT`）用 `re_path` **无条件**挂载——不能用 `django.conf.urls.static.static()`（`DEBUG=False` 时静默 404） | `backend/urls.py:49-59` |
| 信号驱动写路径 | 模型 `save()/delete()` 自动触发审计 + 广播的语义 | `apps/common/signals.py` |
| 中间件顺序 | §5.1 的 **14 条**顺序（尤其 CORS 在认证前、按角色限流在认证后、后台网关在 Session 之后） | `settings.py` MIDDLEWARE |
| 单进程语义 | 广播/seq/限流计数在进程内自洽 | §6、§8 |
| 存储实际形态 | **实际运行 SQLite**；但 `settings.py` **有 PostgreSQL 分支且读 `DB_*` 环境变量**，只是 `requirements.txt` 缺 `psycopg2` → 切库会在加载 settings 时失败。重写时**不要**把"只有 SQLite"当成设计选择，也不要以为"改个环境变量就能切 PG" | `settings.py`、`requirements.txt` |

### 🔄 可以自由重设计的部分

| 部分 | 现状 | 重设计空间 |
| --- | --- | --- |
| 框架与语言 | Django + DRF + python-socketio | 可整体替换（契约不变即可） |
| app 划分 | 28 个 app，粒度极不均（最大的 `preparation` 4,563 行，**22 个不足 700 行**） | 可按限界上下文重新聚类 |

| 重放机制 | 进程内环形缓冲 | 可用事件表 + 游标 |
| 进程内存状态 | 限流计数、seq 环 | **应当**外置 |
| 日志查看器 | 独立 Django 站点 | 可并入统一可观测性栈 |

### ⚠️ 重构陷阱

| # | 陷阱 | 为什么 |
| --- | --- | --- |
| T1 | **引入多进程却不动进程内存状态** | 广播丢事件、seq 非单调、限流计数被放大——且**全是静默失败** |
| T2 | **用 `django.conf.urls.static.static()` 挂 `/uploads`、`/static`** | `DEBUG=False` 时静默 404，表现为"上传成功但图片加载失败" |
| T3 | **放弃"信号驱动广播"，改成视图里手动调用** | 覆盖不全必然发生（管理命令、admin、其他 app 内部调用都会漏） |
| T4 | **认为 `post_save` 在事务提交后触发** | 它在 `save()` 那一刻触发；延迟投递由 emit 内部统一收口，重写必须在**同一层**收口 |
| T5 | **忽略 SQLite 的 `select_for_update` 语义** | 在 SQLite 上它不是真行锁；据此设计并发保护会失效 |
| T6 | **把权限键当成"代码常量"随意改名** | 权限键字面量**持久化在用户表的 JSON 列里**，改名等于让存量授权全部失效 |
| T7 | **改动枚举字面量** | 同样是持久化数据 |
| T8 | **改存储时忘了 `deploy/gipfel.service` 的 `ReadWritePaths` 里列着 `db.sqlite3`** | systemd 对**不存在的路径**会直接失败（挂载命名空间错误）→ 服务无限重启。见 §12 U4 |
