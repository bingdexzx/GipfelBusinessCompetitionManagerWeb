## 3. 架构性缺陷的展开

### 3.0 总纲：该基线的并发与实时状态**全部是「单进程内存」**

| 状态 | 存放位置 | 多进程/多 worker 后的后果 |
| --- | --- | --- |
| **事件序号 `seq` + 环形缓冲** | `emit.py:33,36,38,40`（`_seq_value`、`_event_ring: deque(maxlen=5000)`、`_ring_seqs`），配 `_seq_lock`/`_ring_lock` | 每进程独立 seq 与独立环；`replay_since()`（`:103-107`）只补发本进程事件 → **重连补发漏事件** |
| **广播投递用的 event loop 引用** | `emit.py:43-44`（`_loop`）+ `register_loop()`（`:47-54`） | 只有持有 socket 的进程注册过 loop；REST 落在别的进程 → `_run_coro_on_loop`（`:190-201`）拿不到 loop → **静默丢弃广播**（注释 `#P3`） |
| **Socket.IO 房间** | `gateway.py:152`（`user-{id}`）、`:155`（`comp-{cid}`）、`:215`（订阅房间） | 房间是**每进程一张表** → 同一比赛的用户分散在多进程上时，广播只覆盖一部分 → **部分客户端不刷新** |
| **登录失败限流计数** | `middleware.py:203`（`_locks: dict[(ip, username)]`） | 有效阈值被放大到「进程数 × 阈值」；锁定状态不共享 → **爆破防护被稀释** |
| **按角色限流计数** | `rate_limit.py:42-44`（`_rate_limit_store` + `_lock`） | 同上：`PLAYER` 的 100 次/60 秒变成实际「进程数 × 100」；`reset` 只清当前进程 |
| **并发互斥锁** | `stock/engine.py:1842`（`_advance_locks`）、`company_fields/timer.py:61-62`（`_fiscal_locks`） | 互斥**完全失效** → 可能双推进 |

**结论（作为硬约束写入 09 章）**：`origin/master` **在设计上就是一个单进程应用**。任何「加 worker」的部署变更都不是扩容，而是**同时打破六件事**。若新系统要多进程/多 worker，这六类状态**必须逐一外置**（DB/Redis/队列），或者把「单进程」写成部署期的强制前置条件。

> **已排除的误报（避免重复推导）**：曾有一种说法称「`stock/engine.py` 的 `_release_advance_lock` 会被重复调用、从而释放**他人持有**的锁 → 导致双推进」。**该因果链不成立**，反证为：
> ① 非持有者到不了唯一的释放点（`_release_advance_lock` 的调用位于 `finally`），因为 `advance_round` 的 `raise` 位于 `try` **之前**；
> ② `_release_advance_lock`（`:1862-1868`）在 `with _advance_locks_guard` 内完成两次 release，而 acquire 也需要同一把**非重入**锁（`:1843`）→ 第二次必然打在已解锁的锁上、被吞、**无害**；
> ③ 真正的风险是 `:1849` docstring 自述的「**本锁本身不跨进程**」。
> → 要修的是**跨进程互斥**，不是那个冗余 release。

### 3.1 单写者 × 并发规模：**未知量必须由业务回答**

从源码可以确定的链条：

1. **存储层是单写者**：`DB_ENGINE` 为空 → SQLite（`settings.py:362-370`）。
2. **`timeout=60` 只是把失败推迟**：源码注释说明默认 5 秒太短、股票推进等重操作会触发 `database is locked`。
3. **应用层是单进程**：只有一个 daphne（`deploy/gipfel.service:18-24`），HTTP 与 WebSocket 共享它。
4. **`select_for_update` 在这个引擎上不生效**（AR-02）。
5. **六类状态全在内存**（§3.0）。

> ⚠️ **并发规模是本章最大的未知量，必须由业务确认，不得推测。** 该基线的源码与配置里**没有任何**「客户端数量 / 并发上限 / 网络拓扑」的量化依据。可以拿到手的只有**机制性**事实：
> - 登录失败限流的计数维度是 `(ip, username)`（`middleware.py:203`）→ **若多个客户端共用同一个公网出口，这个维度会退化**；
> - 按角色限流的计数维度是 `user_id`（`rate_limit.py:42`）→ 与出口 IP 无关；
> - Socket.IO 的房间维度是 `user-{id}` / `comp-{cid}`（`gateway.py:152,155`）；
> - `select_for_update` 的使用点见 AR-02。
>
> **确认方法**：① 由业务给出并发客户端数与网络拓扑（是否共用出口）；② 用 `scripts/stress-test.ps1` + `scripts/_load-engine.ps1` 或等价工具在目标环境实测「并发写」的排队与失败率；③ 据此判断是否需要切 PG、是否需要外置限流状态。

### 3.2 ⚠️ 4-worker 模式与单进程内存态的**直接冲突**（重点）

**事实链**：

| 环节 | 事实 | 证据 |
| --- | --- | --- |
| 有一个 4-worker 启动脚本 | `WORKERS=4` / `BASE_PORT=8000` → 在 **8000–8003** 各起一个 `daphne … backend.asgi:application`；启动前先 `pkill -f "daphne.*backend.asgi"` | `deploy/start-daphne-workers.sh:18-19,46,60-75` |
| 它被一个过时 systemd 单元调用 | `gipfel-daphne.service` 的 `ExecStart` 指向它；该单元还 `Requires=mysql.service`、`User=www-data`、无沙箱 | `deploy/gipfel-daphne.service:3-4,8-9,15` |
| 它被 3 处运维脚本调用/推荐 | PG 迁移脚本（`deploy/migrate-to-postgresql.sh:338-339`）、优化脚本（`deploy/quick-optimize.sh:133-134`）、监控脚本的**操作建议**（`deploy/monitor.sh:113,130`） | 同上 |
| 它被另一处当废弃物删除 | `update.sh` 注释「已废弃，由 `gipfel.service` 替代」并 `stop`/`disable`/`rm -f`；还专门「强制释放 8000 端口（旧 `gipfel-daphne` 或手动启动的 daphne 可能占用）」 | `update.sh:435-441`、`:447` |
| 而应用的六类状态**全在进程内存** | §3.0 | —— |
| nginx 只指向其中一个端口 | `upstream gipfel_django` → `server 127.0.0.1:8000`（**仅 worker 1**） | `deploy/nginx-gipfel.conf:9-13` |

**为什么这是「很有价值」的发现**：它不是「某处配置写错了」，而是**两套互不兼容的部署模型同时存在于一个仓库里**，而且**指向旧模型的那条路径写得更清楚、更显眼**（一个 89 行的可执行脚本 + 一个 systemd 单元 + 三处调用/建议），而**指向正确模型的那条只是一个 service 文件里的一行 `-p 8000`**。

**具体失效形态**（按可见性排序）：

| # | 失效 | 用户可见症状 | 根因 |
| --- | --- | --- | --- |
| 1 | **广播只覆盖一部分客户端** | 同一比赛里「有人看到数据变了、有人没变」 | Socket.IO 房间是每进程一张表（`gateway.py:152,155`） |
| 2 | **重连补发漏事件** | 断网重连后「丢了一段更新」 | `seq` 与环是每进程独立（`emit.py:33-40`） |
| 3 | **广播静默丢弃** | 「点了按钮但别人看不到」 | REST 落在无 loop 的进程（`emit.py:190-201`） |
| 4 | **限流被稀释** | 爆破尝试或刷接口没被拦住 | 两个限流表都是进程内（§3.0） |
| 5 | **双推进** | 股票/财年被推进两次，数据错 | 并发锁是进程内（AR-03） |
| 6 | **worker 2–4 成为无主端口** | 无人察觉 | nginx 只覆盖 8000；8001–8003 裸露在回环上 |

**重写结论**：
- ✅ 必须保持：**广播的最终一致性**（房间语义、`seq` 单调、重连补发）与**限流的有效性**。
- 🔄 可以自由重设计：进程模型本身（单进程 / 多进程 / 多容器），以及六类状态的存放位置。
- ⚠️ 陷阱：**「加 worker」在现架构里是负优化**。要么先把六类状态外置，要么把「单进程」写进部署工具并**强制校验**（例如启动时检测是否已有同族进程/端口冲突）。

### 3.3 「全局兜底」是设计意图而非运行时覆盖

`apps/common/guards.py:75` 的注释写「比赛域隔离由 `CompetitionScopePermission` 全局兜底」。该类**确实存在**（`guards.py:105`）且**确实注册在 `DEFAULT_PERMISSION_CLASSES` 里**（`settings.py:341`）—— 但它**在业务视图路径上不生效**（§2-V04）：`apps/*/views.py` 的 90 个 DRF 视图类**全部**显式声明了 `permission_classes`，通用 CRUD 基类也显式覆盖为 `_PERM_CLASSES = (IsAuthenticated, CrudPermission)`（`base_crud.py:46`）。

为什么这比单点 bug 严重：

1. 后人在此基础上做安全决策（「不用每个视图都校验比赛域，全局兜底会拦」）；
2. DRF 的行为是**框架级**的：视图一旦显式声明 `permission_classes`，`DEFAULT_PERMISSION_CLASSES` 就被**完全忽略**；
3. 实际防护只剩视图内显式调用的两道：读过滤与写归属。任何忘记调用它们的新视图 = **跨比赛读写**。

> 这条是「**注释/清单里有一个看起来正确的保护 ≠ 运行时真的有保护**」的典型：清单里有一个看似到位的类，比清单里什么都没有更危险。

### 3.4 广播与 HTTP 响应的一致性、丢事件补偿

| 环节 | 实现 | 风险 |
| --- | --- | --- |
| 触发 | 模型信号 → `emit_resource_changed`（`common/signals.py`） | — |
| 时机 | `_after_commit` → `transaction.on_commit(_run)`（`emit.py:244-267`）→ **回滚不广播、提交后才投递** | 语义正确，但「HTTP 响应可能先于广播返回」是常态 |
| 序号 | `_next_seq()`（`:67-70`）+ `_push_ring()`（`:87-88`）写入 `_event_ring`/`_ring_seqs`（各 `maxlen=5000`） | **纯进程内**（§3.0） |
| 跨循环投递 | `asyncio.run_coroutine_threadsafe(coro, loop)`（`:201`） | loop 未注册/已关闭 → **静默丢弃**（`#P3`） |
| 补偿 | 客户端 `sync:replay`（`gateway.py:231`）→ `replay_since(last_seq)`（`emit.py:103-107`）→ 服务端主动 emit `sync:replay:result`（`gateway.py:279`；注释说明不能只 `return`，因为 ack 会被丢弃） | 只能补发**本进程**环内事件 |
| 事件总量 | **11 个**（S→C 8 + C→S 3，见 §0.3） | 事件目录一旦漂移，前端**静默不刷新** |
| 可观测性 | **无**：没有「投递失败」计数或指标 | 「前端不刷新」在现场无法归因 |

### 3.5 回退类能力的**缺失与替代**

该基线上**没有应用内快照与回退能力**（没有对应 app，也没有强制暂停类门禁）。可用的「回到过去」手段只有：

| 手段 | 位置 | 局限 |
| --- | --- | --- |
| 部署/升级前的文件级备份 | 部署脚本备份段 | 活库 `cp -a`，可能不自洽；无保留策略（OP-03/OP-05） |
| PG 迁移前的 `dumpdata` | `migrate_to_postgresql.sh:69`（含逐 app 回退 `:392-401`） | 只在 PG 迁移路径上 |
| `scripts/change-db-password.sh` 的原子回滚提示 | `:9-12` | 只覆盖密码变更 |
| `update.sh` 的备份分支 | `update.sh:5-6` | 无保留策略 |

**重构结论**：**不要假设现系统有「一键回退」**。重写时若要引入回退能力，它是**新增契约**，必须自己设计并测试，不能按「旧系统怎么做的」来复刻。

### 3.6 Decimal / float 混用的三层问题

| 层 | 现状 | 风险 |
| --- | --- | --- |
| 存储 | 24 处金额 `DecimalField(60,4)` + 22 处 `FloatField`；默认引擎 SQLite（NUMERIC 亲和性） | 精度需在目标引擎实测（§2-V11） |
| 出站 | `renderers.py:25-33` 对 `int > 2^53` 与 Decimal 做了安全转换（含 `is_finite()`），**float 分支没有检查**（`:34-35`） | 一行 `inf`/`nan` 可打挂整个模块的读接口（DA-01） |
| 算法 | 表达式求值器对未定义变量 `return 0`（`engine.py:905`） | 公式写错时静默得 0（DA-04） |

**重写结论**：先定**精度契约**（存储/传输/展示三层），再写存储层。传输层已有一个可复用的约定：`abs(int) > JS_MAX_SAFE_INT (2^53)` 时转字符串（`renderers.py:18,27`）。

### 3.7 动态字段 + 级联重算的递归与性能

`apps/company_fields/` 是一个「用户自定义字段 + 计算图求值」的小型引擎：

| 机制 | 实现 | 评估 |
| --- | --- | --- |
| 依赖排序 | `calc.py` 的 `_order_calc_fields()`：按计算字段之间的 FIELD 依赖做拓扑排序；**成环时放弃重排、按原顺序兜底并打 warning** | 有环检测，但退化是**静默的**（只有日志） |
| 计算图求值 | `calc.py` 的 `_eval_graph()` / `eval_node()`：用 `stack` 做环检测，命中即 warning 并跳过该节点 | 同上 |
| 财年定时器 | `timer.py` 的 `apply_fiscal_year_timer(competition_id, trigger)` + 每比赛一把**进程内**锁 | 与 AR-03 同源 |
| 递归/迭代深度上限 | **未见显式上限常量** | 【待确认】（§7 U4） |

**重写结论**：保留可表达性，但必须 ① 把「环检测」从 warning 升级为**可配置的严格模式**；② 显式设置递归/迭代深度上限并报错；③ 给出规模基线（多少公司 × 多少字段 = 多少时间）。

### 3.8 安全边界的两条独立错误（叠起来才是完整攻击链）

```
① /uploads/** 无鉴权（SE-01）
   → 任何人拿到 URL 即可下载 /uploads/widget-packages/<uid>/component.js
   → 可离线阅读源码、了解内部接口形状
        │
        ▼
② 控件包在主文档执行（SE-02）+ 主文档无 CSP（SE-03）
   → 若攻击者获得超管会话（或促使主办方上传一个"看起来正常"的包）：
     上传 → 所有在线客户端加载 → <script> 在主文档执行
     → 可读取页面可访问的任何状态（含登录态）并以该用户身份发请求
```

**定性**：在「单人办赛、超管即主办方」的场景下风险**可控** —— 能上传控件包的人本来就是最高权限者。但**重写必须显式决策**：接受该信任模型（并写进文档），还是引入沙箱（iframe + `postMessage` / 独立 origin / 严格 CSP + SRI / 声明式 DSL）。**不能默认继承。**

| E15 | **环境变量的键名与语义**（36 个键；`JWT_SECRET` 缺失或弱值 fail-fast；`DB_ENGINE` 为空即 SQLite） | 现场 `.env` 会被复用 | [07-部署运维与环境变量.md](07-部署运维与环境变量.md) §2 |
| E16 | **算法结果的可复现性**（合同结算、股票撮合、产业计算三处） | 比赛的评分与资产都建立在这些数字上 | [05-核心引擎与算法.md](05-核心引擎与算法.md) |

### 🔄 可以自由重设计的部分

| # | 项 | 现系统的问题 | 自由度边界 |
| --- | --- | --- | --- |
| R1 | **进程模型** | 单 daphne 承载 HTTP + WebSocket；另有 4-worker 脚本与单进程内存态冲突（§3.2） | 可拆可合，**但必须先决定「单进程还是多进程」**，因为 §3.0 的六类状态全绑在这一决定上 |
| R2 | **六类进程内状态的存放位置** | `seq`/环、loop 引用、房间、两个限流表、并发锁全在内存 | 可外置到 DB / Redis / 队列；E7/E8/E9/E14 的语义不变。**必须六项一起处理** |
| R3 | **存储引擎** | 默认 SQLite（`OPTIONS.timeout=60`）；PG 分支已有但**依赖未声明** | 可正式切 PG；须同时补驱动（Q2）、重验行锁语义（AR-02）、重测精度（DA-02） |
| R4 | **部署方式** | 980 行 bash + `sed` 渲染；三套更新入口；`ERR` trap 已有但无 `EXIT` trap/回滚 | Ansible/Nix/容器/打包均可；07 章 §10 的 C1/C2/C10/C16 与 T1–T6 语义不变 |
| R5 | **脚本入口收敛** | 三套更新入口 + 3 个 PG 迁移入口 + 3 套压测脚本 | **建议收敛为一条主路径**，PG 迁移做成显式子命令 |
| R6 | **nginx 模板收敛** | 主模板（548，无限流）与 `-optimized`（120，有 30r/s 限流但无人安装、上游名不同）互斥 | 拆成可 include 的片段；把限流并入 80/443 两个形态 |
| R7 | **限流阈值与维度** | 按角色 + 固定阈值；登录锁按 `(ip, username)` | 可按端点分级、可换维度；E14 的对外形态不变 |
| R8 | **前端权限判定的实现** | 前后端各写一份判定 | 可由后端下发可执行 action 集合；E4/E11 的结果不变 |
| R9 | **比赛域隔离的实现层次** | 只靠视图内显式调用的两道约定（AR-09） | 中间件 / 基类 / AOP / DB RLS 均可；**必须显式强制** |
| R10 | **金额字段的存储类型** | 24 处 `Decimal(60,4)` 落在默认引擎的 NUMERIC 列 | 可换 TEXT 亲和自定义字段 / 目标引擎原生 NUMERIC；**不允许静默截断** |
| R11 | **出站渲染的实现** | float 分支无有限性检查（DA-01） | 自由；E2/E3 的约定必须保留 |
| R12 | **动态字段求值引擎** | 环检测只 warning、退化静默；无深度上限 | 可重写为更显式的引擎；E16 的结果不变 |
| R13 | **账号体系** | 业务 `User`（bcrypt）与 `django.contrib.auth.User`（`/admin`、日志查看器）两套 | 可统一；也可保留并明确文档化；E5/E6 的语义不变 |
| R14 | **日志查看器** | 独立 Django 站点 + 自研令牌网关；与业务共用库 | 可用现成方案；E12/E13 与「只有超管能看」不变 |
| R15 | **备份/回滚机制** | 文件级拷贝、无保留策略、无脚本级回滚；**没有应用内快照能力** | 可引入自洽快照 + 保留策略 + 一键回滚（这是**新增**能力，见 Q25） |
| R16 | **systemd 目录结构** | 两个正式 unit 同名共用运行/日志目录、模式 0755、无 `UMask` | 每服务独立目录 + `UMask=0027` |

### ⚠️ 重构陷阱（新系统最容易踩的坑）

| # | 陷阱 | 证据 | 新系统怎么做 |
| --- | --- | --- | --- |
| P1 | **「加 worker」当成扩容** | `deploy/start-daphne-workers.sh:18-19,60-75` + §3.0 的六类进程内状态 | 要么严格单进程，要么把六类状态逐一外置。**没有第三条路** |
| P2 | **沿用「有 PG 分支就等于 PG 可用」的判断** | `requirements.txt` 9 行、无 `psycopg`（OP-10） | 依赖声明与引擎分支**必须同时交付**；部署前置检查加一条「`import psycopg` 可用」 |
| P3 | **以为 `select_for_update` 现在在工作中** | `stock/engine.py:1928-1929` 显式跳过 SQLite | 迁库后行锁**会真的生效** → 先列全部调用点，再做并发回归 |
| P4 | **把「进程内锁」当并发保护** | `stock/engine.py:1842-1868`、`company_fields/timer.py:61-62` | 要么落到 DB 层，要么在部署层**强制**禁止多进程 |
| P5 | **假设 DRF 的 `DEFAULT_PERMISSION_CLASSES` 会兜底** | `guards.py:105` 的类已挂载，但 90 个视图全部显式声明 `permission_classes` | 横切安全策略**显式挂载** + 断言「未标注权限的写视图会被拒绝」 |
| P6 | **以为主文档有 CSP** | CSP 头只在 Django 响应上（且 `/admin` 被跳过）；生产主文档由 nginx 静态托管 | 按「响应由谁发出」判断覆盖面；主文档需在 nginx 层补 CSP |
| P7 | **「上传物 = 可执行代码」+「放在无鉴权静态目录」** | SE-01 + SE-02 | 两者必须**分别**修：可执行资源与静态资源分离；需要鉴权的走带鉴权的下载端点 |
| P8 | **在文件级拷贝上做备份** | 备份段、`quick-sync.sh`、`migrate-server.sh` | 自洽快照（`VACUUM INTO` / `pg_dump`）或强制停服 |
| P9 | **`--delete` + 未锚定的排除模式** | rsync 段的 `--exclude db.sqlite3` 等裸名模式 | 排除模式要**锚定**（前导 `/`）；带边车文件的用通配符 |
| P10 | **`systemctl enable --now` 当「重启」用** | `deploy-linux.sh:583,594` | 「部署生效」必须有断言（版本号/行为探针） |
| P11 | **部署脚本无条件报成功** | `deploy-linux.sh:860` | 引入「问题计数 → 非 0 退出码」；`set -e` 配 `ERR` trap（现已有）并补 `EXIT` trap |
| P12 | **`\|\| true` 吞掉关键失败** | `scripts/migrate-server.sh:239-241,250`（chown 早于 useradd 且都被吞） | 关键步骤不许 `\|\| true`；PATH 不要假设完整（`/usr/sbin` 常缺） |
| P13 | **`ReadWritePaths` 指向可能不存在的路径** | 两个正式 unit 已修好并带警告，但**迁移脚本必须在每次升级时同步清理** | 白名单只列保证存在的路径；把「同步清理」写进部署工具 |
| P14 | **`Restart=always` + 配置错误 = 无限重启且不报警** | `gipfel.service:32-33`；**真实事故：日志查看器重启计数 229** | 补 `StartLimitBurst` + `OnFailure=` 告警单元 |
| P15 | **把「未定义标识符 → 0」当可接受行为** | `contracts/engine.py:905` | 提供严格模式；迁移时全量扫描可疑公式（Q12） |
| P16 | **无界 FloatField + 出站不检查有限性** | `maps/serializers.py:95-96` + `renderers.py:34-35` | 写入拒绝 + 出站兜底 |
| P17 | **先写 `max_digits=60` 再发现精度不够** | 24 处 `Decimal(60,4)`；精度未实测（§2-V11） | **先定精度契约**（存储/传输/展示三层），再写存储层 |
| P18 | **把 `tests/test_*.py` 当回归套件** | §5.2：10 个是探索脚本、1 个是 `console.log`、3 个勉强可重复 | 不要把它们当行为规格；规格要从源码与契约盘点中重新建立 |
| P19 | **依赖 `django_migrations` 等于信任 schema** | 无「模型列 ⊆ 物理列」的对账机制 | 以模型定义为真源，部署前置检查加对账断言 |
| P20 | **认为「有一条自动检查」就够** | `verify-migration.sh` 的 `((PASS++))` 让脚本第一项后就中止（OP-12） | 检查工具自身要有自检（`bash -n`、能被证伪的失败用例） |
| P21 | **仓库里留两套互斥的部署模型** | OP-07/OP-08/OP-09：过时单元被 5 处引用又被删除；两份 nginx 模板 | 收敛为**唯一定义**；删除或显式标注废弃物，不要留「两种都像是对的」 |
| P22 | **在仓库里硬编码凭据** | `deploy/migrate-to-postgresql.sh:20` | 凭据只能来自 `.env`/交互输入/密钥管理；禁止入库 |
| P23 | **忽略「随源码附带的说明文本与代码偏离」本身就是债** | §5.3 B14 | 重写第一步是**契约盘点 + 计数断言**，不是写代码 |
| P24 | **在没有可观测性的情况下上线** | AR-07：无 metrics、空健康检查、无 request id、nginx 无耗时、限流不可观测 | 先补 readiness 与关键计数指标（含限流命中），再补关联 ID，最后补告警 |
| P25 | **假设现系统有「一键回退」** | §3.5：该基线上**没有**应用内快照与回退能力 | 若需要，它是**新增能力**，必须自己设计并测试 |
