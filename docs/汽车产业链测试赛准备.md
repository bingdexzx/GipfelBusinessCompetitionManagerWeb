## 1. 产业链设计

```
 上游资源区                中部智造区                  东部车都
┌───────────┐  运输   ┌────────────┐   运输    ┌────────────┐
│  原料开采  │ ─────▶ │  零部件加工 │ ──────▶  │  整车进销   │
│   2001    │        │    2002    │          │    2003    │
└───────────┘        └────────────┘          └────────────┘
  白云鄂博矿区           中部智造园               东部车都港
  戈壁铝土矿区           中原铁路货场             车都展销中心
  橡胶硅砂基地           上游集运站
```

- **原料**：锂矿石、铝土矿、铁矿石、天然橡胶、石英砂（都带地点价，按地图节点差异定价）
- **零件**：动力电池包、驱动电机、铝合金车身、汽车轮胎、智能座舱域控（原料配比 + 科技前置）
- **产品**：纯电轿车、纯电SUV、商用电动轻卡（零件配比 + `整车平台化` 科技）
- **科技**：电池成组技术 → 电驱系统集成 → 整车平台化（另含轻量化车身工艺）
- **载具**：矿用自卸车、重型卡车、商品车运输车、电动重卡、货运列车、内河滚装船
- **需求**：东部车都 纯电轿车 1200 / 纯电SUV 600；中部智造区 商用电动轻卡 300；上游资源区 120

三大产业共用同一套字段 key（`location` / `cash` / `bank_deposit` / `total_cash` / `quota` /
`inventory` / `ledger` / `carbon` / `contract_amount` / `transport_km` / `last_deal`），
所以**同一份合同模板**可以被链上任意一环的公司使用，`--trial` 对 9 家公司全部通过。

## 2. 三大合同类型

定义在 [`backend/examples/contracts/auto_chain_contracts.py`](../backend/examples/contracts/auto_chain_contracts.py)
（用「合同类型代码化」建库写，产出与可视化编辑器完全同构的四份 JSON）。

| 合同 | key | 参与方 | 主要效果 |
| --- | --- | --- | --- |
| **开采合同** | `auto-mining` | 矿区管理方（主办方）+ 开采企业 | 现金 −（权利金+环保费）、配额 −开采量、库存 +原矿、碳排 +、台账 +1 |
| **购销合同** | `auto-purchase-sale` | 卖方 + 买方 | 按**卖方所在地价**结算（`total_price(清单, at=卖方)`）、双方现金与累计合同额、卖方出库 / 买方入库、双方台账 |
| **运输合同** | `auto-transport` | 委托方 + 承运方 | 按**最短路径路程**（Dijkstra）× 运价计费、超重 +10%、碳税、双方里程与碳排放、双方台账 |

三条约束值得记一笔（都是引擎既有语义，不是本场比赛的特殊处理）：

1. **字典字段只能写常量键值** → 「入库 N 件」用 `range_list` + `for_each` **循环 N 次、每次 +1** 表达；
2. **引擎不套用 inputSchema 的默认值** → 预置合同实例必须把每个输入项**显式填全**，否则按 0 参与运算；
3. 前置检查在效果之前求值 → 检查里用原始值源（如 `freight`），不要用 `assign` 出来的变量。

## 6. 测试途中查出的问题与注意点（未做任何修复）

1. **建包库的计算图助手与产业计算图求值器结构不一致（信息级 bug）**
   `apps/preparation/builder/types.py` 的 `calc_node/calc_graph` 产出的是**合同编辑器风格**的图
   （节点 `type` 直接写 `ADD/FIELD`、连线 `from/to/fromPort/toPort`），而产业计算字段的求值器
   `apps/company_fields/calc.py::_eval_graph` 只认前端「产业计算图」的 GGraph
   （节点 `type` 必须是 `output/value/if/assign`、数值源写在 `data.kind`、
   连线用 `source/target/sourceHandle/targetHandle`、必须有唯一 `output` 汇点）。
   用它建出来的计算字段重算时会被跳过，日志：`[calc] 字段 #xx(total_cash) 计算图无输出/求值为空，跳过`，
   **字段永远是空的**（建包库文档与 `demo_competition.py` 都在示范这种写法）。
   本场比赛的 `total_cash` 因此改为在脚本里直接按求值器结构手写 GGraph
   （见 `_sum_graph()`），重算后 9 家公司的 `货币资金 = 现金 + 银行存款` 均正确。
2. **合同引擎不套用 inputSchema 默认值**（合同建库文档第 9 节陷阱 #7）：预置合同实例必须把每个
   输入项显式填全。初版运输合同实例漏填 `carbon_tax_rate`，碳税被静默算成 0，已修正。
3. **合同执行不触发计算字段重算**：`recompute_calc_fields` 只在「接口写公司字段」与「财年定时器」
   时被调用，所以合同落账后 `货币资金` 会滞后。需要时跑
   `auto_chain_setup.py --recompute-calc`。
4. **重复导入的两个既有行为**：① 比赛内消息不判重，第二次导入会多出一整套（已由
   `auto_chain_setup.py --finish` 去重）；② 已存在的合同实例**只会跳过、不会更新**，
   要改预置实例的参与方/输入项，得先删除该合同再重新导入。
5. **删除比赛时的既有阻断**：`Fuel.competition` 是 `PROTECT` 外键、载具又引用燃料，
   直接删含燃料+载具的比赛会抛 `ProtectedError`（前端「删除比赛」同样会失败）。
   本次重建比赛时的绕行顺序：先删载具 → 再删燃料 → 再删比赛。

## 8. 同一场比赛的「表格建包」写法

比赛**框架**（产业口径 / 地图 / 物资与产能 / 需求 / 合同类型）也可以用表格维护，
策划运营改口径不用碰代码；**公司、账号、合同实例、卡片、消息这些运行期内容不进表格**，
留在界面（或本页的代码脚本）里：
**教程** [比赛 Excel 建包教程](比赛Excel建包教程.md) ·
**规范** [比赛 Excel 建包规范](比赛Excel建包规范.md) ·
示例表 [`backend/examples/excel/汽车产业链示例.xlsx`](../backend/examples/excel/汽车产业链示例.xlsx)
与最小框架 [`backend/examples/excel/最小示例.xlsx`](../backend/examples/excel/最小示例.xlsx)（表头全中文）。

```powershell
cd backend
# 只读表格，看看会建出什么
.\.venv\Scripts\python.exe examples/excel/build_from_sheets.py examples/excel/汽车产业链示例.xlsx --inspect
# 建一场新比赛并导入框架（一条命令）
.\.venv\Scripts\python.exe examples/excel/build_from_sheets.py examples/excel/汽车产业链示例.xlsx --create-competition --name "汽车产业链（表格框架）"
# 再补运行数据（也可以在公司管理 / 账号管理界面里做）
.\.venv\Scripts\python.exe manage.py build_competition examples/competitions/auto_chain_competition.py `
    --competition <比赛id> --resources companies,companyFieldValues,contractInstances,overviewCards,messages `
    --mode overwrite --allow-non-empty
```

实测：表格框架覆盖 26 类资源，其中 **24 类与代码建包逐行一致**（另 2 类为排序/描述等无害差异）；
代码建包多出的 6 类恰好就是运行期数据（公司 / 公司字段值 / 合同实例 / 卡片 / 消息 / 账号）。
先表格建框架（公司、账号、合同实例均为 0）、再补主体后跑合同试算 **9/9 通过**、冒烟金额与代码版完全相同。
